# 运行时动态运营机制结构化梳理

## 1. 核心定义

运行时动态运营，是指 Agentic Playable 发布之后，用户真实进入 H5 体验时，系统根据用户行为、渠道来源、当前进度、风险信号和营销目标，在既定规则边界内动态调整体验和运营动作。

它不是重新生成一个游戏，也不是人工在后台临时改配置，而是 Runtime Agent 在用户会话过程中做小范围、可追踪、可回滚的在线决策。

一句话理解：

运行时动态运营 = 用户正在玩的时候，Agent 根据实时状态决定下一步给什么提示、调什么难度、什么时候展示奖励、什么时候引导分享、什么时候展示 CTA、什么时候触发风控。

## 2. 为什么需要运行时动态运营

传统 Playable 发布后基本是固定体验。

用户看到同一个开场、同一个难度、同一个奖励提示、同一个 CTA、同一个分享文案。

Agentic Playable 的差异在于：

系统可以根据不同用户、不同渠道、不同进度、不同风险状态，动态调整运营动作。

例如：

| 用户状态 | 固定 Playable | Agentic Playable 运行时运营 |
|---|---|---|
| 新用户刚进入 | 展示固定开场 | 展示更低门槛的新手引导 |
| 用户连续失败 | 继续原难度 | 降低难度或给提示 |
| 用户完成度很高 | 展示固定结果页 | 提前准备 CTA 或分享引导 |
| 用户从 KOL 社群进入 | 展示通用文案 | 使用 KOL 专属语气和粉丝称呼 |
| 用户疑似刷奖励 | 正常发奖 | 触发验证、限频或人工复核 |
| 用户点击分享 | 固定分享卡 | 生成更适合当前成绩的分享卡 |

核心价值不是让页面更花哨，而是让营销链路在运行中持续优化。

## 3. 在整体工作流中的位置

运行时动态运营位于发布投放之后，数据反馈之前。

完整链路：

| 顺序 | 环节 | 产物 |
|---|---|---|
| 1 | KOL 身份识别 | `kol_context` |
| 2 | 营销目标选择 | `campaign_goal` |
| 3 | 模板推荐 | `template_schema` |
| 4 | 关键变量填写 | `template_config` |
| 5 | 创作 Brief 生成 | `generation_brief` |
| 6 | 文案、视觉、任务内容生成 | `content_assets` |
| 7 | 游戏规则生成 | `game_rules` |
| 8 | Agent 运营策略生成 | `agent_policy` |
| 9 | 约束与合规验证 | `validation_report` |
| 10 | H5 Playable 组装 | `playable_version` |
| 11 | 模拟测试 | `simulation_result` |
| 12 | KOL 二次编辑 | `config_patch` |
| 13 | 发布投放 | `publish_url` |
| 14 | 运行时动态运营 | `runtime_decision` |
| 15 | 数据反馈与复盘 | `performance_report`、`kol_memory` |

运行时动态运营接收的是已经审核、已经发布、已经可访问的 Playable。

它不能绕过发布审核，也不能把未审核内容临时塞给用户。

## 4. 和 Agent 运营策略生成的区别

Agent 运营策略生成发生在上线前。

运行时动态运营发生在上线后、用户会话中。

| 对比项 | Agent 运营策略生成 | 运行时动态运营 |
|---|---|---|
| 发生时间 | 发布前 | 发布后、用户访问时 |
| 核心问题 | 应该采用什么运营策略 | 当前用户这一刻应该执行哪个动作 |
| 主要产物 | `agent_policy` | `runtime_decision` |
| 决策粒度 | 策略蓝图 | 单次会话、单个节点、单个用户动作 |
| 是否直接影响用户体验 | 间接影响 | 直接影响 |
| 是否需要实时数据 | 主要使用预测和配置 | 必须读取实时事件 |
| 是否可动态变化 | 策略本身相对稳定 | 每次会话都可能不同 |
| 风险重点 | 策略是否合理 | 决策是否越界、是否干扰用户 |

可以理解为：

`agent_policy` 是说明书。

`runtime_decision` 是现场执行动作。

## 5. 和发布投放的区别

发布投放解决的是作品如何上线、审核、分发和触达用户。

运行时动态运营解决的是用户进入作品之后如何被动态运营。

| 对比项 | 发布投放 | 运行时动态运营 |
|---|---|---|
| 核心对象 | 渠道、链接、审核、投放状态 | 用户会话、行为事件、动态策略 |
| 平台动作 | 生成链接、提交审核、发布到渠道 | 读取事件、判断状态、应用决策 |
| KOL 关注 | 是否发出去了、有没有审核通过 | 粉丝玩得怎么样、是否转化更好 |
| 关键数据 | `publish_url`、渠道状态 | `agent_decision_applied`、漏斗表现 |
| 失败类型 | 审核失败、链接异常、连接器失败 | 决策越界、策略无效、风控漏判 |

发布投放是把 Playable 推到用户面前。

运行时动态运营是用户进入之后让体验持续匹配营销目标。

## 6. 和数据反馈的区别

运行时动态运营是在线执行。

数据反馈是事后诊断。

| 对比项 | 运行时动态运营 | 数据反馈与复盘 |
|---|---|---|
| 时间 | 会话中或近实时 | 活动阶段性结束后或周期性汇总 |
| 决策对象 | 单个用户、单个节点、单个渠道片段 | 整体活动、KOL、模板、策略 |
| 输出 | `runtime_decision`、`agent_decision_applied` | `performance_report`、`diagnosis_result` |
| 作用 | 当场调整体验 | 总结效果并反哺下一轮生成 |
| 粒度 | 事件级、会话级 | 活动级、模板级、KOL 级 |

运行时动态运营负责把策略用起来。

数据反馈负责判断这些策略到底有没有用。

## 7. 前台 KOL 能看到什么

MVP 阶段，KOL 不需要看到复杂的决策引擎。

KOL 应该看到的是可理解的运营效果摘要。

| KOL 可见内容 | 说明 |
|---|---|
| 实时访问量 | 有多少人进入 Playable |
| 开始率 | 进入后有多少人点击开始 |
| 完成率 | 有多少人完成游戏或任务 |
| 分享率 | 有多少人点击分享 |
| CTA 点击率 | 有多少人点击目标按钮 |
| 奖励触发数 | 有多少人获得积分、资格、抽奖机会等 |
| 异常拦截数 | 多少疑似刷量或重复领取被拦截 |
| Agent 优化摘要 | Agent 做了哪些动态调整 |
| 表现较好的渠道 | 哪些连接器、渠道或社群效果好 |
| 建议下一步 | 是否建议继续投放、换文案、换 CTA 或复投 |

KOL 不需要理解完整 `runtime_decision` 数据结构。

但平台应该把 Agent 的动态运营结果翻译成 KOL 能理解的语言。

例如：

| 后台事实 | 前台表达 |
|---|---|
| 低完成用户触发提示策略 | 部分用户卡在第 2 步，系统已自动增加提示 |
| 高意向用户提前看到 CTA | 高参与用户在结果页被优先引导加入社群 |
| 风险用户被延迟发奖 | 检测到异常领取行为，系统已自动复核 |
| Telegram 来源转化高 | Telegram 渠道粉丝完成率和 CTA 点击率更高 |

## 8. 后台系统真正发生什么

后台系统在运行时做的是一条在线决策链路。

推荐流程：

| 步骤 | 后台动作 | 关键产物 |
|---|---|---|
| 1 | 用户打开 `publish_url` | `playable_impression` |
| 2 | 系统识别版本、渠道、KOL、活动 | `runtime_context` |
| 3 | 用户点击开始或进入某个场景 | `playable_start`、`scene_view` |
| 4 | 系统更新用户会话状态 | `session_state` |
| 5 | 系统识别用户分群 | `user_segment` |
| 6 | Runtime Agent 读取策略 | `agent_policy` |
| 7 | 系统校验规则边界 | `game_rules`、`runtime_boundaries` |
| 8 | 生成单次运行时决策 | `runtime_decision` |
| 9 | 前端或服务端应用决策 | 动态提示、难度、奖励、CTA 等 |
| 10 | 系统记录决策日志 | `agent_decision_applied` |
| 11 | 用户继续操作 | `user_action`、`step_complete` |
| 12 | 系统观察结果 | `conversion`、`drop_off` |
| 13 | 数据进入看板和诊断 | `runtime_metrics` |

关键原则：

每一次 Agent 改变用户体验，都必须留下决策日志。

否则平台无法判断是内容有效、渠道有效，还是 Agent 决策有效。

## 9. 运行时动态运营的输入

运行时动态运营不是凭空决策。

它需要读取多个上游产物和实时信号。

### 9.1 上游静态输入

| 输入 | 来源 | 作用 |
|---|---|---|
| `kol_context` | KOL 身份识别 | 决定语气、粉丝画像、渠道偏好 |
| `campaign_goal` | 营销目标选择 | 判断优化目标是分享、转化、留存还是教育 |
| `template_schema` | 模板推荐 | 定义模板支持哪些动态槽位 |
| `template_config` | 关键变量填写 | 提供主题、币种、奖励、CTA、难度等配置 |
| `generation_brief` | 创作 Brief | 提供活动意图和内容方向 |
| `content_assets` | 内容生成 | 提供可动态切换的文案、视觉和任务内容 |
| `game_rules` | 游戏规则生成 | 定义玩法、完成条件、奖励和风控边界 |
| `agent_policy` | Agent 运营策略生成 | 定义不同状态下可执行的运营策略 |
| `validation_report` | 约束与合规验证 | 标记哪些内容已通过审核、哪些不可使用 |
| `playable_version` | H5 组装 | 确定当前用户访问的版本 |
| `publish_config` | 发布投放 | 提供渠道、链接、连接器和投放参数 |

### 9.2 运行时实时输入

| 输入 | 说明 | 示例 |
|---|---|---|
| `user_event_stream` | 用户实时事件流 | 开始、点击、失败、完成、分享、CTA 点击 |
| `session_state` | 当前会话状态 | 第几关、分数、失败次数、停留时间 |
| `user_segment` | 用户当前分群 | 新用户、高意向、低完成、风险用户 |
| `channel_context` | 渠道上下文 | X、Telegram、Discord、广告、官网 |
| `device_context` | 设备环境 | 移动端、桌面端、弱网、横竖屏 |
| `risk_signals` | 风险信号 | 重复领取、异常点击、批量访问、设备异常 |
| `performance_signals` | 表现信号 | 当前完成率、点击率、流失节点 |
| `experiment_config` | 实验配置 | A/B 分组、策略开关、灰度比例 |
| `runtime_flags` | 运行开关 | 是否启用动态难度、是否启用动态 CTA |

### 9.3 人工运营输入

| 输入 | 谁配置 | 作用 |
|---|---|---|
| 活动暂停开关 | 平台运营 | 异常时暂停动态策略或暂停活动 |
| 渠道权重 | 平台或 KOL | 决定不同渠道是否优先优化 |
| 奖励库存 | 平台运营 | 控制奖励发放节奏 |
| 风控阈值 | 平台风控 | 控制异常拦截力度 |
| 投放预算 | 平台或广告运营 | 控制付费渠道优化目标 |
| 人工黑名单 | 平台运营 | 限制异常用户或异常渠道 |

## 10. 运行时动态运营的输出

核心输出是 `runtime_decision`。

它代表 Runtime Agent 在某个时刻对某个用户或会话做出的在线决策。

| 输出 | 说明 | 谁使用 |
|---|---|---|
| `runtime_decision` | 单次运行时决策 | 前端、服务端、数据系统 |
| `agent_decision_applied` | 决策应用事件 | 数据系统、诊断系统 |
| `updated_user_segment` | 更新后的用户分群 | Runtime Agent、推荐系统 |
| `runtime_metrics` | 实时表现指标 | 看板、诊断、运营 |
| `risk_action` | 风控处理结果 | 风控系统、奖励系统 |
| `reward_action` | 奖励展示或发放动作 | 奖励系统 |
| `cta_action` | CTA 展示或延迟动作 | 前端、渠道系统 |
| `share_action` | 分享卡或分享引导动作 | 前端、社交连接器 |
| `diagnosis_signal` | 后续诊断线索 | Diagnosis Agent |
| `policy_patch_suggestion` | 策略修正建议 | 运营后台、下一轮生成 |

## 11. `runtime_decision` 数据结构

每一次运行时决策都建议具备以下字段。

| 字段 | 说明 |
|---|---|
| `decision_id` | 决策 ID |
| `playable_version_id` | 当前 Playable 版本 |
| `campaign_id` | 活动 ID |
| `kol_id` | KOL ID |
| `session_id` | 会话 ID |
| `user_id` | 登录用户 ID，未登录时可为空 |
| `anonymous_id` | 匿名用户标识 |
| `channel` | 来源渠道 |
| `connector_id` | 媒体连接器 ID |
| `trigger_event` | 触发决策的事件 |
| `scene_id` | 当前场景、关卡或任务节点 |
| `current_state` | 当前游戏状态 |
| `user_segment` | 当前用户分群 |
| `policy_id` | 命中的 Agent 策略 |
| `decision_type` | 决策类型 |
| `decision_payload` | 具体执行内容 |
| `reason_code` | 决策原因 |
| `expected_metric` | 预期改善指标 |
| `boundary_check` | 边界校验结果 |
| `risk_level` | 风险等级 |
| `experiment_group` | 实验分组 |
| `fallback_used` | 是否使用降级策略 |
| `applied_at` | 决策应用时间 |
| `result_event` | 后续结果事件 |
| `result_metric` | 后续表现 |

## 12. `agent_decision_applied` 事件

`runtime_decision` 是决策对象。

`agent_decision_applied` 是埋点事件。

它用于证明某个 Agent 决策真实影响了用户体验。

| 字段 | 说明 |
|---|---|
| `event_name` | 固定为 `agent_decision_applied` |
| `decision_id` | 对应的运行时决策 |
| `decision_type` | 难度、提示、奖励、CTA、分享、风控等 |
| `decision_action` | 实际应用动作 |
| `before_state` | 应用前状态 |
| `after_state` | 应用后状态 |
| `user_segment` | 应用时用户分群 |
| `policy_id` | 来源策略 |
| `boundary_result` | 是否通过边界校验 |
| `latency_ms` | 决策耗时 |
| `visible_to_user` | 用户是否可感知 |
| `followup_event_window` | 后续效果观察窗口 |

没有这个事件，Agent 的运行时价值无法被归因。

## 13. 核心事件体系

MVP 阶段必须具备基础事件。

| 事件 | 说明 |
|---|---|
| `playable_impression` | H5 加载并可见 |
| `playable_start` | 用户点击开始 |
| `scene_view` | 用户进入页面、关卡或任务节点 |
| `user_action` | 用户点击、选择、拖拽、射击、画线等 |
| `step_complete` | 完成一个题目、任务、波次或关卡 |
| `reward_view` | 用户看到奖励提示 |
| `reward_granted` | 奖励、积分、资格或权益被触发 |
| `share_click` | 用户点击分享 |
| `cta_view` | 用户看到 CTA |
| `cta_click` | 用户点击 CTA |
| `conversion` | 用户完成目标动作 |
| `drop_off` | 用户在关键节点流失 |
| `agent_decision_applied` | Runtime Agent 决策被应用 |
| `risk_triggered` | 风控规则被触发 |
| `fallback_applied` | 降级策略被应用 |

事件记录的最小颗粒度可以理解为：

谁，在什么版本、什么场景、看到了什么 Agent 决策，做了什么动作，最后产生了什么结果。

## 14. 运行时决策闭环

运行时动态运营的核心闭环如下：

| 阶段 | 说明 | 关键问题 |
|---|---|---|
| 事件触发 | 用户产生行为或系统检测到状态变化 | 是否需要决策 |
| 状态更新 | 更新当前会话和用户画像 | 用户现在处于什么状态 |
| 分群识别 | 判断用户属于哪类运营对象 | 应该按什么策略处理 |
| 策略匹配 | 查询 `agent_policy` | 有哪些动作可选 |
| 边界校验 | 检查 `game_rules` 和 `runtime_boundaries` | 是否允许执行 |
| 决策生成 | 生成 `runtime_decision` | 具体执行什么 |
| 动作应用 | 前端或服务端应用决策 | 用户体验如何变化 |
| 日志记录 | 记录 `agent_decision_applied` | 是否可追踪 |
| 结果观察 | 观察用户后续行为 | 是否改善指标 |
| 反馈沉淀 | 进入诊断、看板和 Memory | 下一轮如何优化 |

## 15. 运行时决策类型总览

| 决策类型 | 作用 | 示例 |
|---|---|---|
| 动态难度 | 提高完成率或保持挑战感 | 降低题目难度、减少障碍密度 |
| 动态提示 | 降低卡点流失 | 用户失败两次后显示提示 |
| 动态奖励 | 提升继续参与动力 | 结果页强调下一步奖励 |
| 动态 CTA | 提升转化 | 高意向用户展示入群按钮 |
| 动态分享 | 提升传播 | 根据成绩生成分享文案 |
| 动态留存 | 提升复玩 | 完成后提示明日挑战 |
| 动态推荐 | 推荐下一任务或下一模板 | 完成竞猜后推荐空投任务 |
| 动态风控 | 防止刷量和奖励滥用 | 异常用户延迟发奖 |
| 动态实验 | 测试策略有效性 | CTA 文案 A/B 测试 |
| 动态回退 | 异常时保护体验 | 策略失败回到默认配置 |

## 16. 用户分群机制

运行时动态运营不能只看单个点击。

它要把用户放入可执行的分群中。

| 分群 | 识别依据 | 运营目标 | 可能动作 |
|---|---|---|---|
| 新进入用户 | 首次访问、无历史行为 | 降低理解成本 | 简化引导、降低初始难度 |
| 快速流失风险用户 | 停留短、无操作、首关失败 | 提升开始率和完成率 | 提示、简化任务、减少文案 |
| 低完成用户 | 多次失败、卡在同一节点 | 帮助完成 | 降难度、给提示、减少步骤 |
| 高参与用户 | 多次互动、完成快、分数高 | 引导转化 | 展示 CTA、加入社群、参与下一任务 |
| 分享倾向用户 | 点击分享、查看排行榜 | 扩大传播 | 强化分享卡、展示排名 |
| 奖励敏感用户 | 多次查看奖励、接近领取条件 | 提升完成但控制风险 | 展示进度、明确规则 |
| 回访用户 | 多次访问或复玩 | 提升留存 | 展示新挑战、连续任务 |
| 渠道特定用户 | 来自 X、Telegram、Discord、广告等 | 匹配渠道语境 | 切换 CTA 和文案 |
| 疑似异常用户 | 高频点击、重复领取、设备异常 | 防刷和控损 | 验证、限频、延迟发奖 |

## 17. 分群更新规则

分群不应该只在进入时确定。

它应该随着行为变化而更新。

| 触发条件 | 分群变化 |
|---|---|
| 用户首次进入 | 标记为新进入用户 |
| 用户点击开始 | 从曝光用户变为参与用户 |
| 用户连续失败 | 进入低完成用户或流失风险用户 |
| 用户快速完成 | 进入高参与用户 |
| 用户点击分享 | 进入分享倾向用户 |
| 用户点击 CTA | 进入高意向用户 |
| 用户重复访问 | 进入回访用户 |
| 用户触发异常规则 | 进入风险用户 |

分群变化必须记录。

否则后续无法解释为什么 Runtime Agent 对同一个人采取了不同动作。

## 18. 动态难度运营

动态难度的目标不是让游戏永远变简单。

它的目标是让用户在可完成和有挑战之间保持平衡。

| 场景 | 决策依据 | 动作 |
|---|---|---|
| 用户连续失败 | 失败次数、停留时长 | 降低难度 |
| 用户完成太快 | 完成时间、正确率 | 适度增加挑战 |
| 用户接近流失 | 长时间无操作 | 减少下一步复杂度 |
| 用户来自冷启动渠道 | 渠道转化弱 | 降低首轮门槛 |
| 高参与用户 | 连续完成、分数高 | 解锁进阶挑战 |

MVP 可支持的难度维度：

| 维度 | 示例 |
|---|---|
| 题目数量 | 3 题、5 题、7 题 |
| 题目难度 | 简单、中等、进阶 |
| 时间限制 | 无限制、宽松、标准 |
| 障碍密度 | 少量、标准、密集 |
| 敌人强度 | 低、中、高 |
| 任务步骤 | 简化、标准、完整 |
| 提示强度 | 弱提示、强提示、直接引导 |

动态难度必须受 `game_rules` 约束。

例如规则规定最多 5 题，Runtime Agent 不能临时增加到 8 题。

## 19. 动态提示运营

动态提示用于降低卡点流失。

它不应该一开始就大量出现，否则会削弱游戏感。

| 触发条件 | 提示动作 |
|---|---|
| 首次失败 | 给轻提示 |
| 连续失败两次 | 给强提示 |
| 长时间停留 | 高亮可操作区域 |
| 用户重复点错 | 指示正确方向 |
| 任务规则理解失败 | 简化说明 |
| 用户即将流失 | 给一步完成路径 |

提示内容可以包括：

| 类型 | 说明 |
|---|---|
| 规则提示 | 告诉用户下一步要做什么 |
| 操作提示 | 引导点击、拖拽、射击、画线 |
| 策略提示 | 帮助用户做选择 |
| 奖励提示 | 提醒完成后有什么权益 |
| CTA 提示 | 在合适时机提示下一步行动 |

提示频率必须受控。

否则会变成打扰，而不是运营。

## 20. 动态奖励运营

动态奖励运营不是随意改变奖励。

它只能在已审核、已配置的奖励范围内调整展示、节奏和提醒。

| 可以做 | 不可以做 |
|---|---|
| 调整奖励提示时机 | 把虚拟积分改成真实 Token |
| 展示进度条 | 临时夸大奖励价值 |
| 提醒还差一步完成 | 承诺投资收益 |
| 根据风险延迟发奖 | 绕过反作弊规则发奖 |
| 根据分群展示不同文案 | 展示未审核奖励 |

常见运行时动作：

| 场景 | 动作 |
|---|---|
| 用户完成一半任务 | 展示奖励进度 |
| 用户接近完成 | 强化完成激励 |
| 用户完成任务 | 触发奖励展示或资格确认 |
| 用户重复领取 | 触发风控 |
| 奖励库存紧张 | 改为抽奖资格或等待队列提示 |

奖励策略要特别谨慎。

Web3、数字货币、空投类场景中，MVP 阶段建议只使用虚拟积分、营销权益、抽奖资格、白名单资格等安全表达。

## 21. 动态 CTA 运营

CTA 是营销目标的关键节点。

运行时动态运营要解决的是：

什么时候展示 CTA、展示给谁、展示什么文案、引导到哪里。

| 决策维度 | 示例 |
|---|---|
| 展示时机 | 开始前、完成后、结果页、分享后、回访时 |
| 用户分群 | 高意向用户、低完成用户、分享用户、回访用户 |
| CTA 目标 | 加入社群、领取资格、访问官网、关注账号、下载应用 |
| 文案版本 | KOL 语气、平台语气、奖励导向、挑战导向 |
| 渠道适配 | Telegram 入群、Discord 加社区、X 关注转发 |
| 频率控制 | 每次会话最多展示几次 |

CTA 不应该越界。

例如：

| 边界 | 说明 |
|---|---|
| 未授权 CTA 不展示 | 没有配置的落地页不能运行时生成 |
| 首屏强插要谨慎 | 可能影响开始率 |
| 投资承诺禁止 | 不能用收益承诺引导点击 |
| 频率要控制 | 不能频繁弹窗骚扰用户 |
| 结果要追踪 | CTA 展示和点击必须记录 |

## 22. 动态分享运营

动态分享运营用于提升传播。

它要结合用户成绩、KOL 身份、渠道语境和模板类型。

| 场景 | 动作 |
|---|---|
| 用户获得高分 | 生成炫耀型分享卡 |
| 用户完成挑战 | 生成挑战邀请文案 |
| 用户获得资格 | 生成权益展示文案 |
| 用户来自 KOL 社群 | 使用 KOL 专属称呼 |
| 用户低分但完成 | 生成再挑战邀请 |
| 用户未完成 | 不强推分享，优先降低流失 |

分享素材可动态调整：

| 元素 | 示例 |
|---|---|
| 分享标题 | 我的预测命中率超过 80% |
| 分享副标题 | 来挑战 KOL 的专属行情房 |
| 分享图 | 用户成绩、KOL 头像、活动主题 |
| 分享按钮 | 发到 X、Telegram、Discord |
| 邀请语 | 粉丝专属挑战、社群排名、限时资格 |

分享动作必须和外部平台规则一致。

不能用虚假奖励、误导性收益、强制转发等方式换取用户传播。

## 23. 动态留存运营

运行时动态运营不仅看一次转化，也要看用户是否愿意回来。

| 留存场景 | 动作 |
|---|---|
| 用户完成首轮 | 推荐下一轮挑战 |
| 用户获得分数 | 引导明日刷新排名 |
| 用户领取资格 | 提醒后续任务 |
| 用户加入社群 | 引导关注下一次活动 |
| 用户未完成 | 下次访问时从简化节点开始 |
| 用户回访 | 展示新任务或新奖励进度 |

MVP 阶段可以先做轻量留存：

| 能力 | 说明 |
|---|---|
| 回访识别 | 识别用户是否访问过 |
| 进度恢复 | 恢复上次完成状态 |
| 简单连续任务 | 今日挑战、明日挑战 |
| 结果页复玩 | 再玩一次、挑战更高分 |
| 社群留存 | 引导加入社群接收下一次任务 |

## 24. 动态推荐运营

动态推荐是指系统根据用户行为推荐下一步动作。

它可以推荐任务、模板、活动、CTA 或社群路径。

| 用户行为 | 推荐动作 |
|---|---|
| 完成竞猜 | 推荐加入行情讨论社群 |
| 完成空投任务 | 推荐下一步关注或邀请 |
| 高分完成跑酷 | 推荐分享排行榜 |
| 完成塔防挑战 | 推荐解锁进阶挑战 |
| 低完成用户 | 推荐更简单的任务 |
| 高意向用户 | 推荐直接转化路径 |

MVP 阶段不需要复杂推荐系统。

可以先基于规则和分群做轻量推荐。

## 25. 动态风控运营

风控是运行时动态运营的底线能力。

只要存在奖励、资格、积分、抽奖、空投、白名单，就必须有风控。

| 风险类型 | 信号 | 动作 |
|---|---|---|
| 高频点击 | 极短时间大量操作 | 限频、验证码、忽略部分事件 |
| 重复领取 | 同设备、同钱包、同账号多次领取 | 阻止或人工复核 |
| 批量访问 | 同 IP 或同设备指纹异常集中 | 降低奖励权重 |
| 异常完成 | 完成时间远低于正常用户 | 延迟发奖 |
| 渠道刷量 | 某渠道异常高曝光低互动 | 标记渠道风险 |
| 恶意分享 | 大量无效分享 | 不计入奖励 |
| 钱包风险 | 钱包黑名单或异常地址 | 拦截资格 |

风控动作分级：

| 风险等级 | 动作 |
|---|---|
| 低风险 | 继续观察 |
| 中风险 | 降低奖励、增加验证 |
| 高风险 | 暂停发奖、人工复核 |
| 严重风险 | 阻断行为、标记黑名单 |

Runtime Agent 不能绕过风控。

如果策略建议和风控规则冲突，风控优先。

## 26. 运行时边界 `runtime_boundaries`

运行时动态运营必须有明确边界。

边界来自 `game_rules`、`agent_policy`、合规规则、平台治理规则和渠道规则。

| 边界 | 说明 |
|---|---|
| 目标边界 | 不能改变活动主目标 |
| 玩法边界 | 不能改变核心玩法和完成条件 |
| 奖励边界 | 不能改变奖励性质和发放规则 |
| CTA 边界 | 不能展示未授权 CTA |
| 合规边界 | 不能生成收益承诺、投资建议、虚假宣传 |
| 风控边界 | 不能绕过验证和风险拦截 |
| 数据边界 | 不能采集未授权敏感数据 |
| 频率边界 | 不能过度展示提示、弹窗、CTA |
| 版本边界 | 不能把未审核配置下发给线上用户 |
| 渠道边界 | 不能违反外部平台发布规则 |

边界失败时，Runtime Agent 必须降级到默认策略。

## 27. 运行时可变与不可变内容

不是所有内容都可以运行时变化。

| 内容 | 是否可运行时变化 | 说明 |
|---|---|---|
| 活动主目标 | 不可变 | 例如从拉新改成交易转化，不允许 |
| 核心玩法类型 | 不可变 | 竞猜不能临时变成塔防 |
| 主要奖励性质 | 不可变 | 虚拟积分不能变成真实 Token |
| 完成条件 | 原则上不可变 | 只能在规则允许范围内调整 |
| CTA 目标 | 受限可变 | 只能在审核通过的目标中选择 |
| 提示文案 | 可变 | 需来自已审核文案池 |
| 难度参数 | 可变 | 必须在 `game_rules` 范围内 |
| 分享文案 | 可变 | 必须合规且来自模板池 |
| 任务顺序 | 受限可变 | 只能在规则允许范围内调整 |
| 风控强度 | 可变 | 可提高，不能降低底线 |
| 实验分组 | 可变 | 需受实验配置控制 |

## 28. 渠道维度的动态运营

不同渠道的用户意图和行为不同。

运行时动态运营需要读取 `channel_context`。

| 渠道 | 用户特点 | 运营重点 |
|---|---|---|
| X / Twitter | 浏览快、分享意愿强 | 强化标题、结果分享、轻 CTA |
| Telegram | 社群转化强 | 强化入群、任务进度、KOL 语气 |
| Discord | 社区任务和身份感强 | 强化身份、角色、成就和社群任务 |
| 广告渠道 | 低信任、跳出高 | 降低首屏理解成本、缩短路径 |
| 官网 | 意图更明确 | 强化产品价值和转化 CTA |
| KOL 私域 | 信任高、粉丝关系强 | 使用 KOL 专属表达和排行榜 |

渠道差异不应该导致规则差异失控。

不同渠道可以有不同文案、CTA 顺序和提示节奏，但不能有不一致的奖励承诺。

## 29. 模板维度的运行时运营

不同模板的运行时动态运营重点不同。

### 29.1 竞猜 / 预测模板

| 场景 | 动态运营动作 |
|---|---|
| 用户首次答题 | 展示规则和低门槛提示 |
| 用户连续答错 | 降低题目难度或给背景提示 |
| 用户命中率高 | 展示成绩、排行榜、分享卡 |
| 用户完成后 | 引导加入社群或查看下一题 |
| 用户风险异常 | 检查重复参与和异常奖励领取 |

边界：

不能生成投资建议。

不能承诺收益。

不能把预测结果包装成确定性结论。

### 29.2 空投任务模板

| 场景 | 动态运营动作 |
|---|---|
| 用户进入任务页 | 展示任务步骤和奖励进度 |
| 用户完成部分任务 | 提醒还差几步 |
| 用户卡在钱包或社群任务 | 给操作指引 |
| 用户接近领取资格 | 强化完成激励 |
| 用户重复领取 | 触发风控和复核 |

边界：

不能绕过钱包、账号、任务完成校验。

不能临时扩大空投承诺。

奖励表达要避免误导。

### 29.3 跑酷模板

| 场景 | 动态运营动作 |
|---|---|
| 用户前 5 秒失败 | 降低速度或减少障碍 |
| 用户连续失败 | 提供复活或提示 |
| 用户表现好 | 提高节奏或解锁高分挑战 |
| 用户获得高分 | 展示成绩分享卡 |
| 用户完成挑战 | 展示 CTA 或复玩入口 |

边界：

不能改变核心玩法。

不能让难度变化破坏公平排名。

### 29.4 塔防模板

| 场景 | 动态运营动作 |
|---|---|
| 用户资源不足 | 给升级建议 |
| 用户连续漏怪 | 降低下一波强度 |
| 用户稳定通关 | 增加挑战或展示成就 |
| 用户完成波次 | 引导分享或 CTA |
| 用户即将失败 | 给一次提示或补给 |

边界：

不能临时改变胜利条件。

不能让奖励获取条件不一致。

### 29.5 射击模板

| 场景 | 动态运营动作 |
|---|---|
| 用户命中率低 | 降低目标速度或增加命中容忍 |
| 用户命中率高 | 增加目标数量或速度 |
| 用户疑似连点脚本 | 触发风控 |
| 用户完成挑战 | 展示分数和分享卡 |
| 用户接近流失 | 简化下一轮 |

边界：

不能让自动点击获得优势。

不能破坏奖励判断。

### 29.6 画线模板

| 场景 | 动态运营动作 |
|---|---|
| 用户多次画错 | 显示关键节点提示 |
| 用户停留过久 | 高亮起点或终点 |
| 用户快速完成 | 解锁更难路径 |
| 用户完成关卡 | 展示结果和分享 |
| 用户低完成 | 降低路径复杂度 |

边界：

不能直接替用户完成核心操作。

不能让提示替代玩法。

### 29.7 模拟经营模板

| 场景 | 动态运营动作 |
|---|---|
| 用户资源不足 | 推荐资源分配 |
| 用户不知道下一步 | 展示经营目标 |
| 用户达成里程碑 | 展示成就和奖励 |
| 用户回访 | 展示新任务或收益进度 |
| 用户高参与 | 引导社群、排行榜或长期任务 |

边界：

不能承诺真实收益。

不能把经营结果包装成投资回报。

## 30. Runtime Agent 的职责

Runtime Agent 负责在线决策，但不是无限自治。

| 职责 | 说明 |
|---|---|
| 读取实时状态 | 用户行为、进度、分群、渠道、风险 |
| 匹配策略 | 从 `agent_policy` 中找到可用策略 |
| 生成决策 | 输出 `runtime_decision` |
| 校验边界 | 确保不突破 `game_rules` 和合规限制 |
| 应用动作 | 触发提示、难度、奖励、CTA、分享、风控 |
| 记录日志 | 写入 `agent_decision_applied` |
| 观察结果 | 判断是否改善关键指标 |
| 触发回退 | 异常时回到默认策略 |

Runtime Agent 不负责：

| 不负责事项 | 原因 |
|---|---|
| 临时改活动主目标 | 这是营销目标层决定 |
| 临时生成未审核奖励 | 有合规和资金风险 |
| 绕过平台审核 | 发布内容必须先审核 |
| 改变核心玩法模板 | 会破坏版本一致性 |
| 替代风控系统 | 风控是底线规则 |
| 私自采集敏感数据 | 违反数据权限边界 |

## 31. 前端 Runtime 的职责

H5 前端需要支持动态运营。

否则 Runtime Agent 即使生成决策，也无法落地。

| 前端能力 | 说明 |
|---|---|
| 动态配置读取 | 拉取当前版本的 `runtime_config` |
| 事件埋点 | 上报用户行为和关键节点 |
| 状态同步 | 维护当前关卡、分数、失败次数等 |
| 决策应用 | 根据 `runtime_decision` 改变提示、难度、CTA |
| 兜底体验 | 决策失败时使用默认配置 |
| 延迟控制 | 避免动态请求影响游戏体验 |
| 频率控制 | 避免重复弹窗和过度提示 |
| 可观测性 | 上报应用成功、失败、耗时 |

## 32. 服务端 Runtime 的职责

服务端负责更稳定和更敏感的运行时逻辑。

| 服务端能力 | 说明 |
|---|---|
| 会话管理 | 维护 `session_id`、用户状态和渠道归因 |
| 策略服务 | 根据 `agent_policy` 返回可执行策略 |
| 决策服务 | 生成和记录 `runtime_decision` |
| 风控服务 | 检查异常行为和奖励滥用 |
| 奖励服务 | 控制奖励展示、确认和发放 |
| 实验服务 | 管理 A/B 测试和灰度 |
| 配置服务 | 下发版本和运行时配置 |
| 日志服务 | 写入事件、决策和结果 |
| 看板服务 | 汇总实时数据 |

## 33. 运行时数据看板

运行时动态运营必须有看板。

否则平台只能发布，不能运营。

| 看板模块 | 指标 |
|---|---|
| 实时流量 | 曝光、进入、开始、在线人数 |
| 游戏漏斗 | 开始率、完成率、关卡流失 |
| Agent 决策 | 决策次数、应用成功率、策略命中率 |
| 分群表现 | 不同用户分群的完成率和转化率 |
| 渠道表现 | 不同连接器和渠道的点击、完成、转化 |
| CTA 表现 | CTA 展示、点击、转化 |
| 分享表现 | 分享点击、分享转化、二次访问 |
| 奖励表现 | 奖励展示、触发、领取、异常 |
| 风控表现 | 异常率、拦截数、复核数 |
| 留存表现 | 回访、复玩、二次转化 |

## 34. 关键指标

运行时动态运营要围绕具体指标优化。

| 指标 | 含义 | 可能对应策略 |
|---|---|---|
| Start Rate | 进入后点击开始比例 | 首屏文案、开始按钮、低门槛引导 |
| Completion Rate | 完成游戏或任务比例 | 动态难度、提示、任务简化 |
| Drop-off Rate | 关键节点流失比例 | 卡点提示、路径缩短 |
| Share Rate | 分享点击比例 | 分享卡、成绩展示、排行榜 |
| CTA Rate | CTA 点击比例 | CTA 时机、文案、目标 |
| Conversion Rate | 目标转化比例 | 高意向分群、CTA 路径 |
| Reward Claim Rate | 奖励领取比例 | 奖励提示、进度展示 |
| Risk Rate | 异常行为比例 | 风控阈值、验证、限频 |
| Retention | 回访和复玩 | 连续任务、回访提示 |
| Agent Uplift | Agent 决策带来的增量 | A/B 测试、对照组 |

## 35. Agent 决策效果归因

要证明运行时动态运营有效，需要对照。

| 方法 | 说明 |
|---|---|
| A/B 测试 | 部分用户启用策略，部分用户使用默认 |
| 策略前后对比 | 同一渠道上线前后指标对比 |
| 分群对比 | 同一策略对不同分群的影响 |
| 渠道对比 | 同一策略在不同渠道的效果 |
| 决策链路追踪 | 从决策应用到后续事件完整追踪 |
| 失败样本分析 | 查看策略没有改善的用户路径 |

不建议只看总转化率。

因为总转化率可能由渠道、KOL、奖励、玩法、页面加载速度等因素共同影响。

必须把 Agent 决策单独记录，才能评估 Agentic 的真实价值。

## 36. 运行时实验机制

运行时动态运营可以承载轻量实验。

| 实验对象 | 示例 |
|---|---|
| CTA 文案 | 加入社群 vs 领取资格 |
| CTA 时机 | 结果页展示 vs 分享后展示 |
| 提示强度 | 弱提示 vs 强提示 |
| 难度策略 | 固定难度 vs 动态难度 |
| 分享卡 | 成绩导向 vs 挑战导向 |
| 奖励提示 | 进度条 vs 结果页强调 |
| 新手引导 | 简短引导 vs 分步引导 |

实验必须具备：

| 要素 | 说明 |
|---|---|
| 实验 ID | 方便追踪 |
| 分组规则 | 用户如何进入实验组 |
| 生效范围 | 哪个 KOL、渠道、版本、模板 |
| 成功指标 | 要提升哪个指标 |
| 停止条件 | 何时结束实验 |
| 风险阈值 | 指标变差时自动停止 |
| 版本记录 | 实验配置必须可追溯 |

## 37. 回退与降级机制

运行时动态运营必须支持回退。

因为线上环境会出现策略错误、接口失败、延迟过高、风控误判或渠道异常。

| 异常 | 回退动作 |
|---|---|
| 决策接口超时 | 使用默认配置 |
| 策略边界失败 | 不应用决策 |
| 风控冲突 | 风控优先 |
| 实验配置错误 | 关闭实验组 |
| 奖励库存异常 | 暂停奖励发放 |
| CTA 链接异常 | 隐藏 CTA 或切默认 CTA |
| 前端应用失败 | 记录失败并继续游戏 |
| 渠道异常刷量 | 暂停该渠道策略 |

回退原则：

1. 不影响用户完成基础游戏。
2. 不展示未审核内容。
3. 不突破奖励和合规边界。
4. 不让异常策略继续扩大影响。
5. 所有回退都要记录。

## 38. 运行时权限控制

不同角色能调整的内容不同。

| 角色 | 可操作内容 | 不可操作内容 |
|---|---|---|
| KOL | 查看效果、开关部分推荐、申请调整 CTA | 直接改风控、绕过审核 |
| 平台运营 | 调整策略开关、渠道权重、实验配置 | 绕过合规规则 |
| 风控运营 | 调整风控阈值、处理复核 | 改营销目标 |
| 审核人员 | 审核动态文案和 CTA 池 | 操作投放预算 |
| 系统管理员 | 配置全局策略和权限 | 直接篡改事件结果 |
| Runtime Agent | 生成运行时决策 | 越权修改核心规则 |

MVP 阶段，KOL 的运行时权限应该偏保守。

优先让 KOL 看懂效果和提出调整，而不是直接操作复杂策略。

## 39. 运行时合规要求

运行时动态运营的合规风险比发布前更隐蔽。

因为风险内容可能不是静态页面里出现，而是动态决策后出现。

| 合规点 | 要求 |
|---|---|
| 文案来源 | 动态文案必须来自已审核文案池 |
| 奖励表达 | 不能夸大奖励价值或承诺收益 |
| 投资相关 | 不生成投资建议、收益预测、确定性承诺 |
| 数据采集 | 不采集未授权敏感数据 |
| 用户分群 | 不使用敏感属性进行不当差别待遇 |
| CTA 链接 | 只能使用审核通过的目标 |
| 平台规则 | 遵守 X、Telegram、Discord、广告平台规则 |
| 风控记录 | 奖励、资格、拦截要可审计 |
| 决策可解释 | 重要决策要能说明原因 |

## 40. 运行时内容来源

Runtime Agent 不应该临时自由生成所有内容。

更稳妥的方式是从已审核内容池中选择、组合和排序。

| 内容类型 | 推荐来源 |
|---|---|
| 提示文案 | 已审核提示文案池 |
| CTA 文案 | 已审核 CTA 文案池 |
| 分享文案 | 已审核分享文案池 |
| 奖励提示 | 已审核奖励说明 |
| 风控提示 | 平台统一风控文案 |
| KOL 语气 | `kol_context` 中的语气规则 |
| 视觉素材 | 已审核素材包 |
| 任务内容 | `game_rules` 允许的任务池 |

这样可以兼顾动态性和合规性。

## 41. 运行时版本管理

运行时动态运营必须和版本绑定。

否则后续无法复盘。

| 版本对象 | 说明 |
|---|---|
| `playable_version` | H5 代码和静态配置版本 |
| `runtime_config_version` | 运行时配置版本 |
| `agent_policy_version` | Agent 策略版本 |
| `game_rules_version` | 游戏规则版本 |
| `content_pool_version` | 可选动态文案和素材版本 |
| `experiment_version` | 实验配置版本 |
| `risk_policy_version` | 风控策略版本 |

每条 `runtime_decision` 都应该记录它使用的版本。

这样当指标波动时，才能知道到底是哪一层配置变化造成的。

## 42. 运行时状态机

MVP 可以把运行时状态简化为几个核心状态。

| 状态 | 说明 | 可触发动作 |
|---|---|---|
| `loaded` | H5 已加载 | 曝光记录、渠道归因 |
| `started` | 用户已开始 | 新手引导、初始难度 |
| `in_progress` | 用户正在进行 | 提示、难度、任务推荐 |
| `stuck` | 用户卡住 | 强提示、降难度 |
| `completed` | 用户完成 | 奖励、分享、CTA |
| `shared` | 用户分享 | 二次传播追踪 |
| `converted` | 用户完成目标 | 转化记录、后续留存 |
| `dropped` | 用户流失 | 流失诊断 |
| `risk_flagged` | 用户有风险 | 验证、限频、延迟发奖 |
| `returned` | 用户回访 | 进度恢复、下一任务 |

状态机的作用是让 Runtime Agent 有稳定的判断依据。

## 43. 冷启动阶段的运行时运营

冷启动阶段的目标不是做复杂自动化，而是验证基础链路。

核心问题：

KOL 愿不愿意发，粉丝愿不愿意点，用户能不能完成，结果能不能分享，数据能不能证明有效。

| 优先级 | 能力 | 原因 |
|---|---|---|
| P0 | 曝光、开始、完成、分享、CTA 事件 | 没有数据就不能运营 |
| P0 | 动态提示 | 直接影响完成率 |
| P0 | 动态 CTA 时机 | 直接影响转化 |
| P0 | 基础风控 | 防止奖励被刷 |
| P0 | KOL 看板摘要 | 降低 KOL 信任成本 |
| P1 | 动态难度 | 提升完成率和体验 |
| P1 | 分享卡动态化 | 提升传播 |
| P1 | 分群策略 | 提升精细运营 |
| P2 | 多轮实验 | 需要足够流量后再做 |
| P2 | 自动策略修正 | 需要稳定数据后再做 |

## 44. 稳定阶段的运行时运营

稳定阶段的目标是提高复玩、复投、长期转化和 KOL 资产价值。

| 能力 | 说明 |
|---|---|
| 持续分群 | 形成用户参与画像 |
| 跨活动 Memory | 记录 KOL、模板、渠道、用户偏好 |
| 自动策略优化 | 根据历史表现调整策略 |
| 多模板推荐 | 根据用户行为推荐下一类 Playable |
| 长期留存任务 | 连续挑战、积分成长、社群任务 |
| KOL 资产沉淀 | 粉丝排行榜、专属房间、复用素材 |
| 渠道质量评分 | 判断哪些渠道值得继续投入 |
| 预算优化 | 付费投放时优化投入产出 |

## 45. MVP 建议落地范围

MVP 不建议一开始做过重的实时智能系统。

推荐先实现 P0 闭环。

### 45.1 P0 必须实现

| 能力 | 说明 |
|---|---|
| 基础事件埋点 | 覆盖曝光、开始、完成、分享、CTA、转化、流失 |
| Agent 决策日志 | 记录 `agent_decision_applied` |
| 简单用户分群 | 新用户、低完成、高意向、风险用户 |
| 动态提示 | 根据失败和停留时间触发 |
| 动态 CTA | 根据完成状态和高意向触发 |
| 基础风控 | 重复领取、高频点击、异常完成 |
| 默认回退 | 决策失败时使用静态体验 |
| KOL 简版看板 | 展示关键漏斗和 Agent 摘要 |

### 45.2 P1 可增强

| 能力 | 说明 |
|---|---|
| 动态难度 | 不同模板支持不同难度参数 |
| 动态分享卡 | 根据成绩和 KOL 语气生成 |
| 渠道策略 | 不同渠道使用不同 CTA 和提示节奏 |
| A/B 实验 | 验证策略是否有效 |
| 奖励节奏 | 控制奖励展示和领取体验 |
| 回访识别 | 支持轻量留存 |

### 45.3 P2 再考虑

| 能力 | 说明 |
|---|---|
| 自动策略学习 | 系统根据历史数据自动调整策略 |
| 多活动 Memory | 跨活动沉淀 KOL 和用户偏好 |
| 高级推荐 | 推荐下一模板、下一任务、下一活动 |
| 预算联动 | 与广告投放预算实时联动 |
| 多 Agent 协作 | Runtime Agent、Diagnosis Agent、Risk Agent 协同 |

## 46. 不建议 MVP 阶段做什么

| 不建议事项 | 原因 |
|---|---|
| 让 Agent 自由生成线上文案 | 合规风险高 |
| 实时改变奖励性质 | 风险过高，难以审核 |
| 复杂强化学习 | 数据量不足，解释困难 |
| 过度个性化 | 容易造成体验不一致和合规问题 |
| KOL 直接改风控 | 容易被滥用 |
| 没有日志就做动态策略 | 无法证明效果 |
| 没有回退就上线 Runtime Agent | 线上风险不可控 |
| 把所有渠道混合分析 | 无法判断渠道质量 |
| 只看转化不看流失 | 容易误判策略有效性 |

## 47. 运行时动态运营和 KOL 关系

KOL 是运营资产，不只是发布者。

运行时动态运营要帮助 KOL 看到：

| KOL 关心的问题 | 系统回答 |
|---|---|
| 我的粉丝有没有玩 | 曝光、开始、完成数据 |
| 粉丝卡在哪里 | 流失节点和失败节点 |
| 我的内容有没有带来转化 | CTA 和转化数据 |
| 哪个渠道效果更好 | 渠道对比 |
| Agent 做了什么 | 动态提示、CTA、风控摘要 |
| 下一步怎么优化 | 换文案、换 CTA、换奖励提示、复投建议 |

KOL 不应该被迫理解底层策略字段。

但 KOL 应该拥有足够透明度，相信平台不是黑箱。

## 48. 运行时动态运营和平台运营关系

平台运营负责治理 Runtime Agent。

| 平台运营职责 | 说明 |
|---|---|
| 设定默认策略 | 不同模板的基础 Runtime 策略 |
| 配置动态开关 | 是否启用提示、难度、CTA、分享、风控 |
| 监控异常 | 指标异常、渠道异常、风控异常 |
| 审核内容池 | 确保动态内容可用且合规 |
| 管理实验 | 设置实验范围和停止条件 |
| 处理回退 | 策略异常时快速恢复 |
| 输出复盘 | 把结果沉淀到模板和 KOL Memory |

## 49. 运行时动态运营和数据反馈关系

运行时动态运营产生数据。

数据反馈解释数据。

| Runtime 产生 | 数据反馈使用 |
|---|---|
| `agent_decision_applied` | 判断 Agent 决策是否有效 |
| `runtime_decision` | 分析策略命中和边界情况 |
| 用户事件 | 还原完整用户路径 |
| 分群结果 | 比较不同人群表现 |
| 渠道归因 | 判断渠道质量 |
| 风控事件 | 评估奖励风险 |
| 回退事件 | 发现策略稳定性问题 |
| 实验分组 | 计算策略增量 |

反馈结果可以进入：

| 下游 | 作用 |
|---|---|
| `performance_report` | 给 KOL 和平台看结果 |
| `diagnosis_result` | 解释为什么好或不好 |
| `kol_memory` | 沉淀 KOL 的历史偏好和效果 |
| `template_memory` | 优化模板默认策略 |
| `policy_patch_suggestion` | 建议下一轮修改 `agent_policy` |
| `generation_brief` | 影响下一次创作 Brief |

## 50. 典型运行时场景

### 50.1 用户连续失败

| 项 | 内容 |
|---|---|
| 触发事件 | 连续两次失败 |
| 分群 | 低完成用户 |
| 策略 | 降低难度或给提示 |
| 边界 | 难度只能在 1-3 范围内 |
| 决策 | 下一关降低障碍密度并显示提示 |
| 记录 | `agent_decision_applied` |
| 观察 | 是否继续游戏、是否完成 |

### 50.2 用户完成游戏但未点击 CTA

| 项 | 内容 |
|---|---|
| 触发事件 | `step_complete` 或完成结果页 |
| 分群 | 已完成但未转化用户 |
| 策略 | 展示更清晰 CTA |
| 边界 | CTA 必须来自已审核目标 |
| 决策 | 在结果页展示加入社群按钮 |
| 记录 | `cta_view`、`cta_click` |
| 观察 | CTA 点击率和转化率 |

### 50.3 用户点击分享

| 项 | 内容 |
|---|---|
| 触发事件 | `share_click` |
| 分群 | 分享倾向用户 |
| 策略 | 动态分享卡 |
| 边界 | 分享文案来自审核池 |
| 决策 | 根据成绩生成挑战型分享卡 |
| 记录 | 分享事件和分享来源 |
| 观察 | 二次访问和分享转化 |

### 50.4 用户疑似刷奖励

| 项 | 内容 |
|---|---|
| 触发事件 | 高频点击、重复领取或异常完成 |
| 分群 | 风险用户 |
| 策略 | 风控优先 |
| 边界 | 不允许绕过验证 |
| 决策 | 延迟发奖并进入复核 |
| 记录 | `risk_triggered`、`agent_decision_applied` |
| 观察 | 是否降低异常领取 |

## 51. 运行时动态运营的产研拆分

| 模块 | 主要职责 |
|---|---|

| Policy Service | 管理 `agent_policy` 和版本 |
| Rules Service | 管理 `game_rules` 和边界 |
| Risk Service | 风控识别和处理 |
| Reward Service | 奖励展示、资格确认、发放控制 |

## 53. 运行时动态运营验收标准

上线前要能回答以下问题。

| 验收项 | 标准 |
|---|---|
| 决策可触发 | 用户事件能触发 Runtime 决策 |
| 决策可应用 | 前端能正确应用提示、CTA、难度等动作 |
| 决策可追踪 | `agent_decision_applied` 能记录 |
| 决策可解释 | 能说明为什么做出该决策 |
| 决策不越界 | 通过 `game_rules` 和 `runtime_boundaries` 校验 |
| 异常可回退 | 决策失败不影响基础体验 |
| 风控优先 | 风险用户不会绕过验证 |
| 数据可看 | KOL 和平台能看到关键指标 |
| 效果可评估 | 能比较有无 Agent 决策的差异 |
| 版本可追溯 | 指标变化能定位到配置版本 |

## 54. 常见错误

| 错误 | 后果 |
|---|---|
| 把运行时动态运营理解成改页面皮肤 | 忽略真正影响转化的策略层 |
| 没有 `agent_decision_applied` | 无法证明 Agent 有效 |
| 动态策略不受边界控制 | 合规和奖励风险高 |
| 只看总转化率 | 无法判断是哪种策略有效 |
| 不区分渠道 | 容易误判投放质量 |
| 不做回退 | 策略错误会直接影响线上用户 |
| 让 KOL 看过多底层字段 | 增加使用门槛 |
| 让 Agent 自由生成线上内容 | 审核和合规不可控 |
| 风控晚于奖励 | 容易被刷 |
| 不记录版本 | 后续无法复盘 |

## 55. 推荐产品表达

面向 KOL 时，不建议说：

平台会在运行时生成 `runtime_decision` 并基于 `agent_policy` 进行策略匹配。

建议说：

作品上线后，系统会根据粉丝的真实互动情况，自动优化提示、难度、奖励展示和转化引导，并把效果展示在看板里。

面向平台内部时，可以说：

运行时动态运营是 Airvana Agentic Playable 的在线决策层，负责在 `game_rules` 和 `runtime_boundaries` 内，把 `agent_policy` 转化为可追踪的 `runtime_decision`，并通过 `agent_decision_applied` 事件进入数据反馈闭环。

## 56. 与前面各环节的依赖关系

| 前置环节 | 对运行时动态运营的影响 |
|---|---|
| KOL 身份识别 | 决定 KOL 语气、粉丝分群、渠道偏好 |
| 营销目标选择 | 决定优化指标和 CTA 目标 |
| 模板推荐 | 决定可支持的动态玩法槽位 |
| 关键变量填写 | 决定奖励、难度、CTA、任务等基础参数 |
| 创作 Brief | 决定内容方向和用户动机 |
| 内容生成 | 提供动态文案和素材池 |
| 游戏规则生成 | 定义运行时不可突破的边界 |
| Agent 策略生成 | 提供运行时可执行策略 |
| 约束与合规验证 | 确定哪些内容能在线使用 |
| H5 组装 | 提供 Runtime SDK 和动态槽位 |
| 模拟测试 | 验证策略是否可触发、可回退 |
| KOL 二次编辑 | 修改部分运行时策略输入 |
| 发布投放 | 提供渠道、链接和投放上下文 |

## 57. 最终结论

运行时动态运营是 Agentic Playable 从一次性互动素材变成持续增长系统的关键环节。

它的本质不是“上线后自动改东西”，而是：

在已审核、已发布、可追踪、可回滚的边界内，根据真实用户行为，把前面生成的 `agent_policy` 转化为实时运营动作。

对 Airvana 来说，MVP 阶段应优先做好五件事：

1. 事件埋点完整。
2. `runtime_decision` 可生成。
3. `agent_decision_applied` 可记录。
4. 动态提示、CTA、风控、回退可用。
5. KOL 和平台都能看懂运行时运营效果。

只要这五件事闭环，Airvana 的 Agentic Playable 就不只是一个自动生成 H5 的工具，而是一个可以被数据持续驱动和运营优化的营销系统。
