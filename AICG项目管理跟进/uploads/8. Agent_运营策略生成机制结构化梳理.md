# Agent 运营策略生成机制结构化梳理

## 1. 核心定义

Agent 运营策略生成，是指在 `game_rules` 已经确定之后，系统根据营销目标、用户分群、游戏规则、内容资产、KOL 画像、风险信号和历史数据，生成一套 Runtime Agent 可以在运行中执行的动态运营策略。

它不是基础游戏规则，而是在固定规则边界内优化用户体验和营销结果的策略层。

| 不是 | 是 |
|---|---|
| 不是决定游戏怎么玩的基础规则 | 是在规则允许范围内动态调整体验 |
| 不是随意改奖励、CTA 或主目标 | 是受 `game_rules` 和合规边界约束的运营策略 |
| 不是最终页面内容 | 是决定什么用户、什么状态下看到什么提示、奖励节奏和 CTA |
| 不是一个聊天机器人 | 是基于事件、分群、目标和风险做运营决策的系统 |

一句话：

**Agent 运营策略生成 = 在固定 `game_rules` 之上，为 Runtime Agent 生成可控的动态运营方案，让 Playable 能根据用户状态自动优化完成率、分享率、CTA 和转化。**

## 2. 在完整工作流中的位置

| 阶段 | 输入 | 输出 |
|---|---|---|
| 创作 Brief 生成 | `kol_context`、`campaign_goal`、`template_config` | `generation_brief` |
| 内容生成 | `generation_brief`、`template_schema`、资产 | `content_assets` |
| 游戏规则生成 | `generation_brief`、`template_config`、`content_assets` | `game_rules` |
| Agent 运营策略生成 | `campaign_goal`、`game_rules`、`kol_context`、风险和历史数据 | `agent_policy` |
| 约束验证 | `content_assets`、`game_rules`、`agent_policy` | `validation_report` |
| H5 组装 | 内容、规则、策略、模板代码 | `playable_version` |
| 运行时执行 | 用户行为、事件、分群、策略 | `runtime_decision` |
| 数据复盘 | 事件、策略、结果 | 诊断报告、策略记忆、模板更新 |

Agent 运营策略生成发生在规则生成之后，因为 Agent 必须知道边界在哪里，才能决定能动态调整什么。

## 3. 和游戏规则的区别

| 问题 | `game_rules` | `agent_policy` |
|---|---|---|
| 用户怎么玩 | 定义基础玩法 | 不改变基础玩法 |
| 有几道题 | 固定范围，例如 3 到 5 题 | 在范围内为不同用户选择 |
| 奖励是什么 | 规定只能是积分、徽章、资格等 | 调整奖励提示和触发节奏 |
| CTA 在哪里出现 | 规定允许出现的状态 | 根据用户状态选择具体时机和文案 |
| 失败怎么处理 | 定义失败、重试、退出规则 | 连续失败时给提示或降难度 |
| 风控怎么触发 | 定义异常行为规则 | 根据风险提高验证强度 |

核心原则：

1. Agent 不能改主目标。
2. Agent 不能改奖励性质。
3. Agent 不能突破合规边界。
4. Agent 不能改变 `game_rules` 不允许的状态流转。
5. Agent 每次决策都必须记录为可复盘事件。

## 4. 主要输入

| 输入对象 | 关键字段 | 用途 |
|---|---|---|
| `campaign_goal` | 主目标、次目标、CTA、核心指标 | 决定策略优化方向 |
| `game_rules` | 状态机、胜负、奖励、CTA、反作弊、边界 | 决定 Agent 可调范围 |
| `content_assets` | 文案、任务、反馈、分享卡、CTA 文案 | 决定可替换或强化的内容 |
| `kol_context` | KOL 语气、粉丝画像、历史效果、风险敏感度 | 决定个性化策略 |
| `template_schema` | 可动态字段、运行时槽位、模板能力 | 决定策略是否能落地 |
| `risk_profile` | 异常流量、刷量、钱包、设备、奖励风险 | 决定风控策略 |
| `performance_history` | 开始率、完成率、分享率、CTA、转化 | 决定策略默认值 |
| `tracking_requirements` | 事件、指标、归因字段 | 决定策略如何被评估 |

## 5. 核心输出

统一输出对象是 `agent_policy`。

| 输出模块 | 说明 |
|---|---|
| `segmentation_policy` | 用户分群规则 |
| `difficulty_policy` | 难度调整策略 |
| `hint_policy` | 提示和引导策略 |
| `reward_policy` | 奖励节奏和奖励提示策略 |
| `cta_policy` | CTA 展示时机、文案和目标策略 |
| `share_policy` | 分享、邀请、排行榜强化策略 |
| `risk_policy` | 风控、反作弊和异常路径策略 |
| `retention_policy` | 复玩、回访、下一轮任务策略 |
| `personalization_policy` | KOL 语气、用户状态和渠道个性化策略 |
| `experiment_policy` | A/B 测试和策略实验规则 |
| `runtime_boundaries` | Agent 可调范围和禁止事项 |
| `decision_logging` | 每次 Runtime 决策要记录什么 |
| `fallback_policy` | 策略失败或数据不足时如何降级 |

## 6. 策略类型拆解

### 6.1 用户分群策略 `segmentation_policy`

用户分群是所有动态运营策略的基础。

| 分群维度 | 示例 | 用途 |
|---|---|---|
| 来源渠道 | KOL 链接、X、Telegram、Discord、广告 | 决定 CTA 和分享策略 |
| 用户熟悉度 | 新手、普通用户、专业用户 | 决定难度和解释程度 |
| 参与进度 | 未开始、进行中、接近完成、已完成 | 决定提示和奖励节奏 |
| 行为意图 | 高分享、高转化、高学习、低耐心 | 决定路径推荐 |
| 风险等级 | 正常、可疑、异常、高风险 | 决定验证强度 |
| 历史关系 | 新用户、回访用户、老粉丝、已转化用户 | 决定复投和留存 |

MVP 分群建议先做 5 类：

| 分群 | 判断依据 | 策略 |
|---|---|---|
| 新手用户 | 首次进入、低 Web3 熟悉度 | 降低难度，增加解释 |
| 高意向用户 | 完成度高、停留长、点击 CTA | 提前展示转化路径 |
| 分享型用户 | 点击分享、邀请来源强 | 强化分享卡和排行榜 |
| 流失风险用户 | 停留过久、失败多、准备退出 | 给提示、降难度、强调奖励 |
| 异常用户 | 高频点击、重复钱包、异常设备 | 增加强校验或限制奖励 |

### 6.2 难度策略 `difficulty_policy`

难度策略用于提升完成率和体验质量，但必须在 `game_rules` 允许范围内。

| 模板 | 可调难度 |
|---|---|
| 竞猜 | 题目难度、提示强度、选项干扰程度 |
| 空投任务 | 任务顺序、任务数量提示、验证强度 |
| 跑酷 | 速度、障碍密度、收集物分布 |
| 塔防 | 波次强度、敌人数量、初始资源、失败补救 |
| 射击 | 目标速度、目标密度、命中容错 |
| 画线 | 障碍布局、提示节点、路径评分 |
| 模拟经营 | 资源产出、事件难度、任务目标 |

策略示例：

| 触发条件 | 动作 |
|---|---|
| 用户连续答错 2 次 | 降低下一题难度 |
| 用户停留超过阈值 | 显示轻提示 |
| 用户快速通关 | 提高下一关挑战 |
| 用户撞障碍多次 | 降低障碍密度或给护盾 |
| 用户高分但未分享 | 展示更强结果卡 |

### 6.3 提示策略 `hint_policy`

提示策略用于减少流失，但不能让体验变成教程堆叠。

| 提示类型 | 示例 |
|---|---|
| 轻提示 | 还差一步即可解锁结果 |
| 教育提示 | 这个概念和项目核心功能有关 |
| 操作提示 | 向左滑动避开障碍 |
| 奖励提示 | 完成后可获得抽奖资格 |
| 风险提示 | 奖励以官方规则为准 |
| 继续提示 | 你已经完成 2/3 个任务 |

提示策略必须控制频率：

| 规则 | 说明 |
|---|---|
| 不要首屏堆提示 | 影响开始率 |
| 不要每一步都弹窗 | 打断体验 |
| 失败后提示优先 | 降低挫败 |
| 高风险内容提示必须保留 | 合规优先 |

### 6.4 奖励策略 `reward_policy`

奖励策略不是改变奖励本身，而是在规则允许范围内优化奖励节奏和提示。

| 可调整 | 不可调整 |
|---|---|
| 奖励提示出现时机 | 把积分改成真实 Token |
| 奖励进度展示方式 | 承诺必中或保证收益 |
| 完成前的激励文案 | 改变项目方设定的奖励规则 |
| 对低完成用户强调“还差一步” | 给异常用户绕过风控 |

策略示例：

| 用户状态 | 奖励策略 |
|---|---|
| 刚开始 | 轻提示奖励，不夸大 |
| 完成一半 | 展示进度和剩余任务 |
| 接近完成 | 强化完成后反馈 |
| 已完成 | 展示资格、积分或结果卡 |
| 异常风险 | 限制奖励触发或进入审核 |

### 6.5 CTA 策略 `cta_policy`

CTA 策略决定何时、给谁、用什么语气展示转化入口。

| CTA 类型 | 适合状态 |
|---|---|
| 加入社群 | 完成核心任务、结果页、高兴趣用户 |
| 注册 / 领取 | 达到奖励条件、完成任务链 |
| 查看项目 | 完成教育内容后 |
| 分享给朋友 | 结果页、高分、成就达成 |
| 继续挑战 | 低转化但高参与用户 |

CTA 策略必须和 `campaign_goal` 一致：

| 主目标 | CTA 策略 |
|---|---|
| 项目教育 | 先了解，再加入或查看 |
| 社群增长 | 完成关键互动后入群 |
| 转化领取 | 达到条件后领取或注册 |
| 裂变传播 | 结果页优先分享 |
| 留存复活 | 完成后推荐下一轮任务 |

### 6.6 分享策略 `share_policy`

分享策略用于提升裂变和 KOL 传播意愿。

| 触发条件 | 动作 |
|---|---|
| 用户高分 | 展示成绩型分享卡 |
| 用户完成任务 | 展示资格型分享卡 |
| 用户低分但完成 | 展示挑战好友型分享卡 |
| 用户来自邀请 | 展示回邀请链路 |
| KOL 粉丝榜存在 | 展示排行榜名次 |

分享策略要避免夸大奖励。分享卡可以强调成绩、身份、挑战、KOL 专属活动，但不能暗示收益保证。

### 6.7 风控策略 `risk_policy`

风控策略负责在运行中识别异常行为，并调用 `game_rules` 里的反作弊边界。

| 风险信号 | 策略 |
|---|---|
| 高频点击 | 降低奖励权重或进入验证 |
| 重复钱包 | 限制重复领取 |
| 重复设备 | 标记风险或要求登录 |
| 异常完成速度 | 延迟奖励或人工审核 |
| 异常分享 | 不计有效邀请 |
| 黑名单来源 | 阻断或只允许体验不发奖励 |

风控策略要分层：

| 等级 | 处理 |
|---|---|
| 低风险 | 正常体验 |
| 中风险 | 增加轻验证 |
| 高风险 | 限制奖励，记录异常 |
| 严重风险 | 阻断或人工审核 |

### 6.8 留存和复投策略 `retention_policy`

留存策略负责活动完成后的下一步。

| 用户状态 | 策略 |
|---|---|
| 完成但未 CTA | 提供轻量下一步 |
| 加入社群 | 推荐社群任务或排行榜 |
| 分享成功 | 推荐邀请奖励或下一轮活动 |
| 高分用户 | 推荐进阶挑战 |
| 低分用户 | 推荐新手教育任务 |
| 回访用户 | 展示上次进度和新奖励 |

### 6.9 实验策略 `experiment_policy`

实验策略用于测试不同运营策略的效果。

| 可实验对象 | 示例 |
|---|---|
| CTA 文案 | 加入社群 vs 查看活动进度 |
| CTA 时机 | 第 2 步后 vs 结果页 |
| 奖励提示 | 首屏提示 vs 完成前提示 |
| 难度策略 | 固定难度 vs 动态降难度 |
| 分享卡 | 成绩型 vs 资格型 |
| 提示频率 | 低频 vs 中频 |

MVP 不要做太多实验。先做少量高影响策略，保证可解释。

## 8. Runtime 决策流程

Agent 运营策略生成后，不是一次性写死，而是在运行时被 Runtime Agent 调用。

推荐流程：

1. 用户触发事件，例如开始、答题、失败、完成、分享、CTA 点击。
2. 系统读取当前状态、用户分群、渠道、进度和风险信号。
3. Runtime Agent 查询 `agent_policy`。
4. 系统检查 `runtime_boundaries` 和 `game_rules`。
5. 生成 `runtime_decision`。
6. 应用小范围策略，例如给提示、调难度、调整 CTA 文案。
7. 记录 `agent_decision_applied`。
8. 后续根据结果判断策略是否有效。

## 9. `runtime_decision` 数据结构

每次 Agent 决策都要记录。

| 字段 | 说明 |
|---|---|
| `decision_id` | 决策 ID |
| `policy_id` | 来源策略 |
| `playable_version_id` | 当前版本 |
| `user_segment` | 用户分群 |
| `trigger_event` | 触发事件 |
| `current_state` | 当前状态 |
| `decision_type` | 难度、提示、奖励、CTA、风控等 |
| `decision_action` | 实际采取的动作 |
| `reason` | 决策原因 |
| `expected_metric` | 预期改善指标 |
| `boundary_check` | 是否通过边界校验 |
| `applied_at` | 应用时间 |
| `result_event` | 后续结果事件 |

没有决策日志，就无法判断 Agent 是否真的改善了结果。

## 10. 不同模板的 Agent 策略重点

### 10.1 竞猜 / 预测模板

| 策略 | 重点 |
|---|---|
| 分群 | 新手、专业用户、高分用户、低分用户 |
| 难度 | 根据答题表现调下一题难度 |
| 提示 | 答错或停留过久时给解释提示 |
| 奖励 | 完成前强调积分或资格 |
| CTA | 高分用户加入高手讨论，低分用户加入学习社群 |
| 风控 | 异常高速答题、重复提交限制 |
| 数据 | 每题正确率、提示后完成率、CTA 点击 |

### 10.2 空投任务模板

| 策略 | 重点 |
|---|---|
| 分群 | 新用户、已入群用户、分享用户、异常用户 |
| 难度 | 任务顺序从低门槛到高价值 |
| 提示 | 显示还差几步完成 |
| 奖励 | 强调资格和进度，不承诺空投 |
| CTA | 完成关键任务后展示领取或入群 |
| 风控 | 重复钱包、重复设备、异常速度 |
| 数据 | 任务完成率、入群点击、分享率、异常率 |

### 10.3 跑酷模板

| 策略 | 重点 |
|---|---|
| 分群 | 新手、高手、低耐心用户、高分用户 |
| 难度 | 调整速度、障碍密度、收集物分布 |
| 提示 | 连续失败时提示操作或给保护 |
| 奖励 | 接近终点时强调结果和分享 |
| CTA | 完赛、高分或结果页展示 |
| 风控 | 异常分数、异常速度 |
| 数据 | 完赛率、失败点、收集率、分享率 |

### 10.4 塔防模板

| 策略 | 重点 |
|---|---|
| 分群 | 新手、策略型用户、失败用户、高参与用户 |
| 难度 | 调整波次强度、敌人数量、初始资源 |
| 提示 | 建塔建议、升级建议、失败补救 |
| 奖励 | Boss 后或胜利后强化成就感 |
| CTA | 胜利、升级完成或防守成功后展示 |
| 风控 | 异常分数、异常操作频率 |
| 数据 | 波次流失、塔选择、升级路径、胜利率 |

### 10.5 射击模板

| 策略 | 重点 |
|---|---|
| 分群 | 低命中用户、高命中用户、连击用户 |
| 难度 | 调整目标速度、目标密度、命中容错 |
| 提示 | 低命中时给操作提示 |
| 奖励 | 连击后强化奖励提示 |
| CTA | 高分、连击或通关后展示 |
| 风控 | 异常命中率、异常点击频率 |
| 数据 | 命中率、连击、完赛率、分享率 |

### 10.6 画线 / 路径规划模板

| 策略 | 重点 |
|---|---|
| 分群 | 新手、策略型用户、失败用户 |
| 难度 | 调整障碍布局、路径要求和提示节点 |
| 提示 | 失败后提示风险点或路径方向 |
| 奖励 | 完成路径后展示结果等级 |
| CTA | 完成路径后引导下一步 |
| 风控 | 异常路径提交和重复刷分 |
| 数据 | 路径完成率、失败点、提示使用 |

### 10.7 模拟经营模板

| 策略 | 重点 |
|---|---|
| 分群 | 新手、深度用户、回访用户、高价值用户 |
| 难度 | 调整资源产出、事件频率和任务目标 |
| 提示 | 推荐下一步经营动作 |
| 奖励 | 升级、达成目标、连续参与触发 |
| CTA | 阶段成果后引导继续、入群或注册 |
| 风控 | 异常资源增长、刷任务 |
| 数据 | 资源消耗、升级路径、复访率、长期参与 |

## 11. 策略边界 `runtime_boundaries`

`runtime_boundaries` 是 Agent 运营策略的安全阀。

| 边界 | 示例 |
|---|---|
| 目标边界 | 不允许改变主目标 |
| 规则边界 | 不允许跳过 `game_rules` 的完成条件 |
| 奖励边界 | 不允许把积分改成真实 Token |
| CTA 边界 | 不允许展示未授权 CTA |
| 合规边界 | 不允许生成收益承诺或投资建议 |
| 风控边界 | 不允许异常用户绕过验证 |
| 频率边界 | 提示、弹窗、CTA 不能过度打扰 |
| 数据边界 | 不能采集未授权敏感数据 |

边界失败时，Runtime Agent 必须降级到默认策略。

## 12. 策略校验

`agent_policy` 生成后必须校验。

| 校验项 | 说明 |
|---|---|
| 目标一致 | 策略是否服务 `campaign_goal` |
| 规则一致 | 是否在 `game_rules` 允许范围内 |
| CTA 合法 | CTA 是否与目标和规则匹配 |
| 奖励合规 | 是否改变奖励性质或夸大奖励 |
| 风控充分 | 高奖励、高风险活动是否有风控策略 |
| 数据可追踪 | 每个策略是否能记录决策和结果 |
| 频率可控 | 提示和 CTA 是否过度 |
| Builder 可执行 | 模板是否有对应动态槽位 |
| 可回滚 | 策略异常时能否回到默认 |

校验失败时，不应该进入上线，而是回到策略生成、规则生成或关键变量阶段修正。

## 13. 与数据复盘的关系

Agent 策略必须天然可复盘。

| 策略 | 复盘指标 |
|---|---|
| 难度策略 | 完成率、失败率、重试率 |
| 提示策略 | 提示后完成率、提示后流失率 |
| 奖励策略 | 完成率、奖励触发率、异常率 |
| CTA 策略 | CTA 展示率、点击率、转化率 |
| 分享策略 | 分享率、邀请点击、二跳用户 |
| 风控策略 | 异常拦截率、误伤率、奖励滥用率 |
| 分群策略 | 不同分群的漏斗表现 |

复盘问题：

1. 哪个策略提升了完成率？
2. 哪个策略提升了 CTA 但伤害了体验？
3. 哪个用户分群需要单独路径？
4. 哪个风控策略误伤正常用户？
5. 哪些策略应该沉淀为模板默认值？

## 14. KOL 和运营如何理解 Agent 策略

KOL 不需要看到完整 `agent_policy`，但需要看到可理解的摘要。

| 展示内容 | 示例 |
|---|---|
| 运行目标 | 系统会优先提升任务完成率和入群点击 |
| 动态调整项 | 难度、提示、奖励进度、CTA 文案 |
| 不会调整项 | 主目标、奖励性质、活动规则 |
| 风控说明 | 异常用户可能需要额外验证 |
| 数据看板 | 可查看 Agent 调整后的效果 |

这样可以提高 KOL 对自动运营的信任，避免觉得系统不可控。

## 15. KOL 二次编辑与策略 Patch

KOL 修改某些字段后，不一定要重生成全部策略。

| KOL 修改 | 影响 | 处理 |
|---|---|---|
| 改首屏文案 | 一般不影响策略 | 内容 Patch |
| 改分享文案 | 影响分享策略 | `share_policy_patch` |
| 改奖励表达 | 影响奖励和合规 | `reward_policy_patch` + 校验 |
| 改 CTA 文案 | 影响 CTA 策略 | `cta_policy_patch` |
| 改 CTA 目标 | 影响目标链路 | 回到 `campaign_goal` |
| 改任务数量 | 影响难度和提示 | `difficulty_policy_patch` |
| 改规则 | 影响边界 | 先更新 `game_rules`，再更新 `agent_policy` |

Patch 原则：

1. 只重算受影响策略。
2. 必须重新检查边界。
3. 必须生成新的 `policy_version`。
4. 必须保留旧策略用于回滚和复盘。

| 分群 | 新手、高手、低分用户、高意向用户 |
| 难度 | 前两题都错时降低第三题难度 |

## 18. 示例：空投任务 Agent 策略

| 策略模块 | 示例 |
|---|---|
| 分群 | 未入群、已入群、已分享、异常用户 |
| 任务提示 | 完成第 1 步后提示“还差 2 步解锁资格” |
| 奖励 | 接近完成时强调抽奖资格，不承诺必中 |

## 19. 不建议的做法

| 不建议事项 | 原因 |
|---|---|
| Agent 可以自由改规则 | 运行时不可控，风险高 |
| Agent 改变奖励性质 | 容易造成合规和信任风险 |
| Agent 不记录决策 | 无法复盘策略是否有效 |
| 所有用户同一策略 | 浪费 Agentic 的动态运营价值 |
| 没有风控策略 | 空投、奖励、排行榜容易被刷 |
| 没有回滚策略 | 策略异常会影响整个 campaign |
| 一开始做复杂强化学习 | MVP 阶段成本高且不可解释 |

## 20. 结论

Agent 运营策略生成是 Agentic Playable 从“可运行玩法”升级为“可自动运营系统”的关键阶段。

它要解决四件事：

| 问题 | 解决方式 |
|---|---|
| 不同用户怎么走不同路径 | 生成分群策略 |
| 用户卡住或流失怎么办 | 生成难度和提示策略 |
| 什么时候给奖励和 CTA | 生成奖励节奏和 CTA 策略 |
| 怎么防刷和复盘 | 生成风控策略和决策日志 |

MVP 阶段最重要的是：

1. `agent_policy` 必须结构化，不能只是“AI 自动优化”的口号。
2. Agent 只能在 `game_rules` 和合规边界内调整。
3. P0 先做分群、提示、难度、奖励、CTA 和风控。
4. 每次运行时决策必须记录为 `agent_decision_applied`。
5. 策略效果必须进入数据看板和 Diagnosis Agent 复盘。

这样，Agent 运营策略生成才是真正让 Playable 变成 Agentic Playable 的关键层。
