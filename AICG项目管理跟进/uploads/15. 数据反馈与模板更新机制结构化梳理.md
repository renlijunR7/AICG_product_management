# 数据反馈与模板更新机制结构化梳理

## 1. 核心定义

数据反馈与模板更新，是 Agentic Playable 从生成到运营链路的最后一个闭环环节。

它的核心不是“看报表”，而是把真实用户行为、渠道表现、Agent 决策效果、转化结果、风控结果和 KOL 编辑偏好，转化成下一次生成、模板推荐、默认配置、运营策略和 KOL 记忆的更新依据。

一句话理解：

数据反馈与模板更新 = 用真实运行数据，判断这次 Playable 为什么有效或无效，并把结论沉淀回模板、策略、内容池和 KOL Memory。

## 2. 为什么需要这个环节

如果没有数据反馈与模板更新，Agentic Playable 只是一次性生成 H5。

如果有这个环节，每一次活动都会变成可复用的经验资产。

| 没有数据反馈 | 有数据反馈与模板更新 |
|---|---|
| 每次活动都从零开始 | 下次生成继承有效经验 |
| 只知道总点击和总转化 | 知道哪一步流失、为什么流失 |
| Agent 动态策略无法证明价值 | 可以评估每个 `runtime_decision` 是否有效 |
| 模板默认值长期不变 | 模板会根据真实数据优化 |
| KOL 偏好无法沉淀 | KOL 下次创作更贴近历史成功风格 |
| 失败案例重复出现 | 负样本进入约束和模板规则 |
| 渠道表现无法比较 | 下次能优先推荐高质量渠道 |

这个环节决定 Airvana 是“生成工具”，还是“持续优化的营销系统”。

## 3. 在整体工作流中的位置

数据反馈与模板更新位于运行时动态运营之后，是第 15 步。

完整链路：

| 顺序 | 环节 | 关键产物 |
|---|---|---|
| 1 | KOL 身份识别 | `kol_context` |
| 2 | 营销目标选择 | `campaign_goal` |
| 3 | 模板推荐 | `template_schema` |
| 4 | 关键变量填写 | `template_config` |
| 5 | 创作 Brief 生成 | `generation_brief` |
| 6 | 文案、视觉、任务内容生成 | `content_assets` |
| 7 | 游戏规则生成 | `game_rules` |
| 8 | Agent 运营策略生成 | `agent_policy` |
| 9 | 约束与合规验证 | `validation_report` |
| 10 | H5 Playable 组装 | `playable_version` |
| 11 | 模拟测试 | `simulation_result` |
| 12 | KOL 二次编辑 | `config_patch` |
| 13 | 发布投放 | `publish_url` |
| 14 | 运行时动态运营 | `runtime_decision` |
| 15 | 数据反馈与模板更新 | `performance_report`、`diagnosis_result`、`template_update`、`kol_memory` |

它是闭环终点，也是下一轮生成的起点。

## 4. 和数据看板的区别

数据看板只是展示发生了什么。

数据反馈与模板更新要进一步判断为什么发生，以及下一次该怎么改。

| 对比项 | 数据看板 | 数据反馈与模板更新 |
|---|---|---|
| 核心作用 | 展示指标 | 诊断原因并沉淀改进 |
| 输出形式 | 图表、数字、漏斗 | 结论、建议、补丁、模板更新 |
| 使用对象 | KOL、运营、项目方 | Diagnosis Agent、模板系统、策略系统 |
| 关注点 | 曝光、点击、完成、转化 | 哪个变量、策略、渠道、模板导致结果 |
| 是否影响下一轮生成 | 不一定 | 必须影响 |
| 是否 Agentic | 仅展示不是核心 Agentic | 自动诊断和更新建议属于 Agentic |

数据看板回答：

发生了什么？

数据反馈与模板更新回答：

为什么发生？下次该怎么生成？

## 5. 和运行时动态运营的区别

运行时动态运营发生在用户会话中。

数据反馈与模板更新发生在会话后、活动中期或活动结束后。

| 对比项 | 运行时动态运营 | 数据反馈与模板更新 |
|---|---|---|
| 时间 | 用户正在玩的时候 | 活动阶段性或结束后 |
| 决策对象 | 单个用户、单次会话、单个节点 | 活动、模板、KOL、渠道、策略 |
| 输入 | 实时事件、分群、风险信号 | 汇总事件、归因、决策结果、转化数据 |
| 输出 | `runtime_decision` | `diagnosis_result`、`template_update` |
| 作用 | 当场优化体验 | 优化下一轮生成和模板默认值 |
| 风险 | 决策越界、干扰体验 | 错误归因、错误更新模板 |

运行时动态运营负责把策略用起来。

数据反馈与模板更新负责判断策略是否有效，并把有效经验沉淀下来。

## 6. 和 KOL 二次编辑的区别

KOL 二次编辑是上线前或版本迭代时的人工修改。

数据反馈与模板更新是基于真实数据的系统性沉淀。

| 对比项 | KOL 二次编辑 | 数据反馈与模板更新 |
|---|---|---|
| 发生时间 | 发布前，或新版本前 | 发布后，运行数据产生后 |
| 输入 | KOL 主观偏好和运营判断 | 用户行为、渠道、转化、风控、Agent 决策 |
| 输出 | `config_patch` | `template_update`、`kol_memory` |
| 重点 | 改当前版本 | 改下一次默认生成 |
| 风险 | 修改越界、破坏规则 | 误判原因、污染模板 |

二次编辑的数据本身也要进入反馈系统。

例如 KOL 反复修改首屏标题，说明模板默认标题可能不适合这个 KOL 类型。

## 7. 前台 KOL 能看到什么

KOL 不需要看到完整数据模型。

KOL 需要看到能指导下一步行动的结果。

| KOL 可见内容 | 说明 |
|---|---|
| 活动表现总结 | 这次活动整体效果如何 |
| 核心漏斗 | 曝光、开始、完成、分享、CTA、转化 |
| 最强渠道 | 哪个渠道带来更高质量用户 |
| 流失节点 | 用户主要卡在哪一步 |
| 粉丝行为特征 | 粉丝更爱答题、分享、领奖还是入群 |
| Agent 优化效果 | 动态提示、难度、CTA 是否改善指标 |
| 风控摘要 | 是否出现刷量、重复领取、异常点击 |
| 下次建议 | 下次该用什么模板、文案、CTA、奖励节奏 |
| 可保存配置 | 是否把本次成功配置保存为 KOL 专属模板 |

KOL 前台表达应该简洁。

例如：

| 后台诊断 | 前台表达 |
|---|---|
| 第 2 关流失率高，提示策略有效 | 粉丝主要卡在第 2 步，系统建议下次降低该节点难度 |
| Telegram 渠道 CTA 转化高 | 你的 Telegram 粉丝更适合社群转化，下次可优先投放 |
| 分享卡带来二跳用户但 CTA 低 | 分享内容吸引点击，但落地页转化弱，建议优化结果页 CTA |
| 风控拦截重复领取 | 检测到重复领取行为，下次建议提高空投任务验证强度 |

## 8. 后台系统真正发生什么

后台不是简单汇总数据。

它要把事件、版本、渠道、决策和结果串起来。

推荐流程：

| 步骤 | 后台动作 | 关键产物 |
|---|---|---|
| 1 | 收集运行时事件 | `runtime_events` |
| 2 | 收集 Agent 决策日志 | `agent_decision_applied` |
| 3 | 收集渠道和连接器数据 | `channel_metrics` |
| 4 | 收集 KOL 编辑和版本记录 | `config_patch_log` |
| 5 | 清洗和对齐数据 | `analytics_dataset` |
| 6 | 按活动、KOL、模板、渠道、版本归因 | `attribution_result` |
| 7 | 计算漏斗和关键指标 | `performance_report` |
| 8 | Diagnosis Agent 诊断问题 | `diagnosis_result` |
| 9 | 生成模板和策略更新建议 | `template_update_proposal` |
| 10 | 进入约束和人工审核 | `update_validation_report` |
| 11 | 写入 KOL Memory 和 Template Memory | `kol_memory`、`template_memory` |
| 12 | 生成新模板版本或默认配置 | `template_version` |
| 13 | 影响下一次生成和推荐 | `next_generation_context` |

## 9. 输入数据总览

数据反馈与模板更新需要多个来源。

| 数据来源 | 关键数据 | 用途 |
|---|---|---|
| H5 事件 | 曝光、开始、完成、分享、CTA、转化、流失 | 还原用户路径 |
| Runtime Agent | `runtime_decision`、`agent_decision_applied` | 判断 Agent 决策有效性 |
| 渠道连接器 | 曝光、点击、互动、转发、评论、入群 | 判断渠道质量 |
| 发布投放 | `publish_url`、渠道链接、归因参数 | 做渠道和版本归因 |
| KOL 二次编辑 | `config_patch`、修改字段、拒绝项 | 判断 KOL 偏好和模板默认问题 |
| 模拟测试 | `simulation_result`、预估风险 | 对比上线前预估和真实结果 |
| 约束验证 | `validation_report`、命中规则 | 发现合规和审核高频问题 |
| 奖励系统 | 奖励展示、触发、领取、异常 | 判断激励是否有效和是否被刷 |
| 风控系统 | 异常点击、重复领取、拦截、误伤 | 优化风控规则 |
| 转化系统 | 注册、入群、关注、购买、预约 | 判断营销目标是否达成 |

## 11. 最小分析颗粒度

数据反馈不能只按活动总量统计。

最小颗粒度应该是：

一个用户，在一次会话里，在某个版本、某个场景、某个渠道下，看到了某个组件或 Agent 决策，做了某个动作，并产生了某个结果。

可以拆成：

| 维度 | 说明 |
|---|---|
| 谁 | 用户、匿名用户、KOL 粉丝、风险用户、分群 |
| 从哪里来 | 渠道、连接器、分享链路、广告来源 |
| 在哪个版本 | `playable_version_id`、`template_version_id` |
| 看到什么 | 场景、组件、任务、奖励、CTA、分享卡 |
| Agent 改了什么 | `runtime_decision`、策略类型、应用动作 |
| 用户做了什么 | 点击、选择、完成、失败、分享、跳转 |
| 结果是什么 | 完成、流失、转化、奖励、风险、回访 |

这个颗粒度决定后续能不能判断哪个变量真的影响结果。

## 12. 归因维度

数据反馈必须解决归因。

否则无法判断问题来自模板、KOL、渠道、内容还是 Agent 策略。

| 归因维度 | 字段示例 | 作用 |
|---|---|---|
| 活动归因 | `campaign_id` | 判断哪个活动表现好 |
| KOL 归因 | `kol_id`、`kol_ref` | 判断哪个 KOL 带来高质量用户 |
| 模板归因 | `template_id`、`template_version_id` | 判断模板是否有效 |
| 版本归因 | `playable_version_id` | 判断哪个版本效果好 |
| 渠道归因 | `channel`、`connector_id` | 判断渠道质量 |
| 分享归因 | `share_id`、`referrer_id` | 判断裂变效果 |
| Agent 策略归因 | `policy_id`、`decision_id` | 判断策略是否有效 |
| 实验归因 | `experiment_id`、`group_id` | 判断 A/B 结果 |
| 内容归因 | `content_asset_id` | 判断文案、视觉、题目、分享卡效果 |
| CTA 归因 | `cta_id`、`cta_target` | 判断转化路径 |

## 17. `kol_memory` 结构

`kol_memory` 记录 KOL 的长期偏好和历史表现。

它用于下一次创作时自动给出更合适的默认设置。

| 字段 | 说明 |
|---|---|
| `kol_id` | KOL ID |
| `preferred_templates` | 常用或高表现模板 |
| `effective_channels` | 表现好的渠道 |
| `audience_behavior` | 粉丝行为特征 |
| `tone_preferences` | KOL 常用表达风格 |
| `cta_preferences` | 高表现 CTA 类型 |
| `reward_preferences` | 高表现奖励表达 |
| `share_preferences` | 高表现分享卡风格 |
| `risk_profile` | 历史风险类型 |
| `editing_patterns` | KOL 经常修改的字段 |
| `successful_configs` | 成功配置 |
| `failed_configs` | 失败配置 |
| `last_updated_at` | 更新时间 |

示例用途：

| 记忆内容 | 下次使用方式 |
|---|---|
| 该 KOL 的 Telegram 转化高 | 默认推荐 Telegram 入群 CTA |
| 该 KOL 粉丝喜欢排行榜 | 默认开启粉丝榜和分享卡 |
| 该 KOL 经常改首屏标题 | 下次首屏标题给更多候选 |
| 该 KOL 空投活动刷量多 | 下次提高风控默认强度 |

| `default_difficulty` | 推荐默认难度 |
| `default_session_length` | 推荐体验时长 |
| `best_reward_pattern` | 高表现奖励节奏 |

## 19. 核心指标体系

数据反馈必须围绕营销目标定义指标。

| 指标 | 含义 | 诊断用途 |
|---|---|---|
| Impression | 曝光 | 判断渠道触达 |
| CTR | 点击率 | 判断外部素材和标题吸引力 |
| Start Rate | 开始率 | 判断首屏理解和动机 |
| Completion Rate | 完成率 | 判断玩法难度和任务长度 |
| Drop-off Rate | 流失率 | 判断卡点 |
| Retry Rate | 重试率 | 判断挑战性和挫败感 |
| Share Rate | 分享率 | 判断结果反馈和社交传播 |
| CTA View Rate | CTA 展示率 | 判断 CTA 是否出现 |
| CTA Click Rate | CTA 点击率 | 判断 CTA 文案和时机 |
| Conversion Rate | 转化率 | 判断目标是否达成 |
| Reward Claim Rate | 奖励领取率 | 判断奖励激励 |
| Risk Rate | 异常率 | 判断刷量和滥用风险 |
| Retention | 回访和复玩 | 判断长期价值 |
| ROAS | 投入产出 | 判断付费投放效率 |
| Agent Uplift | Agent 策略增量 | 判断 Agentic 价值 |

## 20. 按营销目标诊断

不同营销目标不能用同一套结论。

| 营销目标 | 优先指标 | 主要诊断问题 |
|---|---|---|
| 项目认知 | Start Rate、Completion Rate、停留时长 | 用户是否看懂项目 |
| 用户教育 | 完成率、正确率、提示使用率 | 内容是否太难或太长 |
| 拉新激活 | CTR、Start Rate、首次任务完成 | 首屏是否有吸引力 |
| 社群增长 | CTA Click、入群转化、分享 | CTA 时机和渠道是否匹配 |
| 空投预热 | 任务完成、资格领取、风险率 | 激励是否有效且可控 |
| 产品转化 | CTA Click、Conversion、ROAS | 转化路径是否清晰 |
| 留存复玩 | 回访、复玩、连续任务完成 | 是否有下一步动力 |
| KOL 共创 | 分享、粉丝互动、KOL 复投意愿 | KOL 是否愿意继续使用 |

## 21. 漏斗诊断

漏斗诊断是最基础的数据反馈。

| 漏斗节点 | 可能问题 | 更新方向 |
|---|---|---|
| 曝光低 | 渠道触达不足或发布时间差 | 优化渠道和发布策略 |
| 点击低 | 标题、封面、分享卡吸引力不足 | 更新外部素材和首屏利益点 |
| 开始低 | 首屏说明不清、按钮弱、加载慢 | 更新首屏模板和性能标准 |
| 完成低 | 任务太长、难度太高、提示不足 | 更新默认难度和提示策略 |
| 分享低 | 结果反馈不够有炫耀感 | 更新分享卡和成绩表达 |
| CTA 低 | CTA 时机、文案或目标不匹配 | 更新 CTA 策略 |
| 转化低 | 落地页弱、信任不足、目标太重 | 更新转化路径和社群承接 |
| 风险高 | 奖励诱因过强或验证不足 | 更新风控规则 |
| 留存低 | 完成后没有下一步任务 | 更新留存和复玩机制 |

## 22. Agent 决策诊断

Agentic Playable 必须能诊断 Agent 决策是否有效。

核心问题：

Agent 做了什么？用户之后发生了什么？

| 策略 | 复盘指标 | 可能结论 |
|---|---|---|
| 动态难度 | 完成率、失败率、重试率 | 降难度是否提升完成 |
| 动态提示 | 提示后完成率、提示后流失率 | 提示是否真的救回用户 |
| 动态奖励 | 奖励查看率、完成率、异常率 | 奖励提示是否有效或引发刷量 |
| 动态 CTA | CTA 展示、点击、转化 | CTA 时机是否正确 |
| 动态分享 | 分享率、二跳访问、二跳转化 | 分享内容是否带来新用户 |
| 动态风控 | 拦截率、误伤率、异常下降 | 风控是否准确 |
| 分群策略 | 各分群漏斗表现 | 分群是否有差异化价值 |
| 回退策略 | 回退次数、失败影响 | Runtime 是否稳定 |

如果 `agent_decision_applied` 缺失，不能做 Agent 效果复盘。

## 23. 内容诊断

内容诊断判断文案、视觉、题目、任务和反馈是否影响结果。

| 内容层 | 诊断指标 | 更新对象 |
|---|---|---|
| 首屏标题 | Start Rate、CTR | 标题模板、利益点模板 |
| 副标题 | Start Rate、停留时长 | 价值说明模板 |
| 按钮文案 | Start Rate | CTA 按钮库 |
| 题目内容 | 正确率、完成率 | 题库和难度标签 |
| 任务说明 | 流失率、错误操作 | 任务说明模板 |
| 反馈文案 | 重试率、分享率 | 成功/失败反馈池 |
| 结果页 | 分享率、CTA 点击 | 结果页布局和文案 |
| 分享卡 | 分享率、二跳访问 | 分享卡模板 |
| 免责声明 | 合规命中率 | 合规模板 |

## 24. 游戏规则诊断

游戏规则诊断判断玩法结构是否合理。

| 规则问题 | 数据信号 | 更新方向 |
|---|---|---|
| 题目太多 | 中途流失高 | 降低默认题量 |
| 难度太高 | 失败率高、提示使用多 | 降低默认难度 |
| 任务链太长 | 后段流失高 | 减少 P0 任务步骤 |
| 奖励条件过难 | 奖励触发低 | 调整奖励门槛 |
| CTA 出现太晚 | 完成后流失 | 提前或分层展示 CTA |
| 分享条件太苛刻 | 分享率低 | 放宽分享触发条件 |
| 反作弊太弱 | 风险率高 | 增强验证和限频 |
| 反作弊太强 | 误伤率高 | 优化风控阈值 |

规则更新通常不能自动直接上线。

需要经过规则校验、模拟测试和合规验证。

## 25. 渠道诊断

渠道诊断判断哪些连接器和渠道值得继续投入。

| 渠道信号 | 可能结论 | 更新方向 |
|---|---|---|
| 点击高、完成低 | 渠道流量不匹配或标题误导 | 降低渠道权重或换素材 |
| 完成高、CTA 低 | 用户愿意玩但转化意愿弱 | 调整 CTA 和承接 |
| 分享高、转化高 | 渠道适合裂变 | 下次优先推荐该渠道 |
| 曝光低、转化高 | 渠道质量高但触达不足 | 增加投放或排期 |
| 风险率高 | 可能刷量或羊毛党集中 | 提高风控或暂停渠道 |
| 入群高、留存低 | 入群承接弱 | 优化社群运营和后续任务 |

渠道诊断结果可以进入：

| 下游 | 用途 |
|---|---|
| KOL Memory | 记录该 KOL 的高效渠道 |
| 模板推荐 | 判断模板适合哪些渠道 |
| 发布投放 | 下次默认推荐渠道组合 |
| 预算建议 | 付费投放时优化预算 |
| 风控策略 | 高风险渠道提高验证 |

## 26. KOL 诊断

KOL 诊断不是评价 KOL 好坏，而是判断 KOL 的粉丝适合什么玩法和路径。

| 观察项 | 诊断问题 | 更新方向 |
|---|---|---|
| 粉丝开始率 | 粉丝是否被首屏吸引 | 更新首屏利益点 |
| 粉丝完成率 | 粉丝是否适合该玩法 | 推荐更适合模板 |
| 粉丝分享率 | 粉丝是否愿意传播 | 优化分享卡和排行榜 |
| 粉丝 CTA | 粉丝是否有转化意愿 | 调整 CTA 类型 |
| 粉丝风险率 | 是否存在刷量或薅奖励 | 提高验证 |
| KOL 编辑行为 | KOL 偏好哪些表达 | 更新 KOL 语气和默认字段 |
| KOL 复投意愿 | 是否愿意继续合作 | 输出下一轮方案 |

KOL 诊断结果不能只看总量。

小 KOL 可能流量少但质量高，大 KOL 可能曝光高但转化弱。

## 27. 模板诊断

模板诊断判断某类玩法是否适合某类目标。

| 模板类型 | 重点诊断 |
|---|---|
| 竞猜 / 预测 | 正确率、完成率、分享率、是否存在投资误解 |
| 空投任务 | 任务完成、奖励领取、风险率、钱包或社群转化 |
| 跑酷 | 前 5 秒流失、失败率、复玩、成绩分享 |
| 塔防 | 波次完成、资源理解、升级路径、策略提示效果 |
| 射击 | 命中率、连击、脚本风险、分数分享 |
| 画线 | 卡点、提示使用、路径复杂度、完成率 |
| 模拟经营 | 留存、资源理解、里程碑、长期任务 |

模板诊断要回答：

1. 这个模板适合什么营销目标？
2. 这个模板适合什么 KOL 类型？
3. 这个模板适合什么渠道？
4. 这个模板最常见的流失点是什么？
5. 这个模板的默认难度是否合理？
6. 这个模板是否容易引发合规或风控问题？

## 28. 模板更新类型

模板更新不是只改视觉。

可以更新的内容包括：

| 更新类型 | 说明 |
|---|---|
| 默认字段更新 | 改默认标题、难度、任务数、CTA 时机 |
| 字段优先级更新 | 改前台表单优先展示哪些字段 |
| 可编辑边界更新 | 调整 KOL 可改和不可改范围 |
| 游戏规则更新 | 调整题量、胜利条件、奖励条件 |
| Agent 策略更新 | 更新动态提示、难度、奖励、CTA 策略 |
| 内容池更新 | 增加高表现文案、题目、分享卡 |
| 风控规则更新 | 增强反作弊和奖励校验 |
| 合规规则更新 | 增加负面案例和禁止表达 |
| 埋点要求更新 | 增加缺失事件或参数 |
| 推荐排序更新 | 调整模板在不同目标下的推荐权重 |

## 29. 模板更新优先级

不是所有诊断结论都应该立刻更新模板。

推荐按影响营销结果的优先级排序。

| 优先级 | 更新项 | 原因 |
|---|---|---|
| P0 | 埋点缺失修复 | 没有数据无法复盘 |
| P0 | CTA 时机和目标 | 直接影响转化 |
| P0 | 首屏标题和利益点 | 直接影响开始率 |
| P0 | 默认任务长度和难度 | 直接影响完成率 |
| P0 | 奖励规则和风控 | 直接影响成本和风险 |
| P1 | 分享卡和结果反馈 | 影响裂变 |
| P1 | 用户分群策略 | 影响精细运营 |
| P1 | 渠道默认推荐 | 影响投放效率 |
| P1 | KOL 专属默认语气 | 影响 KOL 使用体验 |
| P2 | 视觉风格细节 | 通常低于玩法和转化路径 |
| P2 | 高级自动策略学习 | 需要稳定数据积累 |

## 30. 更新是否自动生效

数据反馈可以自动生成建议，但不建议所有更新自动上线。

| 更新类型 | 是否可自动 | 建议 |
|---|---|---|
| 报表总结 | 可以自动 | 直接生成 |
| KOL Memory 更新 | 可半自动 | 低风险偏好可自动，高风险需确认 |
| 模板推荐权重 | 可半自动 | 小范围灰度 |
| 文案池新增 | 需审核 | 先进入候选池 |
| CTA 默认策略 | 需审核 | 涉及转化和合规 |
| 奖励规则 | 需人工审核 | 涉及成本和承诺 |
| 风控规则 | 需人工或风控审核 | 影响误伤和安全 |
| 游戏规则 | 需测试和验证 | 影响玩法和数据归因 |
| 合规负样本 | 可快速加入 | 但要确认分类准确 |

原则：

数据可以自动发现问题。

系统可以自动生成建议。

但影响线上模板默认行为的更新，必须有版本、审核和回滚。

## 31. 模板版本管理

每一次模板更新都必须版本化。

否则数据归因会失效。

| 版本对象 | 说明 |
|---|---|
| `template_version_id` | 模板结构版本 |
| `default_config_version` | 默认配置版本 |
| `agent_policy_version` | Agent 策略版本 |
| `game_rules_version` | 游戏规则版本 |
| `content_pool_version` | 内容池版本 |
| `risk_policy_version` | 风控版本 |
| `tracking_schema_version` | 埋点版本 |

版本更新必须记录：

| 记录项 | 说明 |
|---|---|
| 更新前 | 原始配置 |
| 更新后 | 新配置 |
| 更新原因 | 来自哪个诊断 |
| 数据证据 | 哪些指标支持 |
| 影响范围 | 全局、模板、KOL、渠道、实验 |
| 审核人 | 谁批准 |
| 生效时间 | 何时生效 |
| 回滚方案 | 如何恢复 |

## 32. `template_update` 的验证流程

模板更新不能直接改线上默认值。

推荐流程：

| 步骤 | 说明 |
|---|---|
| 1 | Diagnosis Agent 生成更新建议 |
| 2 | 系统判断风险等级 |
| 3 | 低风险建议进入候选更新 |
| 4 | 高风险建议进入人工审核 |
| 5 | 约束服务验证规则、合规、数据埋点 |
| 6 | 模拟测试验证关键路径 |
| 7 | 灰度到部分 KOL 或部分活动 |
| 8 | 对比更新前后效果 |
| 9 | 表现稳定后合并为模板新版本 |
| 10 | 保留旧版本用于回滚 |

## 33. KOL Memory 更新逻辑

KOL Memory 更新要区分事实、偏好、建议。

| 类型 | 示例 | 是否可直接用于下次生成 |
|---|---|---|
| 事实 | 该 KOL 上次使用竞猜模板 | 可以 |
| 表现 | Telegram 渠道转化高 | 可以，但需带时间和样本量 |
| 偏好 | KOL 多次改成更强挑战语气 | 可以作为候选 |
| 建议 | 下次推荐空投任务模板 | 需要结合目标判断 |
| 风险 | 上次重复领取风险高 | 可以作为风控输入 |
| 失败 | 某 CTA 转化低 | 不一定禁止，但降低推荐 |

KOL Memory 不应该把一次偶然结果永久固化。

需要记录样本量、时间窗口和置信度。

## 34. Template Memory 更新逻辑

Template Memory 更偏全局。

它不只服务单个 KOL，而是服务同类模板的长期优化。

| 更新对象 | 数据证据 | 更新方式 |
|---|---|---|
| 推荐目标 | 多个活动在某目标下表现好 | 提升该目标推荐权重 |
| 默认难度 | 多个活动完成率低 | 降低默认难度 |
| 默认 CTA | 某 CTA 时机稳定提升转化 | 调整默认 CTA 时机 |
| 默认分享卡 | 某分享卡带来二跳高 | 加入默认分享样式 |
| 风控规则 | 某模板异常率高 | 提高默认验证 |
| 字段顺序 | KOL 反复修改某字段 | 把该字段前置 |
| 负样本 | 合规问题高频出现 | 加入禁止表达或校验规则 |

Template Memory 的更新需要更谨慎。

因为它会影响很多 KOL 和很多活动。

## 35. 内容池更新

内容池更新是把高表现内容变成可复用资产。

| 内容池 | 可更新内容 |
|---|---|
| 首屏标题池 | 高开始率标题 |
| 副标题池 | 高理解度说明 |
| 按钮文案池 | 高点击按钮文案 |
| 任务说明池 | 低流失任务说明 |
| 题库 | 高完成、高教育价值题目 |
| 提示文案池 | 能降低卡点的提示 |
| 成功反馈池 | 能提升分享的反馈 |
| 失败反馈池 | 能提升重试的反馈 |
| 分享卡池 | 高二跳访问分享卡 |
| CTA 文案池 | 高转化 CTA 文案 |
| 合规模板池 | 免责声明、风险提示 |

内容池更新必须标注来源和适用范围。

例如一个在 Telegram 社群高转化的 CTA 文案，不一定适合广告渠道。

## 36. 负样本更新

失败和违规案例也要沉淀。

负样本比成功样本更能提升系统稳定性。

| 负样本类型 | 用途 |
|---|---|
| 低开始率标题 | 避免下次生成类似表达 |
| 高流失任务 | 提醒模板降低任务复杂度 |
| 低转化 CTA | 降低推荐权重 |
| 高风险奖励表达 | 加入合规拦截 |
| 高刷量任务结构 | 加强风控 |
| KOL 常拒绝字段 | 调整默认生成或表单 |
| 审核失败内容 | 加入约束服务 |
| 用户投诉内容 | 加入风险提示 |

负样本不一定意味着永久禁止。

它意味着系统下次生成时需要降低权重、增加校验或要求人工确认。

## 37. 模板推荐权重更新

数据反馈会影响模板推荐。

| 数据结果 | 推荐系统更新 |
|---|---|
| 竞猜模板在教育目标下完成率高 | 提升竞猜模板对教育目标推荐权重 |
| 空投模板风险率高 | 对低风控 KOL 降低推荐 |
| 跑酷模板分享率高 | 对裂变目标提高推荐 |
| 塔防模板完成率低但留存高 | 推荐给稳定运营而非冷启动 |
| 画线模板新手完成率高 | 推荐给低门槛拉新 |
| 模拟经营模板回访高 | 推荐给留存目标 |

推荐权重更新要避免单次活动过拟合。

最好结合多个活动、多个 KOL、多个渠道的数据。

## 38. Agent 策略补丁

数据反馈经常会生成 `agent_policy_patch`。

| 发现 | 策略补丁 |
|---|---|
| 用户连续失败后流失高 | 提前触发提示 |
| 提示后完成率提升 | 保留或增强提示策略 |
| 动态难度提升完成但降低分享 | 对高参与用户保持挑战 |
| CTA 太早导致开始率下降 | 延后 CTA 到结果页 |
| 奖励提示提升完成但风险上升 | 加入风控条件 |
| 分享卡二跳高 | 增加分享引导频率 |
| 风控误伤高 | 调整风险阈值 |

Agent 策略补丁必须继续受 `game_rules` 和 `runtime_boundaries` 约束。

## 39. 风控规则更新

风控数据必须进入模板更新。

尤其是空投、奖励、白名单、积分、抽奖类 Playable。

| 风控发现 | 更新方向 |
|---|---|
| 高频点击多 | 增加限频 |
| 重复领取多 | 增加账号、钱包、设备校验 |
| 某渠道风险高 | 渠道降权或暂停奖励 |
| 异常完成时间多 | 增加最短完成时间校验 |
| 分享刷量多 | 分享奖励增加二次验证 |
| 误伤正常用户 | 降低阈值或优化判断条件 |
| 投诉增加 | 加强奖励说明和免责声明 |

风控更新优先级高于增长优化。

如果增长策略和风控冲突，风控优先。

## 40. 合规更新

合规更新来自审核失败、投诉、举报、平台规则变化和运行时风险。

| 发现 | 更新对象 |
|---|---|
| 文案出现收益承诺 | 负样本和 Prompt 约束 |
| CTA 指向未授权链接 | CTA 校验规则 |
| 奖励表达容易误解 | 奖励文案模板 |
| 分享卡夸大效果 | 分享卡合规模板 |
| 用户投诉活动误导 | 审核规则和免责声明 |
| 某平台禁止引导行为 | 渠道发布规则 |
| 风险用户绕过验证 | Runtime 边界和风控规则 |

合规更新不应该只存在审核人员脑子里。

必须沉淀到规则库、负样本库和生成约束里。

## 41. 冷启动阶段的反馈重点

冷启动阶段不要追求复杂模型。

重点是证明链路有效。

| 优先级 | 反馈问题 | 原因 |
|---|---|---|
| P0 | KOL 愿不愿意发 | 决定供给侧是否成立 |
| P0 | 粉丝愿不愿意点 | 决定首屏和分享是否有效 |
| P0 | 用户能不能完成 | 决定模板和任务是否可用 |
| P0 | 结果能不能分享 | 决定裂变是否成立 |
| P0 | 数据能不能验证 | 决定后续是否可优化 |
| P0 | 奖励有没有被刷 | 决定活动是否可控 |
| P1 | 哪些渠道质量高 | 决定投放重点 |
| P1 | 哪些 Agent 策略有效 | 决定是否扩大动态运营 |
| P2 | 自动学习和自动更新 | 数据不足时不应过早做 |

## 42. 稳定阶段的反馈重点

稳定阶段要从单次活动复盘走向长期资产沉淀。

| 方向 | 说明 |
|---|---|
| KOL 长期画像 | 形成 KOL 的模板、渠道、语气和粉丝偏好 |
| 模板长期评分 | 判断模板在不同目标下的长期表现 |
| 策略长期优化 | 根据多次活动优化 Agent 策略 |
| 内容资产沉淀 | 建立高表现内容池 |
| 风控模式识别 | 识别不同模板的风险模式 |
| 复投建议 | 判断哪些 KOL、渠道、模板适合继续投入 |
| 生命周期运营 | 从一次活动扩展到持续任务和留存 |

## 44. 反馈到下一次生成

数据反馈最终要影响下一次生成。

| 反馈结论 | 下一次生成变化 |
|---|---|
| 某 KOL 粉丝喜欢挑战 | 默认使用更强挑战文案 |
| 某模板完成率低 | 默认降低难度或缩短任务 |
| 某 CTA 时机有效 | 默认采用该 CTA 节点 |
| 某渠道转化高 | 默认推荐该渠道 |
| 某分享卡有效 | 默认使用类似分享结构 |
| 某奖励引发风险 | 默认提高风控或调整奖励表达 |
| 某题型教育效果好 | 默认增加类似题型 |
| 某视觉风格低效 | 降低该风格推荐权重 |

## 45. 反馈到营销目标选择

数据反馈也会影响下一次营销目标推荐。

| 数据表现 | 下次目标建议 |
|---|---|
| 完成率高但转化低 | 从直接转化改为社群培育 |
| 分享高但留存低 | 从裂变目标增加留存任务 |
| CTA 高但入群低 | 检查落地页或社群承接 |
| 教育完成高 | 可以推进到转化目标 |
| 风险率高 | 降低奖励型目标权重 |
| 粉丝互动强 | 推荐 KOL 共创或排行榜目标 |

## 46. 反馈到模板推荐

模板推荐不应该只根据用户手动选择。

它应该读取历史数据。

| 历史数据 | 推荐变化 |
|---|---|
| 该 KOL 竞猜表现好 | 优先推荐竞猜衍生模板 |
| 该 KOL 空投风险高 | 空投模板增加风险提示或降低推荐 |
| 该 KOL 粉丝分享强 | 推荐跑酷、排行榜、挑战类模板 |
| 该 KOL 粉丝教育完成好 | 推荐答题、竞猜、教程类模板 |
| 某模板在该渠道表现差 | 降低该渠道下的模板推荐 |

## 47. 反馈到关键变量填写

关键变量填写可以由数据反馈自动预填或推荐。

| 变量 | 数据反馈影响 |
|---|---|
| 目标用户 | 根据历史高转化分群推荐 |
| 玩法模板 | 根据 KOL 和目标历史表现推荐 |
| session length | 根据完成率和流失点推荐 |
| difficulty | 根据失败率和提示使用推荐 |
| first reward | 根据奖励触发和风险推荐 |
| CTA timing | 根据 CTA 点击和转化推荐 |
| share mechanism | 根据分享和二跳转化推荐 |
| retention loop | 根据回访和复玩推荐 |
| risk threshold | 根据异常率推荐 |

## 48. 反馈到创作 Brief

复盘结论可以成为下一次 Brief 的输入。

| 复盘发现 | Brief 更新 |
|---|---|
| 用户更关注奖励资格 | Brief 强调资格和进度 |
| 用户更关注挑战成绩 | Brief 强调挑战和排行榜 |
| 用户对项目理解弱 | Brief 增加教育目标 |
| KOL 语气更有效 | Brief 继承 KOL 专属表达 |
| 某渠道更有效 | Brief 指定渠道语境 |
| 某风险高 | Brief 限制奖励表达 |

## 49. 反馈到 Agent 策略

Agent 策略生成可以读取历史策略效果。

| 历史策略效果 | 下一次策略 |
|---|---|
| 提示策略有效 | 默认启用更早提示 |
| 难度调整有效 | 扩大动态难度范围 |
| CTA 过早伤害开始率 | 延迟 CTA |
| 分享引导有效 | 增加结果页分享模块 |
| 风控误伤高 | 调整风险阈值 |
| 奖励提示引发刷量 | 增加领取前验证 |

## 50. 反馈到约束与合规

复盘中的风险和失败案例应进入约束系统。

| 反馈 | 约束更新 |
|---|---|
| 审核失败文案 | 加入禁止表达 |
| 用户投诉误导 | 加强免责声明 |
| 投资暗示风险 | 增加 Prompt 负样本 |
| CTA 链接风险 | 增加链接校验 |
| 奖励误解 | 更新奖励表达规则 |
| 风控绕过 | 更新 Runtime 校验 |

## 51. 反馈到 H5 Builder

如果数据反馈发现某些动态能力无法被追踪或落地，也要更新 Builder。

| 问题 | Builder 更新 |
|---|---|
| 某按钮未埋点 | 增加组件默认事件 |
| CTA 归因缺失 | 强制 CTA 参数注入 |
| 分享卡无法追踪二跳 | 增加分享 ID |
| 动态提示无法区分版本 | 增加策略版本字段 |
| 前端无法应用策略 | 增加动态槽位 |
| 加载慢影响开始率 | 优化资源加载 |

## 52. 数据质量要求

数据反馈之前必须先保证数据质量。

| 数据质量问题 | 后果 |
|---|---|
| 事件缺失 | 无法判断漏斗 |
| 归因参数缺失 | 无法比较渠道和 KOL |
| 版本号缺失 | 无法判断哪个版本有效 |
| Agent 决策缺失 | 无法证明 Agentic 价值 |
| 重复事件未去重 | 指标虚高 |
| 风险流量未剔除 | 误判增长效果 |
| 时间窗口不一致 | 前后对比失真 |
| 样本量太小 | 容易过拟合 |

## 53. 样本量和置信度

不是所有结论都应该进入模板更新。

| 情况 | 处理方式 |
|---|---|
| 样本量很小 | 只生成观察，不改模板 |
| 指标波动大 | 继续观察或做实验 |
| 单个 KOL 有效 | 先写入 KOL Memory，不更新全局模板 |
| 多个 KOL 有效 | 可进入 Template Memory |
| 多渠道稳定有效 | 可提升推荐权重 |
| 存在合规风险 | 先审核再更新 |
| 有明显风控问题 | 优先更新风控 |

## 54. 人工审核与权限

数据反馈可以自动化，但模板更新要有权限控制。

| 角色 | 权限 |
|---|---|
| KOL | 查看报告、保存成功配置、申请下次方案 |
| 平台运营 | 审核模板更新建议、配置灰度 |
| 数据分析 | 校验诊断结论和实验结果 |
| 风控运营 | 审核风控规则更新 |
| 合规审核 | 审核内容池、CTA、奖励表达 |
| 模板运营 | 管理模板版本和推荐权重 |
| 系统管理员 | 管理全局权限和回滚 |

## 55. MVP 建议落地范围

MVP 不需要一开始做复杂自动学习。

建议先做可解释闭环。

### 55.1 P0 必须实现

| 能力 | 说明 |
|---|---|
| 基础漏斗报表 | 曝光、开始、完成、分享、CTA、转化、流失 |
| 版本和渠道归因 | 能按 KOL、渠道、版本看数据 |
| Agent 决策复盘 | 能看 `agent_decision_applied` 后续结果 |
| 简单 Diagnosis | 输出主要流失点和建议 |
| KOL Memory | 记录 KOL 偏好和有效配置 |
| Template Memory | 记录模板默认值和表现 |
| 模板更新建议 | 先建议，不自动生效 |
| 负样本库 | 记录审核失败、风控失败和低效案例 |

### 55.2 P1 可增强

| 能力 | 说明 |
|---|---|
| 策略 A/B 分析 | 计算 Agent 策略增量 |
| 渠道质量评分 | 推荐下一轮渠道 |
| 内容池优化 | 自动标记高表现文案和分享卡 |
| 模板推荐权重 | 根据历史表现调整推荐 |
| 灰度模板更新 | 小范围验证新默认值 |
| 风控模型优化 | 根据异常模式更新规则 |

### 55.3 P2 再考虑

| 能力 | 说明 |
|---|---|
| 自动模板版本发布 | 需要稳定审核和回滚机制 |
| 跨 KOL 智能推荐 | 需要足够历史数据 |
| 自动预算优化 | 需要连接投放成本和收入 |
| 多 Agent 协作复盘 | Diagnosis、Strategy、Risk、Template Agent 协作 |
| 长期生命周期运营 | 跨多次活动管理用户资产 |

## 56. 数据反馈报告结构

一份标准复盘报告建议包括：

| 模块 | 内容 |
|---|---|
| 活动概览 | 活动目标、KOL、模板、版本、渠道、周期 |
| 核心结论 | 成功点、失败点、最大机会 |
| 漏斗表现 | 曝光到转化每一步 |
| 用户分群 | 不同分群表现 |
| 渠道表现 | 不同渠道质量 |
| Agent 决策 | 哪些动态策略有效 |
| 内容表现 | 首屏、任务、结果页、分享卡、CTA |
| 风控表现 | 异常、拦截、误伤、投诉 |
| 模板问题 | 默认字段和玩法结构问题 |
| KOL 偏好 | KOL 修改和粉丝反馈 |
| 下一轮建议 | 目标、模板、内容、策略、渠道 |
| 更新建议 | 写入哪些 Memory 和模板版本 |

## 57. 常见错误

| 错误 | 后果 |
|---|---|
| 只看总转化率 | 无法判断具体问题 |
| 不记录版本 | 模板更新后无法归因 |
| 不记录 Agent 决策 | 无法证明 Agentic 价值 |
| 单次活动就更新全局模板 | 容易过拟合 |
| 把异常流量算进成功指标 | 误判奖励策略有效 |
| 只看点击不看完成 | 容易做标题党式优化 |
| 只看完成不看转化 | 游戏好玩但营销无效 |
| 不区分渠道 | 无法判断投放质量 |
| 更新模板不审核 | 合规和体验风险高 |
| 不保存失败案例 | 同类错误会重复出现 |

## 58. 推荐产品表达

面向 KOL 时，不建议说：

系统会把 `runtime_events`、`agent_decision_applied`、`diagnosis_result` 写入 `template_memory` 并生成 `template_update_proposal`。

建议说：

活动结束后，Airvana 会自动分析粉丝在哪一步流失、哪个渠道效果最好、哪些 Agent 优化有效，并把成功经验保存为你下次创作的默认配置。

面向平台内部时，可以说：

数据反馈与模板更新是 Airvana 的学习闭环。它把运行时事件、Agent 决策、渠道归因、KOL 编辑和转化结果，通过 Diagnosis Agent 转化为 `performance_report`、`diagnosis_result`、`kol_memory`、`template_memory` 和 `template_update_proposal`，再经过验证、审核和版本化，影响下一轮生成、模板推荐和运行时策略。

## 59. 验收标准

这个环节是否成立，可以用以下标准判断。

| 验收项 | 标准 |
|---|---|
| 数据完整 | 核心事件和归因参数齐全 |
| 决策可复盘 | 每个 Agent 决策可追踪到后续结果 |
| 报告可读 | KOL 能看懂主要结论 |
| 诊断可解释 | Diagnosis Agent 能给出证据 |
| 更新可落地 | 建议能映射到模板、内容、规则或策略 |
| 版本可追溯 | 每次更新有版本和原因 |
| 风险可控制 | 高风险更新需要审核 |
| 效果可验证 | 更新后能比较前后效果 |
| 记忆可复用 | KOL Memory 和 Template Memory 能进入下一次生成 |
| 失败可沉淀 | 负样本进入约束和模板系统 |

## 60. 最终结论

数据反馈与模板更新，是 Airvana Agentic Playable 的学习层。

它把一次活动的真实结果，转化成下一次更准的生成、更稳的模板、更有效的 Agent 策略、更清晰的 KOL 画像和更安全的风控规则。

MVP 阶段最重要的是先跑通五件事：

1. 事件和归因完整。
2. Agent 决策能复盘。
3. Diagnosis Agent 能输出可解释建议。
4. KOL Memory 和 Template Memory 能写入。
5. 模板更新建议必须经过验证、审核和版本化。

只要这五件事成立，Airvana 的 Agentic Playable 就不是一次性内容生成，而是一个会从每次投放中学习、沉淀和进化的营销增长系统。
