# 约束与合规验证机制结构化梳理

## 1. 核心定义

约束与合规验证，是指在 Agentic Playable 进入 H5 组装、预览、发布或运行时更新之前，系统对生成结果进行结构化审核，确认它是否符合业务目标、模板规则、品牌要求、奖励边界、平台政策、数据隐私、风控要求和可追踪要求。

它的核心不是“人工看一遍”，而是把平台不能违反的规则做成可执行的校验系统。

| 容易误解 | 正确认知 |
|---|---|
| 只是文案敏感词检测 | 同时检查目标、内容、规则、奖励、CTA、数据、Agent 策略和风控 |
| 只是上线前人工审核 | 应该贯穿生成、编辑、发布和运行时策略更新 |
| 只是法律合规 | 还包括品牌、安全、可玩性、可追踪、平台政策和运营风险 |
| 只要 AI 自己判断就行 | 必须有规则中心、结构校验、审计日志和人工复审机制 |
| 只检查最终页面 | 必须检查 `content_assets`、`game_rules`、`agent_policy` 和版本配置 |

一句话：

**约束与合规验证 = 让 Agentic Playable 在可控边界内生成、上线和运营，防止 AI 为了转化率突破业务、合规、品牌和数据安全边界。**

## 2. 在完整工作流中的位置

约束与合规验证发生在核心生成链路之后、H5 组装和发布之前，同时也发生在 KOL 二次编辑和 Runtime Agent 策略更新之后。

| 阶段 | 输入 | 输出 |
|---|---|---|
| KOL 身份识别 | `kol_context` | KOL 风险、受众、语气和合作边界 |
| 营销目标选择 | `campaign_goal` | 主目标、次目标、CTA、指标和目标约束 |
| 模板推荐 | `template_schema` | 可用玩法、素材槽位、规则能力 |
| 关键变量填写 | `template_config` | 活动主题、奖励、CTA、任务和合规字段 |
| Brief 生成 | `generation_brief` | 生成任务书和合规边界 |
| 内容生成 | `content_assets` | 文案、视觉、任务、分享卡、CTA、免责声明 |
| 游戏规则生成 | `game_rules` | 状态机、胜负、奖励、反作弊、埋点 |
| Agent 运营策略生成 | `agent_policy` | 分群、难度、提示、奖励、CTA、风控和日志策略 |
| 约束与合规验证 | 以上所有对象 | `validation_report` |
| H5 组装 | 通过验证的对象 | `playable_version` |
| 模拟测试 | 可运行版本 | `simulation_result` |
| 发布 | 通过测试和审核的版本 | `publish_url` |
| 运行时优化 | 事件和策略 | `runtime_decision`、策略补丁 |

关键原则：

1. 没有通过验证，不能进入正式发布。
2. KOL 修改后必须重新验证受影响模块。
3. Runtime Agent 策略更新后必须验证是否仍在边界内。
4. 高风险活动必须进入人工复审。
5. 所有拦截、放行和自动修复都要留审计日志。

## 3. 约束与合规验证的核心目标

| 目标 | 说明 |
|---|---|
| 可上线 | 内容、规则、CTA、奖励和数据采集符合平台和项目要求 |
| 可运行 | 游戏规则完整，状态可达，不死循环，不破坏玩法 |
| 可解释 | 每个拒绝、警告、自动修复都有明确原因 |
| 可追踪 | 关键事件、转化和 Agent 决策都有埋点 |
| 可风控 | 高奖励、高传播、高金融风险场景具备反作弊和滥用控制 |
| 可回滚 | 版本、策略和补丁可以追溯和回退 |
| 可复审 | 人工审核能看到问题、证据、建议修改和影响模块 |

## 4. 验证对象总览

约束与合规验证不是只看最终页面，而是检查一组结构化产物。

| 验证对象 | 重点检查 |
|---|---|
| `kol_context` | KOL 风险、合作限制、地区、受众、历史违规和品牌敏感点 |
| `campaign_goal` | 主目标、CTA、指标、目标约束是否一致 |
| `template_schema` | 模板能力、可编辑槽位、规则边界、素材要求 |
| `template_config` | 关键变量是否完整，是否越过模板允许范围 |
| `generation_brief` | 生成任务是否包含合规、奖励、CTA、数据和品牌边界 |
| `content_assets` | 文案、视觉、任务、CTA、分享卡、免责声明是否安全 |
| `game_rules` | 状态机、胜负、奖励、反作弊、埋点是否完整可执行 |
| `agent_policy` | 运行时策略是否越过主目标、规则、奖励和合规边界 |
| `playable_version` | 最终版本是否与已验证对象一致 |
| `config_patch` | KOL 或运营编辑是否影响规则、奖励、CTA 或合规字段 |
| `runtime_decision` | 运行时决策是否符合 `runtime_boundaries` |

## 5. 主要输入

| 输入 | 来源 | 作用 |
|---|---|---|
| `compliance_constraints` | 项目方、平台、行业规则、默认规则库 | 决定不能说、不能做、必须展示什么 |
| `brand_constraints` | 项目方资料、品牌手册、资产库 | 检查品牌名、Logo、语气、视觉资产 |
| `campaign_goal` | 营销目标选择 | 检查目标、CTA、奖励和指标是否匹配 |
| `template_schema` | 模板库 | 检查玩法参数、素材槽位和规则边界 |
| `template_config` | 关键变量填写 | 检查活动配置是否完整和合理 |
| `generation_brief` | Brief Agent | 检查下游生成是否遵循任务书 |
| `content_assets` | Content Agent / Visual Agent | 检查文案、视觉、任务和分享资产 |
| `game_rules` | Rule Agent | 检查状态机、胜负、奖励、反作弊和埋点 |
| `agent_policy` | Strategy Agent / Runtime Agent | 检查动态策略是否可控 |
| `risk_profile` | KOL 风控、活动风险、渠道风险 | 决定是否强制人工复审 |
| `tracking_requirements` | 数据和看板系统 | 检查埋点是否完整 |

## 6. 核心输出

统一输出对象是 `validation_report`。

| 输出字段 | 含义 |
|---|---|
| `validation_report_id` | 验证报告 ID |
| `playable_version_id` | 被验证的版本 |
| `validation_scope` | 验证范围，例如全量、内容变更、规则变更、策略变更 |
| `input_artifacts` | 本次验证读取了哪些对象 |
| `risk_level` | 风险等级 |
| `publish_status` | 是否允许进入发布 |
| `blocked_items` | 必须修复的问题 |
| `warning_items` | 可发布但建议修复的问题 |
| `auto_fixed_items` | 系统已经自动修复的问题 |
| `auto_fix_suggestions` | 系统建议如何修改 |
| `human_review_required` | 是否需要人工复审 |
| `approved_modules` | 已通过验证的模块 |
| `rejected_modules` | 未通过验证的模块 |
| `required_disclaimers` | 必须展示的免责声明 |
| `runtime_boundaries` | Runtime Agent 需要遵守的边界 |
| `audit_log` | 规则命中、修复、放行和拦截记录 |

## 7. 风险等级与发布状态

### 7.1 风险等级

| 风险等级 | 含义 | 处理 |
|---|---|---|
| Low | 低风险，常规模板和常规奖励 | 可自动通过 |
| Medium | 涉及奖励、分享、KOL 推广或轻度金融表达 | 可发布，但需要警告和强制提示 |
| High | 涉及空投、抽奖、排行榜、真实利益、强 CTA 或高传播 | 阻止自动发布，进入人工复审 |
| Critical | 涉及收益承诺、投资建议、赌博、虚假背书、未授权数据采集 | 必须阻止发布 |

### 7.2 发布状态

| 状态 | 含义 |
|---|---|
| `approved` | 可进入 H5 组装或发布 |
| `approved_with_warnings` | 可继续，但保留警告和审计记录 |
| `needs_auto_fix` | 可以自动修复后再次验证 |
| `needs_user_revision` | 需要 KOL 或运营修改字段 |
| `needs_human_review` | 需要人工审核 |
| `blocked` | 不允许发布 |

### 7.3 一票否决项

| 一票否决项 | 示例 |
|---|---|
| 收益承诺 | 保证收益、稳赚、必涨、必中空投 |
| 投资建议 | 现在买入、推荐持仓、预测明确投资回报 |
| 赌博表达 | 用真实资产参与下注、以输赢决定真实收益 |
| 奖励误导 | 完成任务即可获得真实 Token，但没有规则和风控 |
| 虚假背书 | 未授权使用官方认证、交易所背书、名人背书 |
| 隐私越界 | 未授权采集钱包、联系方式、社交关系或私域内容 |
| Agent 越权 | Runtime Agent 改变奖励性质、绕过风控或强插 CTA |
| 规则不可玩 | 状态机死循环、任务无法完成、奖励无法触发 |

## 8. 验证维度一：结构完整性

结构完整性校验负责确认生成对象是否具备最基本的可执行结构。

| 校验项 | 说明 | 失败处理 |
|---|---|---|
| 必填字段完整 | 目标、模板、任务、奖励、CTA、埋点是否存在 | 要求补充 |
| 对象引用一致 | `campaign_goal`、`template_config`、`game_rules` 是否互相引用正确 | 阻止发布 |
| 版本 ID 完整 | 每个对象是否绑定同一版本 | 阻止发布 |
| 语言和地区字段 | 是否明确默认语言、地区和渠道 | 警告或要求补充 |
| 编辑权限 | KOL 是否修改了锁定字段 | 回滚修改 |
| 资产完整 | Logo、头像、背景、奖励图、分享卡是否可用 | 降级或阻止 |

MVP 阶段，结构完整性应该通过 Schema Validator 自动完成。

## 9. 验证维度二：营销目标与 CTA 一致性

CTA 是营销目标的执行出口，所以必须重点校验。

| 冲突类型 | 示例 | 处理 |
|---|---|---|
| 主目标与 CTA 不一致 | 主目标是社群增长，但 CTA 是购买 | 要求调整 CTA 或切换目标 |
| CTA 出现过早 | 用户还没理解项目就强制注册 | 改为结果页或阶段完成后展示 |
| CTA 权限不明 | 跳转到未授权链接 | 阻止发布 |
| CTA 文案过度刺激 | 立即领取暴富机会 | 自动改写或阻止 |
| CTA 目标不可追踪 | 链接没有参数或事件 | 要求补充埋点 |
| CTA 与规则冲突 | 规则规定结果页出现，Agent 在首屏展示 | 阻止策略 |

CTA 合法不等于 CTA 有转化力。约束系统只判断是否允许，运营优化再判断效果。

## 10. 验证维度三：内容合规

内容合规覆盖首屏、任务说明、结果反馈、奖励文案、分享卡、CTA、免责声明。

| 风险 | 示例 | 处理 |
|---|---|---|
| 收益承诺 | 完成任务必赚 100 USDT | 阻止或改为积分、资格、抽奖机会 |
| 投资建议 | 现在买入，下一轮一定涨 | 阻止 |
| 预测误导 | 准确预测明日价格 | 改为互动挑战或知识问答 |
| 空投误导 | 完成任务必中空投 | 改为获得活动资格或抽奖资格 |
| 奖励夸大 | 限时领取高额 Token | 要求规则证明和人工复审 |
| 未披露推广 | KOL 推广但没有广告或合作提示 | 根据地区和平台要求补充披露 |
| 敏感词 | 暴富、稳赚、保本、内幕、官方保证 | 替换或阻止 |
| 未成年人风险 | 面向未成年人引导金融或奖励行为 | 阻止或改目标人群 |

内容校验不能只依赖关键词。它还要结合语义、上下文、奖励类型、CTA 和活动规则判断。

## 11. 验证维度四：视觉与品牌

视觉资产也会产生合规和信任风险。

| 校验项 | 示例 | 处理 |
|---|---|---|
| 品牌名称 | 项目名拼写错误、旧名称、错误缩写 | 阻止发布 |
| Logo 使用 | 拉伸、错色、低清、未授权 Logo | 阻止或替换 |
| KOL 头像 | 使用错误头像或未授权头像 | 要求确认 |
| 官方背书 | 未授权展示官方认证、交易所 Logo | 阻止 |
| 视觉暗示 | 用钞票、暴涨箭头暗示收益 | 替换为中性资产 |
| 分享卡 | 分享图夸大奖励或隐去风险说明 | 重新生成 |
| 地区敏感元素 | 使用地区禁忌、政治敏感元素 | 人工复审 |

品牌验证的本质是：不允许 AI 为了视觉吸引力制造错误背书或误导信号。

## 12. 验证维度五：奖励与空投边界

奖励是 Agentic Playable 的高风险模块，尤其是 Web3、空投、抽奖、排行榜和邀请裂变。

| 奖励类型 | 默认风险 | 合规要求 |
|---|---|---|
| 虚拟积分 | 低 | 明确仅用于活动内展示或排名 |
| 徽章 / 身份 | 低 | 不暗示金融价值 |
| 抽奖资格 | 中 | 明确不是必中，规则透明 |
| 白名单资格 | 中 | 明确资格条件和最终解释规则 |
| 空投资格 | 高 | 不保证获得空投，不承诺价值 |
| 实物 / 现金奖励 | 高 | 需要地区规则、领取规则和人工审核 |
| Token 奖励 | 高 | MVP 阶段不建议自动生成，需要人工审核 |

奖励校验重点：

1. 奖励性质是否被清楚定义。
2. 奖励是否有触发条件。
3. 奖励是否有发放上限。
4. 奖励是否有反作弊。
5. 奖励文案是否夸大。
6. 奖励是否需要免责声明。
7. Agent 是否被禁止改变奖励性质。

## 13. 验证维度六：游戏规则可执行性

`game_rules` 需要经过规则校验，不只是合规校验。

| 校验项 | 说明 |
|---|---|
| 状态完整 | 是否包含开始、进行、成功、失败、奖励、结果页 |
| 状态可达 | 每个状态是否能从入口到达 |
| 状态可退出 | 每个状态是否能继续或结束 |
| 无死循环 | 是否存在无法结束的循环 |
| 胜负条件明确 | 成功、失败、部分完成如何判断 |
| 奖励触发明确 | 什么条件下触发奖励或资格 |
| CTA 位置明确 | CTA 出现在允许的状态 |
| 反作弊规则 | 是否限制异常速度、重复提交、重复钱包和重复设备 |
| 埋点绑定 | 每个关键状态是否有事件 |
| 降级路径 | 资产缺失、网络异常、验证失败时如何处理 |

游戏规则校验失败时，不能只改文案，通常要回到规则生成或模板配置阶段。

## 14. 验证维度七：Agent 运营策略边界

`agent_policy` 是动态的，所以必须设置比静态内容更严格的运行边界。

| 策略项 | 必须校验 |
|---|---|
| 分群策略 | 是否涉及敏感属性，是否有歧视或隐私风险 |
| 难度策略 | 是否在模板允许范围内，是否故意制造挫败 |
| 提示策略 | 是否频率过高，是否误导用户 |
| 奖励策略 | 是否改变奖励性质，是否绕过触发条件 |
| CTA 策略 | 是否在允许状态展示，是否过度打扰 |
| 分享策略 | 是否鼓励刷量、骚扰或误导性传播 |
| 风控策略 | 是否能拦截异常，是否允许异常用户绕过验证 |
| 实验策略 | 是否有版本标记和数据隔离 |
| 决策日志 | 是否记录 Agent 为什么做了调整 |

Agent 不能做的事：

1. 不能改变主目标。
2. 不能把虚拟奖励改成真实资产。
3. 不能绕过反作弊。
4. 不能强制用户完成未授权动作。
5. 不能采集未授权数据。
6. 不能为了提升 CTA 点击而制造误导。
7. 不能在未记录日志的情况下改变用户路径。

## 15. 验证维度八：数据隐私与授权

Agentic Playable 会连接 KOL、用户行为、社媒、钱包和转化数据，因此数据边界必须明确。

| 数据类型 | 风险 | 校验要求 |
|---|---|---|
| 登录信息 | 身份识别风险 | 明确授权和用途 |
| 社媒连接 | 公开资料和授权范围 | 不能超范围读取 |
| 钱包地址 | Web3 身份和资产关联风险 | 只在必要场景采集 |
| 联系方式 | 隐私和营销触达风险 | 需要明确授权 |
| 行为事件 | 用户画像和分群 | 只采集运营所需字段 |
| 分享关系 | 社交图谱风险 | 不采集未授权私域关系 |
| 设备指纹 | 反作弊和隐私冲突 | 需要最小化和合规说明 |
| 地理位置 | 地区合规风险 | MVP 不建议采集精确位置 |

数据校验原则：

1. 最小采集。
2. 明确用途。
3. 用户授权。
4. 可删除或可退出。
5. 敏感数据不暴露给 KOL。
6. 风控数据只做风险判断，不做营销歧视。

## 16. 验证维度九：渠道和平台政策

不同分发渠道对内容、奖励、分享和跳转有不同限制。

| 渠道 | 重点校验 |
|---|---|
| X / Twitter | 推广披露、虚假互动、误导性金融表达、链接安全 |
| Telegram | Bot / Mini App 跳转、群组任务、空投任务、反刷 |
| Discord | 社区任务、邀请奖励、成员权限和机器人行为 |
| Web H5 | 隐私提示、Cookie、钱包连接、跳转安全 |
| 广告平台 | 金融、博彩、抽奖、虚假承诺和落地页一致性 |
| App Store / Google Play | 外部支付、抽奖、钱包、数据采集和年龄分级 |

MVP 阶段不需要覆盖所有平台细则，但必须先建立渠道字段和渠道规则扩展位。

## 17. 验证维度十：风控与反作弊

风控验证负责判断活动是否容易被刷、被滥用或被异常流量攻击。

| 风险 | 示例 | 验证要求 |
|---|---|---|
| 重复领取 | 多账号、多钱包、多设备领取奖励 | 钱包、设备、行为和频次限制 |
| 异常速度 | 1 秒完成全部任务 | 速度阈值和异常标记 |
| 刷分享 | 大量无效分享点击 | 分享质量和来源校验 |
| 排行榜刷分 | 异常高分、重复提交 | 分数上限和提交频率限制 |
| 邀请作弊 | 虚假邀请、批量账号 | 邀请链路和完成质量校验 |
| CTA 刷量 | 大量无效点击 | 点击频率、来源和会话质量校验 |
| KOL 流量异常 | 粉丝点击异常、转化异常 | KOL 风险分和人工复审 |

风控验证不是为了拦住正常用户，而是防止奖励、排行榜、空投和数据看板被污染。

## 18. 约束系统架构

约束与合规验证应当作为平台级 Constraint Service，而不是散落在 Prompt 里的几句话。

| 模块 | 作用 |
|---|---|
| Constraint Registry | 规则中心，管理平台、行业、品牌、模板和活动规则 |
| Schema Validator | 校验对象结构、必填字段、类型和引用关系 |
| Rule Validator | 校验 `game_rules` 的状态机、奖励、CTA、反作弊和埋点 |
| Content Validator | 校验文案、视觉、任务、分享和免责声明 |
| Agent Policy Validator | 校验 `agent_policy` 和 `runtime_boundaries` |
| Risk Scorer | 对活动、KOL、奖励、渠道和内容给出风险等级 |
| Auto Fix Engine | 对可修复问题生成安全替代表达或配置 |
| Critic Agent | 对复杂语义风险进行二次判断 |
| Human Review Queue | 高风险问题进入人工复审 |
| Audit Log | 记录规则命中、修改、放行、拒绝和责任链 |
| Negative Example Manager | 沉淀失败案例，反向更新规则库 |

架构原则：

1. 规则必须版本化。
2. 规则命中必须可解释。
3. 高风险规则不能只靠模型判断。
4. 自动修复不能改变用户的核心营销意图。
5. 人工放行必须有记录。

## 19. 验证流程

标准流程如下：

| 步骤 | 说明 | 输出 |
|---|---|---|
| 1. 收集对象 | 读取目标、模板、内容、规则、策略和版本配置 | `input_artifacts` |
| 2. 结构校验 | 检查字段、类型、引用、版本和必填项 | 结构校验结果 |
| 3. 规则校验 | 检查游戏规则、奖励、CTA、反作弊和埋点 | 规则校验结果 |
| 4. 内容校验 | 检查文案、视觉、任务、分享卡和免责声明 | 内容校验结果 |
| 5. 策略校验 | 检查 Runtime Agent 的可调范围和日志要求 | 策略校验结果 |
| 6. 风险评分 | 结合 KOL、奖励、渠道、地区和目标计算风险 | `risk_level` |
| 7. 自动修复 | 对低风险问题给出替代表达或默认配置 | `auto_fixed_items` |
| 8. 再次验证 | 修复后重新跑相关校验 | 二次结果 |
| 9. 决定状态 | 通过、警告通过、要求修改、人工复审或阻止 | `publish_status` |
| 10. 留痕 | 记录命中规则、修复方案和责任人 | `audit_log` |

## 20. 自动修复与阻止发布

不是所有问题都需要人工处理。系统应该区分自动修复、用户修改、人工复审和直接阻止。

| 问题类型 | 处理方式 |
|---|---|
| 轻微措辞风险 | 自动替换为安全表达 |
| 缺少免责声明 | 自动补充并重新验证 |
| CTA 缺少埋点参数 | 自动补参数或要求运营确认 |
| 奖励表达不清 | 建议改为积分、徽章、资格或抽奖机会 |
| 目标和 CTA 冲突 | 要求用户选择其一 |
| 空投没有反作弊 | 阻止发布，要求开启风控 |
| 明确收益承诺 | 直接阻止 |
| 投资建议 | 直接阻止 |
| 未授权品牌背书 | 直接阻止 |
| 真实 Token 奖励 | 进入人工复审，MVP 默认阻止自动发布 |

自动修复的边界：

1. 可以改表达，不能改事实。
2. 可以加提示，不能删除关键规则。
3. 可以降低风险表达，不能替用户承诺项目方没有确认的内容。
4. 可以建议低风险奖励，不能自动创建真实奖励。
5. 可以修复埋点，不能新增未授权数据采集。

## 21. 人工复审机制

以下场景必须进入人工复审：

| 场景 | 原因 |
|---|---|
| 高价值奖励 | 可能涉及抽奖、税务、地区规则和滥用 |
| 空投或白名单 | 容易被误解为确定收益 |
| 金融或交易相关表达 | 投资建议和收益承诺风险高 |
| 使用第三方品牌资产 | 需要授权确认 |
| KOL 高风险画像 | 历史违规、刷量、投诉或异常转化 |
| 多地区投放 | 不同地区规则不同 |
| 人工覆盖系统拦截 | 必须记录责任和理由 |
| Agent 策略大幅影响用户路径 | 可能产生过度诱导或不公平 |

人工复审界面应展示：

| 展示内容 | 说明 |
|---|---|
| 问题摘要 | 哪些模块有问题 |
| 风险等级 | Low、Medium、High、Critical |
| 命中规则 | 命中了哪条规则 |
| 原始内容 | 被拦截的原文或配置 |
| 建议修复 | 系统推荐如何改 |
| 影响模块 | 影响内容、规则、策略还是发布 |
| 处理按钮 | 通过、退回、修改后通过、阻止 |
| 审计记录 | 审核人、时间、理由和版本 |

## 22. KOL 和运营前台如何呈现

KOL 不需要看到完整规则系统，但需要知道为什么不能发布或为什么要修改。

| 前台模块 | 展示方式 |
|---|---|
| 总体状态 | 可发布、需修改、需审核、不可发布 |
| 问题卡片 | 用自然语言解释问题 |
| 修改建议 | 给出可直接替换的安全表达 |
| 锁定字段 | 告知该字段由项目方或平台锁定 |
| 风险提示 | 告知奖励、空投、金融表达的限制 |
| 重新验证 | 修改后重新检查 |
| 人工审核状态 | 已提交、审核中、已通过、已驳回 |

前台文案应该具体，不应该只说“合规失败”。

示例：

| 不推荐提示 | 推荐提示 |
|---|---|
| 内容违规 | “必中空投”属于确定性奖励承诺，请改为“获得活动资格” |
| CTA 不合法 | 当前目标是社群增长，CTA 不能直接引导购买，请改为加入社群或了解项目 |
| 奖励错误 | 当前奖励缺少发放条件和反作弊规则，请补充领取条件或改为积分奖励 |

## 23. 与 KOL 二次编辑的关系

KOL 二次编辑后，不应该全部重跑，而是根据修改范围做局部验证。

| KOL 修改 | 需要重新验证 |
|---|---|
| 改标题 | 内容合规、品牌语气 |
| 改首屏按钮 | CTA 一致性、埋点 |
| 改奖励文案 | 奖励边界、免责声明 |
| 改奖励类型 | 奖励规则、风控、人工复审 |
| 改任务数量 | 游戏规则、难度、埋点 |
| 改分享卡 | 分享合规、品牌、奖励表达 |
| 改 CTA 链接 | 链接授权、埋点、安全 |
| 改 Agent 策略 | `runtime_boundaries`、日志和风控 |
| 改模板 | 全量重新验证 |

补丁机制建议：

| Patch 类型 | 验证重点 |
|---|---|
| `content_patch` | 文案、视觉、任务、分享、免责声明 |
| `rule_patch` | 状态机、奖励、CTA、反作弊、埋点 |
| `agent_policy_patch` | 分群、难度、提示、奖励、CTA、风控 |
| `compliance_patch` | 禁止表达、必需提示、锁定字段 |
| `tracking_patch` | 事件、参数、归因和数据看板 |

## 24. 与 Runtime Agent 的关系

约束系统不仅管生成阶段，也要管 Runtime Agent 的策略执行。

| Runtime 场景 | 约束要求 |
|---|---|
| 动态调难度 | 只能在 `game_rules` 允许范围内 |
| 动态给提示 | 不能误导用户，不能过度打扰 |
| 动态奖励提示 | 不能改变奖励性质 |
| 动态 CTA | 只能在允许状态和授权链接展示 |
| 动态分群 | 不能使用未授权敏感属性 |
| 动态分享话术 | 不能夸大奖励或制造虚假传播 |
| 异常用户处理 | 不能绕过反作弊 |
| A/B 实验 | 必须记录版本、实验组和效果 |

运行时验证有两种方式：

| 方式 | 说明 |
|---|---|
| 发布前静态校验 | 验证 `agent_policy` 中所有允许策略 |
| 运行时决策校验 | 每次 `runtime_decision` 应用前检查是否越界 |

MVP 阶段可以先做静态校验和关键决策日志，不一定一开始就做复杂实时拦截。

## 25. 不同模板的验证重点

### 25.1 竞猜 / 预测模板

| 验证项 | 重点 |
|---|---|
| 内容 | 不能变成投资建议或收益预测 |
| 题目 | 不能暗示确定性涨跌 |
| 奖励 | 使用积分、徽章、抽奖资格，不承诺收益 |
| CTA | 引导了解、入群或学习，不直接诱导投资 |
| 规则 | 题目数、计分、答案解释、结果页完整 |
| Agent 策略 | 不能因为用户高分就推荐交易动作 |
| 埋点 | 每题正确率、提示使用、结果页 CTA |

### 25.2 空投任务模板

| 验证项 | 重点 |
|---|---|
| 内容 | 不保证获得空投 |
| 奖励 | 表达为活动资格、抽奖机会或积分 |
| 任务 | 不能强制骚扰式分享或违规刷量 |
| 风控 | 钱包、设备、频次、任务完成质量 |
| CTA | 入群、绑定、查看进度必须授权 |
| 隐私 | 钱包和社媒连接需要授权说明 |
| Agent 策略 | 不能给异常用户更宽松路径 |

### 25.3 跑酷模板

| 验证项 | 重点 |
|---|---|
| 内容 | 收集物不能暗示真实收益 |
| 规则 | 速度、障碍、失败、复活和得分完整 |
| 奖励 | 高分奖励要有上限和反作弊 |
| 分享 | 高分分享不能夸大奖励 |
| Agent 策略 | 难度调整不能造成不可玩或故意诱导付费 |
| 埋点 | 开始、失败点、复活、完赛、分享、CTA |

### 25.4 塔防模板

| 验证项 | 重点 |
|---|---|
| 内容 | 风险、防守、资产等表达不能夸大项目能力 |
| 规则 | 波次、敌人、资源、胜利和失败明确 |
| 奖励 | 防守成功奖励不能变成真实收益承诺 |
| Agent 策略 | 失败补救不能强制转化 |
| 风控 | 异常分数和异常操作频率 |

### 25.5 射击模板

| 验证项 | 重点 |
|---|---|
| 内容 | 目标、命中和奖励表达不误导 |
| 规则 | 命中、连击、失误、时间和分数完整 |
| 风控 | 异常点击频率和异常命中率 |
| CTA | 高分后可以引导分享或入群，但不能承诺收益 |
| Agent 策略 | 目标速度和命中容错在范围内 |

### 25.6 画线 / 路径规划模板

| 验证项 | 重点 |
|---|---|
| 内容 | 路径不能被描述为确定收益路径 |
| 规则 | 起点、终点、障碍、评分和失败条件完整 |
| 提示 | 不能直接替用户完成全部决策 |
| 奖励 | 完成路径奖励需要边界说明 |
| CTA | 完成后引导下一步，不强制跳转 |

### 25.7 模拟经营模板

| 验证项 | 重点 |
|---|---|
| 内容 | 经济增长不能暗示投资回报 |
| 规则 | 资源、升级、事件、回合和目标完整 |
| 奖励 | 虚拟资源和真实奖励边界清晰 |
| Agent 策略 | 动态事件不能制造虚假紧迫感 |
| 埋点 | 资源增长、升级、任务完成、复访、CTA |

## 28. 示例：币价竞猜模板验证

| 模块 | 原始内容 | 验证结果 | 处理 |
|---|---|---|---|
| 首屏标题 | 猜中 BTC 明日价格，稳赚奖励 | Critical | 阻止发布 |
| 奖励文案 | 赢 100 USDT | High | 改为积分或抽奖资格 |
| 题目 | 判断 BTC 明天必涨还是必跌 | High | 改为行情知识挑战 |
| CTA | 立即买入 | Critical | 改为加入社区了解活动 |
| 规则 | 答对即发真实 Token | High | 要求人工复审和风控 |
| Agent 策略 | 高分用户推荐交易 | Critical | 删除策略 |
| 免责声明 | 缺失 | High | 强制补充 |

安全版本方向：

| 模块 | 建议表达 |
|---|---|
| 标题 | 完成 BTC 行情知识挑战，解锁活动积分 |
| 奖励 | 完成挑战可获得积分和抽奖资格，奖励以官方规则为准 |
| CTA | 加入社区查看活动进度 |
| 免责声明 | 本活动仅用于互动教育，不构成投资建议，不保证任何收益 |

## 29. 示例：空投任务模板验证

| 模块 | 原始内容 | 验证结果 | 处理 |
|---|---|---|---|
| 奖励文案 | 完成任务必中空投 | Critical | 阻止发布 |
| 任务 | 邀请 50 人必得奖励 | High | 要求明确反作弊和规则 |
| 钱包采集 | 未说明用途 | High | 强制补充授权说明 |
| 分享卡 | 免费领取高额 Token | High | 改为活动资格表达 |
| 风控 | 缺失 | High | 阻止发布 |
| CTA | 连接钱包领取 | High | 检查授权、链接和规则 |

安全版本方向：

| 模块 | 建议表达 |
|---|---|
| 奖励 | 完成任务可获得活动积分和空投资格抽选机会 |
| 任务 | 完成指定社区任务并通过校验后进入活动名单 |
| 风控 | 限制重复钱包、重复设备和异常完成速度 |
| 隐私 | 钱包地址仅用于活动资格校验 |

## 30. 与数据复盘的关系

约束验证结果也要进入数据复盘，不只是生成阶段的报告。

| 数据 | 用途 |
|---|---|
| 哪些规则最常命中 | 优化 Brief、模板默认值和前台提示 |
| 哪些问题最常阻止发布 | 优化模板设计和 KOL 教育 |
| 哪些自动修复被接受 | 沉淀安全表达库 |
| 哪些人工审核被驳回 | 强化规则和负样本 |
| 哪些警告上线后带来风险 | 提升风险等级 |
| 哪些模板风险最高 | 调整模板推荐和默认风控 |
| 哪些 KOL 容易触发风险 | 更新 `kol_context` 和审核策略 |

复盘要回答：

1. 是模板默认值导致风险，还是 KOL 输入导致风险？
2. 是内容生成问题，还是规则生成问题？
3. 是 Agent 策略越界，还是边界定义不清？
4. 是风控过严导致误伤，还是风控太弱导致滥用？
5. 哪些规则应该升级，哪些规则应该降级为警告？

## 31. MVP 实施建议

### 31.1 P0 先做

| 模块 | 原因 |
|---|---|
| `validation_report` 基础结构 | 所有生成结果必须有验证结果 |
| Schema Validator | 先保证对象完整和可执行 |
| 禁止表达规则 | 收益承诺、投资建议、必中空投、真实奖励误导 |
| 奖励边界 | MVP 默认虚拟积分、徽章、资格、抽奖机会 |
| CTA 一致性 | 防止目标和转化路径冲突 |
| 游戏规则校验 | 状态机、奖励、CTA、埋点、反作弊 |
| Agent 策略边界 | 不允许突破 `game_rules` 和合规规则 |
| 风控基础规则 | 重复钱包、设备、异常速度、异常点击 |
| 审计日志 | 记录拦截、修复、人工放行 |

### 31.2 P1 再做

| 模块 | 原因 |
|---|---|
| 品牌资产校验 | 提升项目方信任 |
| 渠道规则扩展 | 适配 X、Telegram、Discord、广告平台 |
| 自动修复引擎 | 降低 KOL 修改成本 |
| 人工审核队列 | 支撑高风险活动发布 |
| 负样本库 | 把失败案例沉淀成规则 |
| 风险评分 | 根据 KOL、奖励、渠道和目标动态分级 |
| Patch 局部校验 | 支持 KOL 二次编辑 |

### 31.3 P2 平台化后做

| 模块 | 原因 |
|---|---|
| 地区规则引擎 | 不同国家和地区规则不同 |
| 实时 Runtime 拦截 | 对每次 `runtime_decision` 做在线校验 |
| 多语言合规校验 | 支撑全球化投放 |
| 审核工作台 | 支撑项目方、平台、法务和运营协同 |
| 规则效果分析 | 判断哪些规则提升安全但伤害转化 |
| 自动规则升级 | 从负样本和事故中升级规则 |

## 32. 不建议的做法

| 不建议做法 | 问题 |
|---|---|
| 只在 Prompt 里写“不要违规” | 不可控、不可审计、不可版本化 |
| 只做关键词过滤 | 无法识别语义误导和上下文风险 |
| 只检查最终页面 | 会漏掉规则、奖励、Agent 策略和数据采集风险 |
| 所有问题都交给人工 | 成本高，速度慢，无法规模化 |
| 所有问题都自动改 | 容易改变营销意图或制造新风险 |
| KOL 可自由删除免责声明 | 风险不可控 |
| Agent 可自由改奖励和 CTA | 可能为了转化越过边界 |
| 没有审计日志 | 出现问题无法追责和复盘 |
| 高风险奖励没有反作弊 | 容易被刷量和滥用 |
| 不记录验证版本 | 后续无法判断哪个版本被批准 |

## 33. 结论

约束与合规验证是 Agentic Playable 从“AI 生成 demo”走向“可发布产品”的关键环节。

它要回答五个问题：

| 问题 | 对应机制 |
|---|---|
| 这个 Playable 能不能上线？ | `validation_report` 和 `publish_status` |
| 哪些内容不能说？ | `compliance_constraints` 和 Content Validator |
| 哪些规则不能被突破？ | `game_rules`、Rule Validator、`runtime_boundaries` |
| 哪些奖励和 CTA 有风险？ | Reward Validator、CTA Validator、Risk Scorer |
| 出问题后能不能追溯？ | Audit Log、版本记录、人工复审记录 |

MVP 阶段最重要的是：

1. 先把约束做成规则中心，而不是散落在 Prompt 里。
2. 先检查结构、内容、奖励、CTA、游戏规则和 Agent 策略边界。
3. 对收益承诺、投资建议、必中空投、真实奖励误导设置一票否决。
4. 对 KOL 修改和 Agent 策略更新做局部验证。
5. 每次通过、拦截、自动修复和人工放行都必须留痕。

这样，Airvana 的 Agentic Playable 才能在保持生成效率的同时，具备可发布、可运营、可复盘、可监管的产品能力。
