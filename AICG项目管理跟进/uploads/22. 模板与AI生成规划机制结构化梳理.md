# 模板与 AI 生成规划机制结构化梳理

## 1. 核心定义

模板与 AI 生成规划机制，是把用户目标、生成模式和 RAG 上下文，转成可执行 Playable 蓝图的环节。

它解决的问题是：

Airvana 既要支持模板生成，又要支持 AI 生成，但最终都必须落到可验证、可构建、可运营的结构化 schema。

核心产物：

| 产物 | 说明 |
|---|---|
| `template_schema` | 模板结构、字段、规则边界 |
| `playable_blueprint` | AI 生成或混合生成的玩法蓝图 |
| `template_config_draft` | 关键变量草案 |
| `schema_mapping_result` | AI 蓝图映射到模板 schema 的结果 |

## 2. 所处位置

| 上游 | 当前环节 | 下游 |
|---|---|---|
| `generation_mode`、`campaign_goal`、`retrieval_context` | 模板 / AI 生成规划 | 内容、玩法、规则与策略生成 |

## 3. 业务目标

| 目标 | 说明 |
|---|---|
| 统一生成入口 | 模板生成和 AI 生成进入同一产物链路 |
| 保证可构建 | 所有方案都能被 Builder 消费 |
| 控制自由度 | AI 创意必须落到结构化字段 |
| 支持推荐 | 根据目标和上下文推荐模板 |
| 支持扩展 | 后续能加入更多玩法类型 |

## 4. 生成模式与规划方式

| 生成模式 | 规划方式 |
|---|---|
| `template_based` | 直接读取模板 schema，生成 `template_config_draft` |
| `ai_assisted_template` | AI 先理解目标，再推荐模板和预填字段 |
| `ai_generated_playable` | AI 生成玩法草案，再映射到已有或新 schema |
| `hybrid` | AI 生成活动方案，模板承接玩法结构 |

## 5. 输入数据

| 输入 | 用途 |
|---|---|
| `campaign_goal` | 判断玩法服务什么目标 |
| `generation_mode` | 决定规划路径 |
| `kol_context` | 决定 KOL 专属表达和模板适配 |
| `project_context` | 决定项目资产和主题 |
| `retrieval_context` | 提供模板、案例、合规知识 |
| `asset_inventory` | 判断能否支持某些模板 |
| `risk_profile` | 限制高风险玩法 |

## 6. 关键 Agent

| Agent | 职责 |
|---|---|
| Template Agent | 推荐和读取模板 schema |
| Blueprint Agent | 生成玩法蓝图 |
| Schema Mapping Agent | 把 AI 蓝图映射到模板结构 |
| Feasibility Agent | 判断资产、成本、风险是否可行 |
| Planning Critic | 检查玩法规划是否服务目标 |

## 7. Playable 蓝图结构

| 字段 | 说明 |
|---|---|
| `playable_type` | 竞猜、空投、跑酷、塔防等 |
| `campaign_goal` | 服务的营销目标 |
| `core_loop` | 用户核心操作循环 |
| `scene_flow` | 页面和游戏状态流 |
| `task_chain` | 任务链 |
| `reward_pattern` | 奖励节奏 |
| `cta_path` | 转化路径 |
| `share_mechanism` | 分享机制 |
| `agentic_slots` | 可动态调整点 |
| `risk_controls` | 风控要求 |

## 8. Schema 映射逻辑

| AI 蓝图元素 | 映射对象 |
|---|---|
| 玩法类型 | `template_id` |
| 核心循环 | `game_loop_schema` |
| 页面流程 | `scene_schema` |
| 任务链 | `task_schema` |
| 奖励节奏 | `reward_schema` |
| CTA 路径 | `cta_schema` |
| 分享机制 | `share_schema` |
| Agentic 可调项 | `agentic_schema` |
| 风控 | `risk_schema` |

## 9. 决策逻辑

| 判断项 | 结果 |
|---|---|
| 模板完全匹配 | 直接使用现有模板 |
| 模板部分匹配 | 使用模板 + 配置扩展 |
| 没有现成模板 | 生成新蓝图，但进入模板化评审 |
| 风险较高 | 限制玩法自由度 |
| 资产不足 | 降级为轻资产模板 |
| 成本过高 | 推荐更简单模板 |

## 10. 约束边界

| 约束 | 说明 |
|---|---|
| AI 蓝图不能直接发布 | 必须 schema 化 |
| 模板 schema 是构建边界 | Builder 只消费结构化配置 |
| 高风险奖励不能自由生成 | 必须受规则限制 |
| 玩法不能脱离营销目标 | 每个玩法要解释为什么服务目标 |
| 新模板不能跳过验证 | 需要模板评审和模拟测试 |

## 11. MVP 范围

| P0 能力 | 说明 |
|---|---|
| AI 推荐模板 | 根据目标推荐 2-3 个模板 |
| 自动预填字段 | 生成 `template_config_draft` |
| 混合生成 | AI 生成方案，模板承接 |
| Schema 映射 | 检查蓝图是否能构建 |
| 可行性评分 | 资产、成本、风险初筛 |

## 12. P1 / P2 扩展

| 阶段 | 能力 |
|---|---|
| P1 | 新模板草案生成、模板变体生成 |
| P2 | 自动模板抽象、跨行业模板迁移、复杂玩法规划 |

## 13. 验收标准

| 验收项 | 标准 |
|---|---|
| 可选择 | 用户能选择模板、AI 辅助或混合生成 |
| 可落地 | 所有方案能映射到 schema |
| 可解释 | 系统能说明为什么推荐该模板或蓝图 |
| 可校验 | 下游 Constraint 能检查 |
| 可构建 | Builder 能消费输出 |

## 14. 最终结论

模板与 AI 生成规划，是 Airvana 同时支持稳定生产和 AI 创意的关键。

MVP 阶段不要追求完全自由生成，应该让 AI 负责理解目标和生成方案，让模板 schema 负责承接和约束。
