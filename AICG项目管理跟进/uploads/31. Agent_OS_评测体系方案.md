# Agent OS 评测体系方案

> 本文档为 2026-08 重建稿（原稿遗失），内容依据工作台内既有结构与数据整理，待相关负责人审校。

## 1. 评测目标与原则

Agent OS 的输出直接面向 KOL 传播和品牌方结算，生成质量、合规性和稳定性不能靠"感觉不错"上线。

评测体系回答三个问题：

1. 单个模型 / Agent 在它的任务上是否够好。
2. 整条链路端到端跑出来的 Playable 是否可发布、可玩、可合规。
3. 上线后的业务结果是否证明生成策略有效。

| 原则 | 说明 |
|---|---|
| 评测先于发布 | 评测不过不发版，评测是发布门禁而非事后报告 |
| 分层归因 | 链路结果差时能定位到具体环节和 Agent |
| 数据可复现 | 评测集版本化，同一版本可重复跑 |
| 对抗覆盖 | 不只测正常输入，必须测越狱、注入、违禁诱导 |
| 成本入指标 | 质量提升不能以成本失控为代价 |
| 人机结合 | 机器评测保证覆盖率，人工评审保证判断质量 |

## 2. 评测分层

| 层级 | 对象 | 评什么 | 频率 |
|---|---|---|---|
| L1 单模型 / 单 Agent 能力评测 | Gateway 路由的每类模型、每个 Agent | 任务级质量：抽取准确率、生成合格率、校验召回率 | Prompt / 模型 / 路由变更时 |
| L2 链路级端到端评测 | 一次完整 Agent OS 运行 | 从输入到 `playable_version` 的成功率、质量、延迟、成本 | 每次发版前 + 每日回归 |
| L3 业务结果评测 | 已发布 Playable | 完成率、分享率、CTA 转化、投诉率、Runtime 决策效果 | 上线后持续 |

分层关系：

```
L1 能力评测 ──通过──> L2 链路评测 ──通过──> 发版
                                        │
上线后 L3 业务评测 ──发现问题──> 归因回 L2 / L1 ──> 修复 + 回归集补充
```

各层的典型评测项：

| 层级 | 评测项举例 |
|---|---|
| L1 | 字段抽取模型对 `project_context` 的抽取准确率 |
| L1 | Goal Agent 对营销目标的识别一致率 |
| L1 | Constraint Agent 对违禁样本的拦截召回率 |
| L2 | 标准输入集端到端生成 `playable_version` 的成功率 |
| L2 | 生成的 Playable 通过模拟测试主路径的比例 |
| L3 | Runtime 决策后完成率相对默认策略的提升 |
| L3 | 上线后合规投诉与下架率 |

## 3. 评测集建设

| 评测集 | 内容 | 来源 | 更新机制 |
|---|---|---|---|
| 黄金集 | 覆盖主要模板、生成模式、KOL 类型、品牌类型的标准输入与期望产物 | 真实活动脱敏 + 人工构造 | 每季度评审，版本化管理 |
| 对抗集 | prompt 注入、违禁诱导（涉政 / 涉黄 / 暴恐 / 侵权）、博彩敏感玩法请求、越权指令 | 内容安全团队 + 线上攻击样本回收 | 发现新攻击方式后 48h 内入集 |
| 回归集 | 历史线上事故与被打回的生成案例 | 每次故障与校验失败沉淀 | 修复即入集，只增不删 |

评测集要求：

- 每条样本包含：输入、上下文（`kol_context` / `project_context`）、期望结果或判定规则、所属风险等级。
- 对抗集与负样本库（Negative Examples）打通，校验环节的负样本同时是评测样本。
- 评测集变更走版本管理，评测报告标注所用评测集版本。

## 4. 核心指标体系

| 指标 | 定义与口径 | 目标值 | 所属层级 |
|---|---|---|---|
| 生成质量分 | 黄金集上生成产物经规则 + 模型评审 + 人工抽评的综合得分（0-100） | ≥ 85 | L1 / L2 |
| 合规通过率 | 生成产物一次性通过 Constraint Service 全部校验的比例 | ≥ 90% | L2 |
| 对抗拦截率 | 对抗集样本被安全护栏或校验拦截的比例 | ≥ 99% | L1 / L2 |
| 任务完成率 | 端到端运行成功产出可预览 `playable_version` 的比例 | ≥ 95% | L2 |
| 链路 P95 延迟 | 从确认目标到可预览版本的 P95 耗时 | ≤ 5 分钟 | L2 |
| 单次生成成本 | 一次完整运行的模型调用总成本（按 `llm_call_log` 汇总） | ≤ 预算基线 | L2 |
| 人工介入率 | 需要人工修复才能通过的运行占比（不含固定审核卡点） | ≤ 10% 且逐季下降 | L2 |
| 校验召回率 | 已知违规样本被校验环节拦截的比例 | ≥ 99% | L1 |
| 校验误杀率 | 合规样本被错误打回的比例 | ≤ 5% | L1 |
| 线上事故率 | 上线后因生成质量或合规问题下架的活动占比 | ≤ 1% | L3 |
| Runtime 决策增益 | Agent 动态运营相对默认策略的完成率 / 转化提升 | 为正且显著 | L3 |

口径说明：

- 所有比例类指标分母为对应评测集或统计周期内的全部运行，不做样本剔除。
- 成本口径与 Gateway 的 `cost` 字段一致，按活动、KOL、Agent 三个维度可下钻。
- 人工介入率区分"必需卡点"（发布确认、奖励审核）与"质量兜底"（生成失败人工修），只统计后者。

## 5. 评测流程

### 5.1 上线前门禁

| 步骤 | 内容 | 通过条件 |
|---|---|---|
| 1 | 变更方提交：模型 / Prompt / 路由 / Agent / 模板变更说明 | 变更范围明确 |
| 2 | L1 能力评测：受影响任务跑黄金集 + 对抗集 | 指标不低于当前基线 |
| 3 | L2 链路评测：全量黄金集端到端运行 | 任务完成率、合规通过率、延迟、成本达标 |
| 4 | 回归集全量通过 | 历史问题零复发 |
| 5 | 人工评审抽样 | 高风险类目样本人工确认 |
| 6 | 出具评测报告，附评测集版本 | 报告归档后允许发版 |

### 5.2 线上抽检

- 每日按活动类型分层抽样线上生成结果，跑机审 + 人工抽评。
- 高风险类目（代币激励、抽奖玩法）抽检比例上浮至 100% 机审 + 20% 人工。
- 抽检发现的问题样本 48h 内进入回归集。

### 5.3 定期回归

- 每日定时任务跑核心黄金集子集，监控指标漂移。
- 模型供应商侧变更（模型升级、API 行为变化）触发全量回归。
- 指标连续 3 日劣化超阈值自动告警并冻结相关路由变更。

## 6. 人机协同评审机制

| 角色 | 职责 |
|---|---|
| 机器评审（规则） | Schema、埋点、敏感词、结构完整性等确定性判定 |
| 机器评审（模型即评委） | 文案质量、语气贴合 KOL、创意性打分，Prompt 版本化 |
| 人工评审 | 高风险类目终审、模型评委校准、争议样本仲裁 |
| 合规 / 法务 | 对抗集设计评审、合规判定标准维护 |

校准机制：

- 每月抽样对比模型评委与人工评审的一致率，一致率低于 85% 时重新校准评委 Prompt。
- 人工评审结论回写为标注数据，用于评委改进与回归集扩充。

## 7. 评测基础设施与工具链

| 模块 | 职责 |
|---|---|
| Eval Service | 评测任务调度与执行（Gateway 内已有模块的扩展） |
| 评测集仓库 | 黄金集 / 对抗集 / 回归集的版本化存储 |
| 评测运行器 | 支持单任务评测与端到端链路评测两种模式 |
| 评委服务 | 规则评委 + 模型评委统一接口，评委 Prompt 版本化 |
| 指标看板 | 按层级、任务、模型、Agent 维度展示指标与趋势 |
| 报告生成器 | 发版门禁报告自动生成与归档 |
| 告警服务 | 指标劣化、回归失败、抽检异常告警 |

实现约束：

- 评测调用同样走 AI Gateway，评测成本单独记账，不与业务成本混算。
- 评测环境与生产隔离，评测数据脱敏。

## 8. 与版本发布的联动

| 规则 | 说明 |
|---|---|
| 评测不过不发版 | 门禁任一步骤未达标，发版流程自动阻断 |
| 基线锁定 | 每次发版后当前指标成为新基线，后续变更不得劣化 |
| 灰度联动 | 达标后先灰度发布，灰度期 L3 指标异常自动回滚 |
| 回滚可评测 | 回滚后跑一次链路评测确认恢复 |
| 豁免留痕 | 紧急发版豁免需负责人书面审批，48h 内补跑评测 |

发版状态与评测状态的对应：

| 发版阶段 | 评测要求 |
|---|---|
| 提测 | L1 能力评测通过 |
| 预发 | L2 链路评测 + 回归集通过 |
| 灰度 | 线上抽检加密度，L3 指标监控 |
| 全量 | 灰度期指标达标，报告归档 |

## 9. 演进路线

| 阶段 | 能力 |
|---|---|
| P0 | 黄金集 + 回归集、L2 端到端门禁、核心指标看板、发版阻断 |
| P1 | 对抗集常态化、模型评委上线与校准、线上分层抽检、灰度自动回滚 |
| P2 | 模型效果排行榜驱动路由选择、评测结果自动回写 Memory、跨活动策略 A/B 评测 |

## 10. 最终结论

评测体系是 Agent OS 的质量地基：Gateway 保证调用可控，Constraint 保证单次输出可控，评测体系保证系统整体质量随迭代单调不退化。

三条硬规则必须长期坚持：

1. 评测不过不发版。
2. 线上问题必须沉淀回归集，只增不删。
3. 评测集、评委 Prompt、评测报告全部版本化，任何指标都可复现。
