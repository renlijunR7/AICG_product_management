# 钱包身份识别与用户画像体系结构化梳理

> 状态：目标设计稿（非生产能力说明）  
> 适用范围：Airvana 营销 Agent、Agentic Playable、Web3 Campaign  
> 核心原则：长期身份可延续、授权可撤回、画像可解释、商业权限服务端控制

## 1. 结论

Airvana 可以采用 DID 作为身份凭证与跨平台互操作层，但不应把 DID 直接作为唯一账号、角色权限或资产结算系统。

推荐采用双层身份模型：

| 层级 | 主体 | 职责 |
| --- | --- | --- |
| 平台身份层 | `airvana_uid` | 长期账号主键、账号恢复、租户隔离、角色与权限引用 |
| 可验证身份层 | DID + VC / Attestation | 钱包控制权、资格、KYC 等级、信誉等可验证声明 |

用户可以更换或解绑钱包，但 `airvana_uid` 保持稳定。DID 或凭证的存在不自动授予预算、奖励、CTA、地区、发布、归因或结算权限。

## 2. 核心对象

| 对象 | 建议字段 | 说明 |
| --- | --- | --- |
| 平台用户 | `airvana_uid`、账号状态、租户 | 账号与业务关系的长期主键 |
| 钱包关联 | chain、address_hash、verified_at、revoked_at | 保存地址哈希或必要索引，不保存私钥与助记词 |
| DID | did、method、controller、status | 默认可从钱包控制权派生 `did:pkh`，后续可扩展 |
| 可验证凭证 | type、issuer、claims、expires_at、status | 只存业务所需声明及验证摘要 |
| 同意记录 | purpose、source、version、region、expires_at | 每一种用途独立授权并支持撤回 |
| 画像特征 | feature、value、source、confidence、ttl | 必须有来源、置信度和过期时间 |
| 分群规则 | segment_id、rule_version、contract_version | 规则版本与 Campaign Contract 绑定 |

## 3. 身份建立流程

1. 用户先建立 Airvana 平台身份，生成 `airvana_uid`。
2. 在清晰说明用途、数据源、保存期限后，用户主动连接钱包。
3. 通过一次性 nonce 签名验证用户对钱包的控制权。
4. 建立钱包与 `airvana_uid` 的可撤销关联，并派生或登记 DID。
5. 按 Campaign 需要验证凭证，例如 KYC 等级、地区资格或 Proof of Personhood。
6. 只在用户同意范围内连接公开链上行为、社交渠道和第一方互动事件。
7. 生成可解释受众分群；每次决策记录规则版本、凭证摘要和合同版本。

## 4. 用户画像模型

不建议生成一个不可解释的“综合用户分”。应将三类评分独立保存：

### 4.1 身份质量

- 钱包签名是否有效
- 凭证是否有效、是否过期或撤销
- 账号与钱包关联是否稳定
- 身份证据之间是否冲突

### 4.2 价值潜力

- Agentic Playable 的完玩、复玩、分享与转化行为
- 用户主动选择的兴趣与渠道偏好
- 公开链上协议交互类型与活跃度
- 对不同玩法、内容和奖励形式的响应

价值潜力不等于钱包余额或财富等级，不应用于推断敏感属性。

### 4.3 欺诈风险

- 短期批量创建钱包或异常邀请网络
- 设备、网络、行为节奏的显著冲突
- 奖励领取模式与正常用户偏离
- 凭证重复使用或失效状态

风险评分只能触发限流、补充验证或人工复核；永久封禁必须保留证据、申诉与复核流程。

## 5. 可运营受众分群

| 分群 | 主要信号 | 适用动作 | 限制 |
| --- | --- | --- | --- |
| 高可信活跃用户 | 有效签名、活跃历史、低风险 | 进阶玩法、忠诚度任务 | 不自动提高奖励预算 |
| DeFi / 交易行为人群 | 公开链上交互与授权标签 | 协议教育、模拟交易类 Playable | 不推断财富与风险承受能力 |
| Playable 高参与人群 | 完玩、复玩、分享等第一方事件 | 新玩法推荐、KOL 专属版本 | 必须遵守同意目的 |
| 新钱包 / 低信息人群 | 信号不足 | 探索型内容与冷启动问答 | 不因信息少而判低价值 |
| 疑似女巫或异常群体 | 批量行为、设备与邀请冲突 | 限流、补充验证、人工复核 | 不自动永久封禁 |

## 6. Campaign Contract 必须锁定的内容

| 控制项 | 必须定义 |
| --- | --- |
| 数据来源 | 允许的钱包链、凭证签发方、渠道和第一方事件 |
| 同意范围 | 目的、地区、版本、保存期限、撤回机制 |
| 人群规则 | 可用特征、排除条件、规则版本、最低置信度 |
| 商业约束 | 预算、奖励、CTA、地区、品牌、安全与合规规则 |
| 归因规则 | KOL、渠道、版本、窗口期、重复触点处理 |
| 决策审计 | `campaign_id`、`contract_version`、`playable_id`、规则版本、凭证摘要 |
| 删除与申诉 | 钱包解绑、画像更正、凭证撤销、风险复核和数据删除 |

## 7. 营销 Agent 的可做与不可做

### 可自动执行

- 在合同批准的特征范围内选择受众分群
- 为不同分群推荐玩法、文案、视觉和难度变体
- 生成 KOL 专属 Agentic Playable 版本
- 对隐私安全事件进行漏斗、留存和转化分析
- 在批准边界内淘汰低效变体并生成复盘

### 必须人工审批

- 新增身份数据源或凭证签发方
- 改变用户同意目的、保存期限或地区范围
- 改变高风险人群处置规则
- 涉及 KYC、钱包充值、交易、提现或代币奖励的流程
- 任何预算、奖励、CTA、归因与结算规则变更

### 明确禁止

- 采集或存储私钥、助记词、原始 KYC 文档
- 用 DID 直接授予后台角色或商业权限
- 基于钱包余额推断敏感属性或社会身份
- 将用户画像数据跨品牌或跨租户直接共享
- 在用户撤回同意后继续新增画像或用于新 Campaign

## 8. 事件与归因要求

事件至少绑定：`campaign_id`、`contract_version`、`playable_id`、`build_id`、`config_version`、`kol_id`、`channel`、`privacy_safe_user_id`、`consent_state`。

建议核心事件：

- `wallet_connect_requested`
- `wallet_control_verified`
- `credential_verified`
- `consent_granted`
- `consent_revoked`
- `segment_assigned`
- `playable_started`
- `playable_completed`
- `cta_clicked`
- `conversion_confirmed`
- `risk_review_requested`
- `risk_appeal_resolved`

玩家身份、KOL 归因和品牌结算必须保持为三套独立账本，通过 Campaign 标识关联，不能因钱包相同而合并权限或结算关系。

## 9. 分阶段实施建议

| 阶段 | 范围 | 验收标准 |
| --- | --- | --- |
| Phase 1 | `airvana_uid`、钱包签名、同意记录、第一方事件 | 可连接与解绑；撤回后停止新增画像；事件可审计 |
| Phase 2 | DID、凭证验证、身份质量与欺诈风险分离 | 凭证可过期与撤销；风险结果可申诉 |
| Phase 3 | 身份图谱、可解释分群、Campaign 决策 | 每次分群可追溯到规则、来源与合同版本 |
| Phase 4 | 跨平台凭证、隐私增强证明 | 最小披露；跨平台不暴露原始身份数据 |

## 10. 验收清单

- 用户更换钱包后平台身份与历史仍可恢复
- 钱包解绑和同意撤回有明确入口并即时生效
- 任何 DID 或 VC 都不能绕过服务端权限
- 分群结果可解释到字段来源、规则版本与置信度
- 原始私钥、助记词和 KYC 文件不会进入事件、日志或画像库
- Campaign 预算、奖励、CTA、地区、归因和结算字段保持锁定
- KOL 仍是 Agentic Playable 的创作者、所有者与运营者，Agentic Playable 才是营销 Agent
- LOCAL / DEMO 与生产能力在界面和文档中清晰区分
