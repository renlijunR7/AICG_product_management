# 创作 Brief 生成机制结构化梳理

## 1. 核心定义

创作 Brief 生成，是指系统把 KOL 的营销意图、营销目标、模板选择、关键变量、KOL 画像、项目资料、资产状态和合规边界，整理成一份可执行的生成任务书。

它不是最终 Playable，也不是最终文案，而是给 Brief Agent、Strategy Agent、Generation Agent、Constraint Service 和 Builder 使用的“生成说明书”。

| 不是 | 是 |
|---|---|
| 不是用户随便写的一段 Prompt | 是结构化、可校验、可追踪的生成任务 |
| 不是最终游戏内容 | 是生成游戏内容、规则和策略之前的任务说明 |
| 不是纯文案需求 | 同时包含目标、玩法、奖励、CTA、合规、资产和数据要求 |
| 不是只给模型看的提示词 | 是给多个系统模块共享的中间对象 |

一句话：

**创作 Brief 生成 = 把“用户想做什么”转换成“系统应该如何生成”的结构化任务书。**

## 2. 在完整工作流中的位置

创作 Brief 生成位于“关键变量填写”之后、“内容生成 / 游戏规则生成 / Agent 策略生成”之前。

| 上下游 | 输入 / 输出 | 说明 |
|---|---|---|
| 上游：KOL 身份识别 | `kol_context` | 决定语气、粉丝画像、风险偏好、历史效果 |
| 上游：营销目标选择 | `campaign_goal` | 决定主目标、CTA、核心指标和目标约束 |
| 上游：模板推荐 | `template_schema` | 决定玩法结构、字段边界和可编辑范围 |
| 上游：关键变量填写 | `template_config`、`generation_brief_input` | 决定主题、奖励、任务、难度、分享、合规 |
| 当前：创作 Brief 生成 | `generation_brief` | 把上游信息组织成可执行任务 |
| 下游：内容生成 | `content_assets` | 生成首屏、任务、题目、结果页、分享卡等内容 |
| 下游：规则生成 | `game_rules` | 生成玩法规则、奖励规则、胜负条件和反作弊边界 |
| 下游：Agent 策略生成 | `agent_policy` | 生成动态难度、奖励、提示、CTA 和分群策略 |
| 下游：约束验证 | `validation_report` | 检查生成任务和产物是否合规、可玩、可追踪 |
| 下游：H5 构建 | `playable_version` | Builder 组装成可预览、可发布版本 |

## 3. 为什么需要创作 Brief

关键变量虽然已经结构化，但它们仍然是“字段”，不是“创作任务”。Brief 的作用是把字段转成有方向、有边界、有执行顺序的生成说明。

| 没有 Brief 的问题 | Brief 解决什么 |
|---|---|
| AI 只看到一堆字段，不知道创作重点 | 明确创作目标、用户对象和生成优先级 |
| 内容生成和规则生成各做各的 | 统一文案、玩法、奖励、CTA 和数据要求 |
| 合规要求容易遗漏 | 把禁止表达和免责声明写入生成边界 |
| 生成结果不可解释 | Brief 记录为什么这样生成 |
| 后续复盘无法追踪原因 | Brief 可以和版本、数据、Agent 决策关联 |
| KOL 二次编辑难以局部更新 | Brief 能定位改的是目标、玩法、文案还是奖励 |

Brief 的核心价值是：让生成链路从“自由发挥”变成“受控创作”。

## 4. Brief 与其他对象的区别

| 对象 | 作用 | 谁使用 |
|---|---|---|
| `campaign_goal` | 说明这次活动要达成什么 | Brief Agent、Strategy Agent、数据看板 |
| `template_schema` | 说明这个模板能怎么生成、哪些字段可改 | Builder、Constraint Service、Generation Agent |
| `template_config` | 说明当前这次活动填了哪些变量 | Builder、Strategy Agent、Generation Agent |
| `generation_brief` | 说明应该如何创作这次 Playable | 多个 Agent 和验证服务 |
| `content_assets` | 生成后的文案、题目、图片提示、分享卡内容 | Builder、发布服务 |
| `game_rules` | 玩法、胜负、奖励、反作弊规则 | Builder、Runtime Agent、Constraint Service |
| `agent_policy` | 运行时动态策略 | Runtime Agent、Analytics |

简单区分：

| 环节 | 问题 |
|---|---|
| 关键变量填写 | 用户想做什么 |
| 创作 Brief 生成 | 系统应该怎么创作 |
| 内容生成 | 具体写什么、展示什么 |
| 规则生成 | 用户怎么玩、怎么赢、怎么拿奖励 |
| Agent 策略生成 | 上线后怎么动态调整 |

## 5. Brief 生成的输入

### 5.1 必需输入

| 输入 | 来源 | 用途 |
|---|---|---|
| `kol_context` | KOL 身份识别 | 确定 KOL 语气、粉丝画像、历史偏好 |
| `campaign_goal` | 营销目标选择 | 确定主目标、CTA、核心指标 |
| `template_schema` | 模板推荐 / 模板库 | 确定模板边界、字段结构和玩法能力 |
| `template_config` | 关键变量填写 | 确定本次活动具体参数 |
| `asset_inventory` | 项目和 KOL 资产库 | 确定能使用哪些 Logo、头像、题库、图标、角色 |
| `compliance_constraints` | 约束服务 / 项目方规则 | 确定不能说什么、不能做什么 |

### 5.2 可选输入

| 输入 | 用途 |
|---|---|
| `project_context` | 项目介绍、卖点、行业、活动背景 |
| `audience_profile` | 粉丝地域、语言、兴趣、Web3 熟悉度 |
| `performance_history` | KOL 历史开始率、完成率、分享率、转化率 |
| `channel_context` | X、Telegram、TikTok、Discord、广告投放等渠道 |
| `campaign_reference` | 项目方提供的活动资料、竞品案例、风格参考 |
| `template_memory` | 该模板历史上表现好的变量组合 |
| `kol_memory` | 该 KOL 过去喜欢或不喜欢的表达方式 |

## 6. Brief 生成的核心任务

Brief Agent 不是直接写完整游戏，而是做 8 件事。

| 任务 | 说明 |
|---|---|
| 目标翻译 | 把营销目标翻译成创作方向 |
| 用户翻译 | 把目标用户翻译成难度、语气、解释程度 |
| 模板翻译 | 把模板结构翻译成可生成模块 |
| 内容规划 | 决定要生成哪些文案、题目、任务和反馈 |
| 玩法规划 | 给 Strategy Agent 提供玩法结构方向 |
| 奖励规划 | 明确奖励表达、触发条件和风险边界 |
| CTA 规划 | 明确 CTA 位置、语气和触发时机 |
| 约束注入 | 把合规、品牌、奖励和数据要求写入 Brief |

## 7. Brief 输出结构

`generation_brief` 建议包含以下结构。

| 模块 | 字段 | 作用 |
|---|---|---|
| 基础信息 | `brief_id`、`campaign_id`、`template_id`、`version` | 版本追踪 |
| 目标说明 | `primary_goal`、`secondary_goal`、`target_action` | 明确创作目标 |
| 用户说明 | `target_audience`、`audience_level`、`audience_motivation` | 明确给谁玩 |
| KOL 表达 | `kol_tone`、`kol_identity_hook`、`fan_label` | 明确 KOL 专属感 |
| 项目说明 | `project_name`、`core_message`、`proof_points` | 明确项目表达 |
| 模板说明 | `template_type`、`core_loop`、`scene_plan` | 明确玩法结构 |
| 内容任务 | `copy_tasks`、`question_tasks`、`share_tasks` | 告诉内容生成要产出什么 |
| 规则任务 | `game_rule_tasks`、`reward_rule_tasks` | 告诉规则生成要产出什么 |
| Agentic 任务 | `runtime_strategy_tasks`、`segmentation_tasks` | 告诉策略生成要产出什么 |
| 资产要求 | `required_assets`、`available_assets`、`missing_assets` | 明确素材和降级 |
| 合规边界 | `do_not_claim`、`required_disclaimers`、`risk_notes` | 控制风险 |
| 数据要求 | `target_metrics`、`required_events`、`decision_logs` | 支持复盘 |
| 生成优先级 | `must_have`、`should_have`、`nice_to_have` | 控制 MVP 范围 |
| 输出格式 | `expected_outputs` | 约束下游产物格式 |

## 8. Brief 不是 Prompt，但会生成 Prompt

Brief 是结构化任务书，Prompt 是调用模型时的具体指令。

| 项目 | Brief | Prompt |
|---|---|---|
| 形式 | 结构化对象，可存储可复盘 | 一次模型调用的指令文本 |
| 生命周期 | 贯穿生成、验证、发布、复盘 | 通常只服务一次生成 |
| 使用者 | 多个 Agent、Builder、Constraint Service | 某个模型或工具 |
| 是否可审计 | 应该可审计 | 需要记录但不宜作为唯一真相 |
| 是否给用户看 | 可摘要展示 | 一般不直接展示 |

推荐机制：

1. `generation_brief` 先生成。
2. 系统根据 Brief 为不同 Agent 生成不同 Prompt。
3. 内容生成、规则生成、策略生成分别执行。
4. 产物回写并接受 Constraint Service 检查。

## 9. Brief 生成流程

完整流程建议如下：

1. 读取 `campaign_goal`，确定主目标和目标动作。
2. 读取 `kol_context`，确定 KOL 语气、粉丝画像、历史偏好。
3. 读取 `template_schema`，确定模板结构和可生成模块。
4. 读取 `template_config`，确定本次活动的关键变量。
5. 读取 `asset_inventory`，确认可用素材和缺失素材。
6. 读取 `compliance_constraints`，确认硬性边界。
7. Brief Agent 生成结构化 `generation_brief`。
8. Constraint Service 对 Brief 做前置校验。
9. 如有冲突，返回用户修改关键变量或使用平台默认修正。
10. Brief 通过后，分发给内容生成、规则生成和策略生成模块。

## 10. 不同模板的 Brief 重点

### 10.1 竞猜 / 预测模板

| Brief 模块 | 重点 |
|---|---|
| 创作目标 | 通过判断题、预测题或知识题完成教育、拉新或转化 |
| 用户对象 | 新手要降低术语密度，专业用户可增强判断深度 |
| 内容任务 | 生成题目、选项、正确/错误反馈、结果分型 |
| 玩法任务 | 题目数量、难度递进、计分规则、结果页 |
| Agentic 任务 | 动态调整题目难度、提示强度、CTA 时机 |
| 合规边界 | 不能承诺收益，不能构成投资建议 |
| 数据要求 | 题目完成率、正确率、流失点、CTA 点击 |

### 10.2 空投任务模板

| Brief 模块 | 重点 |
|---|---|
| 创作目标 | 通过任务链推动入群、注册、领取资格或分享 |
| 用户对象 | 区分新手、项目粉丝、羊毛用户、高意向用户 |
| 内容任务 | 生成任务说明、奖励说明、进度反馈、规则说明 |
| 玩法任务 | 任务顺序、完成条件、奖励触发、反作弊校验 |
| Agentic 任务 | 根据完成进度调整提示和 CTA，根据风险调整验证 |
| 合规边界 | 奖励以官方规则为准，不保证获得空投或收益 |
| 数据要求 | 任务完成、入群点击、分享、异常行为 |

### 10.3 跑酷模板

| Brief 模块 | 重点 |
|---|---|
| 创作目标 | 用短时间挑战完成拉新、品牌曝光或分享 |
| 用户对象 | 短视频用户、泛娱乐用户、低耐心用户 |
| 内容任务 | 生成首屏、道具说明、结果等级、分享卡 |
| 玩法任务 | 角色、赛道、障碍、收集物、终点反馈 |
| Agentic 任务 | 动态调整速度、障碍密度、奖励提示和 CTA |
| 合规边界 | 收集物和奖励不能暗示实际收益 |
| 数据要求 | 开始率、完赛率、收集率、分享率 |

### 10.4 塔防模板

| Brief 模块 | 重点 |
|---|---|
| 创作目标 | 用防守和升级表达项目能力、风险防护或生态建设 |
| 用户对象 | 游戏用户、项目深度用户、社区用户 |
| 内容任务 | 生成敌人设定、防御塔说明、胜利失败反馈 |
| 玩法任务 | 地图、波次、塔升级、Boss、胜负条件 |
| Agentic 任务 | 动态调整波次难度、失败补救、升级建议 |
| 合规边界 | 风险表达要准确，不能夸大项目能力 |
| 数据要求 | 波次流失、升级选择、胜利率、CTA 点击 |

### 10.5 射击模板

| Brief 模块 | 重点 |
|---|---|
| 创作目标 | 用即时反馈和击中目标完成激活、娱乐传播或风险教育 |
| 用户对象 | 游戏用户、短视频用户、轻量互动用户 |
| 内容任务 | 生成目标设定、反馈文案、分数等级、分享卡 |
| 玩法任务 | 目标速度、命中反馈、连击奖励、局内道具 |
| Agentic 任务 | 根据命中率调节目标速度、密度和提示 |
| 合规边界 | 奖励和目标表达不能误导 |
| 数据要求 | 命中率、连击、完赛率、分享率 |

### 10.6 画线 / 路径规划模板

| Brief 模块 | 重点 |
|---|---|
| 创作目标 | 把用户旅程、项目流程或任务路径变成互动规划 |
| 用户对象 | 教育型用户、策略型用户、项目新手 |
| 内容任务 | 生成起点、终点、障碍、教育节点、反馈文案 |
| 玩法任务 | 路径规则、评分方式、失败条件、提示 |
| Agentic 任务 | 调整障碍布局、提示节点和教育内容 |
| 合规边界 | 不能把路径描述成确定收益路径 |
| 数据要求 | 路径完成率、失败点、提示使用、CTA |

### 10.7 模拟经营模板

| Brief 模块 | 重点 |
|---|---|
| 创作目标 | 用经营、资源和升级表达项目生态、长期价值和用户参与 |
| 用户对象 | 深度用户、GameFi 用户、社区运营用户 |
| 内容任务 | 生成资源说明、建筑说明、事件文案、增长报告 |
| 玩法任务 | 资源系统、升级路径、任务目标、事件触发 |
| Agentic 任务 | 推荐下一步经营动作、调整资源节奏和复访激励 |
| 合规边界 | 经济表达不能变成投资收益承诺 |
| 数据要求 | 升级路径、资源消耗、复访、长期参与 |

## 11. Brief 的生成策略

### 11.1 信息补全

如果用户填的信息不足，Brief Agent 应该先补全，而不是直接生成弱内容。

| 缺失信息 | 补全方式 |
|---|---|
| 目标用户缺失 | 根据 KOL 粉丝画像推断，并标注置信度 |
| 语气缺失 | 根据 KOL 历史内容或平台默认语气生成 |
| 奖励描述缺失 | 根据营销目标推荐低风险奖励 |
| CTA 缺失 | 根据 `campaign_goal` 自动推荐 |
| 资产缺失 | 标记缺失资产，并选择降级方案 |
| 合规边界缺失 | 使用行业默认合规规则 |

### 11.2 冲突处理

| 冲突 | 处理方式 |
|---|---|
| 目标是社群增长，但 CTA 是购买 | 要求调整 CTA 或将购买作为后置动作 |
| 空投奖励强，但没有反作弊 | Brief 标记高风险并要求补充反作弊 |
| KOL 语气娱乐，但项目方要求严肃合规 | 项目方规则优先，保留轻松但不夸张 |
| 模板需要角色资产，但资产缺失 | 生成占位资产需求或推荐轻量模板 |
| 题目涉及收益预测 | 转成风险识别或知识判断 |

### 11.3 优先级控制

Brief 需要明确什么必须生成，什么可以后续补。

| 优先级 | 内容 |
|---|---|
| Must Have | 首屏、核心玩法、奖励规则、CTA、合规、基础埋点 |
| Should Have | 分享卡、结果分型、动态提示、排行榜 |
| Nice to Have | 复杂动画、多路径剧情、高级 A/B 实验 |

## 12. Brief 生成后的校验

Brief 不是生成完就直接使用，必须先被校验。

| 校验项 | 说明 |
|---|---|
| 目标一致性 | Brief 是否和 `campaign_goal` 一致 |
| 模板一致性 | Brief 是否在 `template_schema` 支持范围内 |
| 字段完整性 | 是否包含必须生成的内容和规则 |
| CTA 合法性 | CTA 是否和目标匹配 |
| 奖励合规 | 奖励是否存在误导或收益承诺 |
| 资产可用性 | 必需资产是否存在或有降级方案 |
| 数据可追踪 | 是否声明必要埋点和关键指标 |
| Agentic 边界 | 运行时策略是否有明确边界 |

校验失败时，不应该直接让模型继续生成，而应该回到关键变量或模板推荐阶段修正。

## 13. Brief 与 KOL 二次编辑

KOL 二次编辑不应该每次重跑整条链路，而应该变成 Brief 的局部 Patch。

| KOL 修改 | 应该更新 Brief 的哪个部分 |
|---|---|
| 改首屏标题 | `copy_tasks`、`kol_tone` |
| 改奖励 | `reward_rule_tasks`、`compliance_constraints` |
| 改 CTA | `target_action`、`primary_cta`、`target_metrics` |
| 改题目数量 | `game_rule_tasks`、`required_events` |
| 改分享卡 | `share_tasks` |
| 改目标用户 | `target_audience`、`difficulty_guidance` |
| 改模板 | 需要重新生成 Brief |

局部更新流程：

1. KOL 修改某个字段。
2. 系统生成 `brief_patch`。
3. Constraint Service 校验 Patch。
4. 只重生成受影响的内容、规则或策略。
5. 生成新的 `playable_version`。

## 14. Brief 示例：空投任务

| 模块 | 示例 |
|---|---|
| 创作目标 | 为 KOL 的 Web3 粉丝生成一个低门槛空投任务 Playable，目标是提升 Telegram 社群增长 |
| 目标用户 | Web3 新手和项目潜在用户，避免复杂术语 |
| 核心玩法 | 用户完成 3 步任务：了解项目、加入 Telegram、完成 3 题知识问答 |
| KOL 表达 | 轻松、福利感、社区感，突出 KOL 专属活动 |
| 奖励表达 | 完成任务后获得白名单抽奖资格，不承诺必中 |
| CTA 策略 | 完成核心任务后引导加入 Telegram |
| 内容任务 | 首屏标题、任务说明、问答题、结果页、分享卡、规则说明 |
| 规则任务 | 任务完成条件、奖励触发、重复参与限制 |
| Agentic 任务 | 对未完成用户加强提示，对异常用户增加验证 |
| 合规边界 | 不承诺收益，不暗示投资回报，奖励以官方规则为准 |
| 数据要求 | 记录开始、任务完成、入群点击、分享、异常行为 |

## 15. Brief 示例：数字货币竞猜

| 模块 | 示例 |
|---|---|
| 创作目标 | 用 3 道轻量竞猜题帮助用户理解项目和市场风险 |
| 目标用户 | Web3 新手用户和 KOL 粉丝 |
| 核心玩法 | 用户回答 3 道判断题，获得结果分型和分享卡 |
| KOL 表达 | 专业但不压迫，像 KOL 在给粉丝做轻量测试 |
| 奖励表达 | 完成后获得积分和抽奖资格 |
| CTA 策略 | 结果页引导加入社群或查看项目资料 |
| 内容任务 | 生成题目、选项、解释、结果分型、分享标题 |
| 规则任务 | 计分规则、结果等级、奖励触发条件 |
| Agentic 任务 | 根据答题表现调整最后一题难度和 CTA 文案 |
| 合规边界 | 不预测收益，不提供投资建议 |
| 数据要求 | 记录每题完成率、正确率、流失点、CTA 点击 |

## 17. 前台是否给用户展示 Brief

完整 Brief 不一定给 KOL 全量展示，但应该展示“Brief 摘要”。

| 展示内容 | 作用 |
|---|---|
| 活动目标 | 确认系统理解对了 |
| 目标用户 | 确认给谁玩 |
| 核心玩法 | 确认玩法方向 |
| 奖励和 CTA | 确认转化路径 |
| 语气和风格 | 确认 KOL 表达 |
| 合规提示 | 告知哪些不能改 |
| 生成清单 | 告诉用户系统接下来会生成什么 |

不建议给用户展示：

| 不展示 | 原因 |
|---|---|
| 内部 Prompt | 容易误解，也不稳定 |
| 复杂策略规则 | 对 KOL 没有必要 |
| 风控模型细节 | 可能被绕过 |
| 全量数据字段 | 会增加认知负担 |

## 18. MVP 实施建议

### 18.1 P0 先做

| 模块 | 要求 |
|---|---|
| Brief 基础结构 | 目标、用户、模板、玩法、奖励、CTA、合规、数据 |
| Brief Agent | 从 `campaign_goal` 和 `template_config` 生成结构化 Brief |
| Brief 校验 | 检查目标、模板、CTA、奖励、合规是否冲突 |
| Brief 摘要 | 给 KOL 看系统理解和生成方向 |
| 下游分发 | 内容生成、规则生成、策略生成统一读取 Brief |
| 版本记录 | Brief 和 Playable 版本绑定 |

### 18.2 P1 再做

| 模块 | 要求 |
|---|---|
| KOL Memory 介入 | 根据 KOL 历史语气和偏好生成 Brief |
| Template Memory 介入 | 使用模板历史最佳实践 |
| Brief Patch | 支持 KOL 二次编辑后的局部更新 |
| 多渠道 Brief | 根据 X、Telegram、TikTok 等渠道调整表达 |
| 复杂模板 Brief | 支持塔防、跑酷、射击、画线 |

### 18.3 P2 平台化后做

| 模块 | 要求 |
|---|---|
| 自动复盘回写 | Diagnosis Agent 判断 Brief 是否选错方向 |
| A/B Brief | 为同一目标生成多个 Brief 变体 |

## 19. 不建议的做法

| 不建议事项 | 原因 |
|---|---|
| 让 KOL 直接写 Prompt | 难以稳定生成和验证 |
| Brief 只写文案方向 | 会漏掉玩法、奖励、CTA、数据和合规 |
| Brief 不做版本记录 | 复盘时无法知道当时为什么这样生成 |
| Brief 和模板 schema 脱节 | Builder 可能无法生成 |
| Brief 不经过校验 | 后续内容生成会放大错误 |
| KOL 每次小改都重跑全链路 | 成本高，也容易引入新错误 |
| Brief 不进入数据闭环 | 无法判断哪类 Brief 更有效 |

## 20. 结论

创作 Brief 生成是 Agentic Playable 从“结构化输入”走向“可执行生成”的关键中间层。

它要解决四个问题：

| 问题 | 解决方式 |
|---|---|
| 用户意图无法直接生成 | 把关键变量组织成可执行任务 |
| 多 Agent 生成方向不一致 | 用统一 Brief 约束内容、规则和策略 |
| 合规和数据容易后补 | 在 Brief 阶段前置合规和埋点要求 |
| 复盘无法解释生成原因 | Brief 绑定版本和数据，支持后续诊断 |

MVP 阶段最重要的是：

1. Brief 必须结构化，不要只是自然语言 Prompt。
2. Brief 必须读取 `kol_context`、`campaign_goal`、`template_schema`、`template_config` 和合规边界。
3. Brief 必须输出内容任务、规则任务、Agentic 策略任务、资产要求和数据要求。
4. Brief 必须通过校验后才能进入生成。
5. Brief 必须和 Playable 版本绑定，方便二次编辑和复盘。

这样，创作 Brief 才能成为 Airvana Agentic Playable 生成链路里的稳定“任务编排层”，而不是一次性的文案提示词。
