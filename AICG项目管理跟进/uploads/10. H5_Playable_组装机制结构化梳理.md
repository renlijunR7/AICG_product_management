# H5 Playable 组装机制结构化梳理

## 1. 核心定义

H5 Playable 组装，是指在内容、规则、Agent 策略和约束验证都完成之后，Builder 把经过验证的结构化对象、模板代码、视觉资产、运行时配置和埋点配置组合成一个可以在浏览器、WebView、Telegram Mini App、广告落地页或社群链接中打开体验的 HTML5 Playable 版本。

它不是重新生成文案，也不是重新设计玩法，而是把前面生成出来的“配置和资产”变成一个真实可运行、可预览、可发布、可追踪、可回滚的产品版本。

| 容易误解 | 正确认知 |
|---|---|
| H5 组装就是写一个网页 | 它是把模板、内容、规则、策略、埋点和版本配置组合成可运行版本 |
| Builder 可以自由决定玩法 | Builder 只能执行 `game_rules`，不能改业务规则 |
| H5 只是前端页面 | 它还包含运行时配置、事件追踪、版本信息和发布参数 |
| 组装后就能直接发布 | 还需要预览、模拟测试、发布参数和渠道检查 |
| KOL 改页面就是改代码 | KOL 改结构化字段或补丁，Builder 重新组装版本 |

一句话：

**H5 Playable 组装 = Builder 把已验证的 `content_assets`、`game_rules`、`agent_policy`、模板代码和埋点配置，打包成一个可运行的 `playable_version`。**

## 2. 在完整工作流中的位置

H5 组装位于约束与合规验证之后、模拟测试和发布之前。

| 阶段 | 输入 | 输出 |
|---|---|---|
| KOL 身份识别 | KOL 注册、社媒、历史 campaign、风险信号 | `kol_context` |
| 营销目标选择 | 目标、CTA、指标、渠道 | `campaign_goal` |
| 模板推荐 | 目标、KOL、资产、渠道 | `template_schema` |
| 关键变量填写 | 主题、奖励、任务、CTA、风格 | `template_config` |
| Brief 生成 | 上游意图和约束 | `generation_brief` |
| 内容生成 | Brief、模板、资产库 | `content_assets` |
| 游戏规则生成 | Brief、模板、内容、目标 | `game_rules` |
| Agent 运营策略生成 | 目标、规则、用户路径、风险 | `agent_policy` |
| 约束与合规验证 | 内容、规则、策略、目标、资产 | `validation_report` |
| H5 Playable 组装 | 通过验证的对象、模板代码、资产 | `playable_version` |
| 模拟测试 | 可运行版本、模拟用户、关键路径 | `simulation_result` |
| 二次编辑 | KOL / 运营补丁 | `config_patch`、新版本 |
| 发布投放 | 通过测试的版本、渠道参数 | `publish_url` |
| 运行时优化 | 用户事件、Agent 策略 | `runtime_decision` |

关键原则：

1. 没有通过 `validation_report` 的对象不能进入正式组装。
2. Builder 不重写业务意图，只做映射、绑定、编译和打包。
3. 每次组装都要生成新的版本快照。
4. 预览版本和发布版本要能区分。
5. 组装结果必须可追踪、可复盘、可回滚。

## 3. H5 组装解决的问题

前面的生成阶段产出的是结构化对象，但用户无法直接体验。H5 组装要把这些对象变成可运行产品。

| 问题 | H5 组装的作用 |
|---|---|
| 文案不知道放哪里 | 按 `template_schema` 映射到页面和组件槽位 |
| 视觉资产无法直接使用 | 处理尺寸、格式、加载路径和降级图 |
| 游戏规则只是配置 | 转成前端状态机、交互逻辑和结算逻辑 |
| Agent 策略无法运行 | 绑定可动态调整的槽位和运行时配置 |
| CTA 无法归因 | 绑定链接、渠道参数和点击事件 |
| 埋点缺失 | 注入基础事件、业务事件和 Agent 决策事件 |
| KOL 无法预览 | 生成 `preview_url` 和可编辑版本 |
| 发布无法追溯 | 生成 `build_manifest` 和版本快照 |

## 4. Builder 的职责边界

### 4.1 Builder 负责什么

| 职责 | 说明 |
|---|---|
| 模板实例化 | 按 `template_schema` 创建具体页面和组件 |
| 内容绑定 | 把 `content_assets` 填入页面、任务、结果、分享和 CTA |
| 视觉绑定 | 绑定 Logo、头像、背景、角色、图标和奖励图 |
| 规则执行 | 把 `game_rules` 转成可运行交互逻辑 |
| Agent 插槽绑定 | 把 `agent_policy` 绑定到允许动态变化的位置 |
| 埋点注入 | 注入曝光、开始、完成、分享、CTA、转化和错误事件 |
| 运行时配置生成 | 生成前端可读取的 `runtime_config` |
| 版本快照 | 记录本次组装使用的所有对象版本 |
| 预览构建 | 生成 KOL / 运营可访问的 `preview_url` |
| 发布准备 | 输出可交给发布服务的构建产物 |

### 4.2 Builder 不负责什么

| 不负责 | 原因 |
|---|---|
| 决定营销目标 | 由 `campaign_goal` 决定 |
| 创作文案和任务 | 由内容生成阶段决定 |
| 设计游戏规则 | 由 `game_rules` 决定 |
| 改变奖励性质 | 由规则和合规边界锁定 |
| 放宽合规要求 | 由 Constraint Service 控制 |
| 自由调整 Agent 策略 | 由 `agent_policy` 和 `runtime_boundaries` 控制 |
| 判断投放效果 | 由数据看板和 Diagnosis Agent 负责 |

Builder 的判断原则：

1. 能映射就组装。
2. 字段缺失就返回缺失报告。
3. 规则不支持就返回不支持报告。
4. 资产不可用就走降级或阻止。
5. 不允许静默忽略关键字段。

## 5. 主要输入

| 输入 | 来源 | Builder 使用方式 |
|---|---|---|
| `template_schema` | 模板库 | 决定页面结构、组件槽位、可编辑字段、规则能力 |
| `template_code` | 模板工程 | 提供前端组件、动画、交互和样式 |
| `template_config` | 关键变量填写 | 决定本次活动的主题、奖励、CTA、难度、任务数量 |
| `content_assets` | 内容生成 | 提供首屏、任务、题目、结果、分享、CTA、免责声明 |
| `visual_assets` | 内容生成 / 资产库 | 提供背景、角色、Logo、头像、图标、奖励图 |
| `game_rules` | 规则生成 | 提供状态机、胜负、得分、奖励、反作弊和 CTA 位置 |
| `agent_policy` | Agent 策略生成 | 提供可动态调整的难度、提示、奖励、CTA、分群策略 |
| `validation_report` | 约束服务 | 决定是否允许组装和哪些模块可用 |
| `tracking_plan` | 数据系统 / 模板规则 | 决定需要注入哪些事件 |
| `channel_config` | 发布服务 / 运营配置 | 决定渠道参数、分享能力和跳转行为 |
| `runtime_flags` | 平台配置 | 控制实验、降级、预览模式和运行时功能 |

## 6. 核心输出

H5 组装的统一输出对象是 `playable_version`。

| 输出对象 | 含义 |
|---|---|
| `playable_version` | 本次可运行 Playable 版本 |
| `preview_url` | KOL、运营、项目方预览链接 |
| `build_manifest` | 本次构建使用的模板、资产、规则、策略和版本快照 |
| `runtime_config` | 前端运行时读取的配置 |
| `tracking_map` | 页面、组件、规则状态和事件的埋点映射 |
| `asset_manifest` | H5 加载所需资产清单 |
| `component_map` | 模板槽位和具体内容的映射 |
| `error_report` | 构建失败或降级原因 |
| `handoff_package` | 交给模拟测试和发布服务的产物集合 |

## 7. `playable_version` 数据结构建议

| 字段 | 类型 | 说明 |
|---|---|---|
| `playable_version_id` | string | Playable 版本 ID |
| `campaign_id` | string | 所属 campaign |
| `kol_id` | string | 所属 KOL |
| `template_id` | string | 使用的模板 |
| `template_version` | string | 模板版本 |
| `build_id` | string | 构建任务 ID |
| `build_status` | enum | building、success、failed、preview、published、archived |
| `source_artifacts` | object | 本次读取的上游对象版本 |
| `content_asset_version` | string | 内容资产版本 |
| `game_rule_version` | string | 规则版本 |
| `agent_policy_version` | string | Agent 策略版本 |
| `validation_report_id` | string | 约束验证报告 |
| `runtime_config_id` | string | 运行时配置 ID |
| `tracking_map_id` | string | 埋点映射 ID |
| `build_manifest_id` | string | 构建清单 ID |
| `preview_url` | string | 预览链接 |
| `publish_url` | string | 发布后链接，可为空 |
| `checksum` | string | 构建校验值 |
| `created_at` | datetime | 创建时间 |
| `created_by` | string | 生成来源，例如 system、KOL、operator |

## 8. `build_manifest` 数据结构建议

`build_manifest` 是版本追溯的核心。它回答“这个 H5 到底由哪些东西组装出来”。

| 字段 | 说明 |
|---|---|
| `build_manifest_id` | 构建清单 ID |
| `playable_version_id` | 对应版本 |
| `template_bundle` | 模板代码包和版本 |
| `source_artifacts` | `template_config`、`content_assets`、`game_rules`、`agent_policy` 等对象版本 |
| `asset_manifest_id` | 资产清单 |
| `runtime_config_id` | 运行时配置 |
| `tracking_map_id` | 埋点映射 |
| `validation_report_id` | 约束验证报告 |
| `feature_flags` | 本次启用的功能开关 |
| `channel_targets` | 目标渠道 |
| `bundle_files` | 生成的文件列表 |
| `bundle_size` | 构建产物体积 |
| `checksum` | 构建校验值 |
| `build_warnings` | 构建警告 |
| `build_errors` | 构建错误 |

没有 `build_manifest`，后续就很难回答：

1. 用户看到的是哪个版本？
2. KOL 修改影响了哪些模块？
3. 哪个规则导致了某个用户路径？
4. 哪个版本可以回滚？
5. 数据看板应该归因到哪个配置？

## 9. `runtime_config` 数据结构建议

`runtime_config` 是 H5 页面运行时读取的配置，它不能是散乱字段。

| 模块 | 内容 |
|---|---|
| `public_config` | 页面可展示的标题、文案、任务、CTA、分享信息 |
| `asset_config` | 图片、音效、动画、字体和降级资源 |
| `rule_config` | 状态、题目、任务、计分、胜负、奖励、CTA 状态 |
| `agent_config` | 可动态调整的槽位、策略 ID、默认策略 |
| `tracking_config` | 事件名、参数、触发位置、上报规则 |
| `compliance_config` | 免责声明、风险提示、锁定文案 |
| `channel_config` | 渠道、分享、跳转、UTM、referral 参数 |
| `experiment_config` | 实验组、版本、变量和分流规则 |
| `fallback_config` | 资产失败、网络失败、策略失败时的降级 |
| `debug_config` | 预览模式、调试面板、日志级别 |

运行时配置原则：

1. 前端读取配置执行，不在前端硬编码业务规则。
2. 预览模式和发布模式配置要区分。
3. 敏感配置不能暴露给前端。
4. Agent 策略只能暴露必要的执行配置，不暴露完整风控逻辑。
5. 配置必须带版本号。

## 10. `tracking_map` 数据结构建议

`tracking_map` 负责把页面、组件、规则状态和用户行为映射到事件。

| 字段 | 说明 |
|---|---|
| `tracking_map_id` | 埋点映射 ID |
| `playable_version_id` | 对应版本 |
| `event_schema_version` | 事件 schema 版本 |
| `global_params` | campaign、KOL、模板、渠道、版本等通用参数 |
| `scene_events` | 页面展示事件 |
| `component_events` | 按钮、卡片、任务、奖励、分享组件事件 |
| `rule_events` | 状态流转、成功、失败、奖励触发事件 |
| `agent_events` | Agent 决策应用和策略版本 |
| `conversion_events` | CTA、注册、入群、领取、购买、预约等事件 |
| `error_events` | 资源加载失败、规则异常、上报失败等事件 |

MVP 必须注入的基础事件：

| 事件 | 触发 |
|---|---|
| `playable_impression` | H5 加载并可见 |
| `playable_start` | 用户点击开始 |
| `scene_view` | 用户进入某个页面或游戏状态 |
| `user_action` | 用户点击、选择、拖拽、射击、画线等 |
| `step_complete` | 完成一个题目、任务、波次或关卡 |
| `reward_view` | 用户看到奖励提示 |
| `reward_granted` | 奖励或资格被触发 |
| `share_click` | 用户点击分享 |
| `cta_view` | 用户看到 CTA |
| `cta_click` | 用户点击 CTA |
| `conversion` | 用户完成目标动作 |
| `drop_off` | 用户在关键节点流失 |
| `agent_decision_applied` | Runtime Agent 策略被应用 |
| `build_error` | 运行时发生构建或配置错误 |

## 11. 标准组装流程

| 步骤 | 动作 | 输出 |
|---|---|---|
| 1. 读取验证报告 | 确认 `validation_report` 允许组装 | 构建准入结果 |
| 2. 锁定对象快照 | 锁定模板、内容、规则、策略、配置版本 | `source_artifacts` |
| 3. 选择模板渲染器 | 根据 `template_id` 选择 H5 模板代码 | 模板实例 |
| 4. 映射组件槽位 | 把页面、组件和字段映射到 `template_schema` | `component_map` |
| 5. 绑定内容资产 | 注入标题、任务、题目、结果、CTA、分享文案 | 内容绑定结果 |
| 6. 绑定视觉资产 | 注入 Logo、头像、背景、角色、图标、奖励图 | `asset_manifest` |
| 7. 编译游戏规则 | 把 `game_rules` 转成前端状态机和交互逻辑 | `rule_config` |
| 8. 绑定 Agent 策略 | 把动态槽位和默认策略注入运行时配置 | `agent_config` |
| 9. 注入埋点 | 将事件绑定到页面、组件和规则状态 | `tracking_map` |
| 10. 注入合规提示 | 添加免责声明、活动规则和风险提示 | `compliance_config` |
| 11. 生成运行时配置 | 合并公开配置、规则、资产、渠道和降级策略 | `runtime_config` |
| 12. 构建 H5 产物 | 生成 HTML、JS、CSS、资源包和配置文件 | bundle |
| 13. 生成预览链接 | 部署到预览环境或静态资源服务 | `preview_url` |
| 14. 生成构建清单 | 记录所有输入、输出、警告和校验值 | `build_manifest` |
| 15. 交给模拟测试 | 把可运行版本交给测试链路 | `handoff_package` |

## 12. 组装前准入条件

H5 组装不能直接读取未验证对象。

| 条件 | 是否必须 | 说明 |
|---|---:|---|
| `validation_report` 存在 | 必须 | 没有验证报告不允许正式构建 |
| `publish_status` 可继续 | 必须 | blocked 或 review 未通过不能构建发布版 |
| `template_schema` 完整 | 必须 | 没有 schema 无法映射槽位 |
| `template_code` 可用 | 必须 | 没有模板代码无法生成 H5 |
| `content_assets` 完整 | 必须 | 首屏、任务、结果、CTA 等不能缺失 |
| `game_rules` 可执行 | 必须 | 规则无法执行就无法可玩 |
| `agent_policy` 有边界 | 必须 | Runtime 策略不能越界 |
| `tracking_plan` 完整 | 必须 | 没有数据就无法复盘 |
| 关键视觉资产存在 | 建议 | 可降级，但不能破坏体验 |
| 渠道配置存在 | 建议 | 预览可缺省，发布必须补齐 |

## 13. 模板实例化

模板实例化是 H5 组装的第一步。

| 模板层 | 说明 |
|---|---|
| 页面结构 | 首屏、游戏页、任务页、结果页、分享页、CTA 区 |
| 组件结构 | 按钮、卡片、计分器、进度条、奖励弹窗、排行榜 |
| 规则槽位 | 题目、关卡、波次、障碍、目标、资源、路径 |
| 资产槽位 | 背景、角色、道具、Logo、头像、奖励图 |
| Agentic 槽位 | 可动态调难度、提示、奖励提示、CTA 文案的位置 |
| 埋点槽位 | 每个页面、按钮、状态和关键动作的事件绑定 |
| 锁定槽位 | 项目方、合规和模板不可被 KOL 改动的字段 |

模板实例化失败的常见原因：

| 原因 | 处理 |
|---|---|
| `template_schema` 缺少必填槽位 | 返回 schema 错误 |
| 生成内容和模板槽位不匹配 | 回到内容生成或模板配置 |
| 规则要求模板不支持的交互 | 回到规则生成或换模板 |
| Agent 策略要求不存在的动态槽位 | 降级策略或返回策略不支持 |
| 视觉资产比例不适配 | 自动裁切、降级或要求重生成 |

## 14. 内容绑定

内容绑定负责把 `content_assets` 放进正确的页面和组件。

| 内容类型 | 绑定位置 |
|---|---|
| 首屏标题 | Landing / Start Scene |
| 副标题 | Landing / Start Scene |
| 开始按钮 | Start CTA |
| 任务说明 | Task Scene / Tutorial |
| 题目内容 | Quiz / Prediction Scene |
| 反馈文案 | Success / Fail / Progress Feedback |
| 奖励文案 | Reward Modal / Result Scene |
| 结果等级 | Result Scene |
| 分享文案 | Share Card / Share Dialog |
| CTA 文案 | Result CTA / Floating CTA / Task CTA |
| 免责声明 | Footer / Rule Modal / Reward Modal |

内容绑定原则：

1. 必需内容缺失不能生成半成品。
2. 文案长度超出组件限制时要返回可修复问题。
3. 免责声明不能被省略。
4. CTA 文案必须绑定目标动作和事件。
5. 分享文案必须和分享卡资产一致。

## 15. 视觉资产绑定

视觉绑定不仅是放图，还要保证加载、尺寸、清晰度和降级。

| 资产 | 用途 | 校验 |
|---|---|---|
| 项目 Logo | 首屏、结果页、分享卡 | 清晰、正确、授权 |
| KOL 头像 | 首屏、排行榜、分享卡 | 正确、可加载 |
| 背景图 | 主视觉和游戏场景 | 尺寸、裁切、安全区 |
| 角色图 | 跑酷、射击、塔防等玩法 | 动画帧或静态图可用 |
| 道具图 | 收集物、子弹、障碍、资源 | 与规则对象匹配 |
| 奖励图 | 奖励弹窗、结果页 | 不误导奖励性质 |
| 分享卡图 | 社交传播 | 带版本、KOL、活动信息 |
| 图标 | 任务、按钮、状态反馈 | 风格一致 |

资产处理能力：

| 能力 | 说明 |
|---|---|
| 格式转换 | PNG、JPG、WebP、SVG 等适配 |
| 尺寸压缩 | 控制移动端加载速度 |
| 安全区裁切 | 避免移动端遮挡关键信息 |
| 多倍图 | 支持高清屏 |
| 懒加载 | 非首屏资产延迟加载 |
| 失败降级 | 资产加载失败时使用默认图 |
| CDN 路径 | 发布时替换为稳定资源地址 |

## 16. 游戏规则绑定

Builder 不发明规则，而是执行 `game_rules`。

| `game_rules` 模块 | Builder 处理方式 |
|---|---|
| `state_machine` | 转成前端状态流转 |
| `start_condition` | 绑定开始按钮和初始化状态 |
| `step_rules` | 绑定题目、任务、波次、关卡或路径 |
| `scoring_rules` | 绑定计分器和结果等级 |
| `success_condition` | 绑定通关、完成或达标状态 |
| `fail_condition` | 绑定失败、重试、复活或退出状态 |
| `reward_rules` | 绑定奖励展示和奖励触发 |
| `cta_rules` | 绑定 CTA 出现位置和条件 |
| `anti_abuse_rules` | 绑定异常速度、重复提交、频次限制 |
| `tracking_rules` | 绑定规则状态事件 |

规则绑定失败时，Builder 必须返回错误，而不是静默忽略。

| 失败类型 | 示例 | 处理 |
|---|---|---|
| 状态缺失 | 结果页没有对应状态 | 返回规则错误 |
| 内容缺失 | 第 3 题没有题目内容 | 返回内容错误 |
| 资产缺失 | 跑酷收集物没有图标 | 降级或返回资产错误 |
| CTA 状态不支持 | 规则要求中途弹 CTA，但模板无该槽位 | 返回模板不支持 |
| 奖励触发不明确 | 完成任务后不知道是否发奖励 | 返回规则错误 |
| 反作弊无法执行 | 需要钱包校验但没有钱包模块 | 降级或阻止发布 |

## 17. Agent 策略绑定

Agent 策略绑定是 Agentic Playable 与普通 Playable 的关键差异之一。

| Agent 策略 | H5 绑定方式 |
|---|---|
| 用户分群 | 作为事件维度和策略选择输入 |
| 动态难度 | 绑定速度、题目难度、障碍密度、波次强度等动态槽位 |
| 提示策略 | 绑定提示弹窗、按钮高亮、步骤引导 |
| 奖励提示 | 绑定奖励进度、差一步提示、结果页激励 |
| CTA 策略 | 绑定 CTA 展示条件、文案版本和位置 |
| 分享策略 | 绑定分享卡文案、分享按钮和榜单激励 |
| 风控策略 | 绑定异常用户的验证、限制和降级路径 |
| 实验策略 | 绑定 A/B 版本、曝光记录和实验维度 |
| 决策日志 | 绑定 `agent_decision_applied` 事件 |

Agent 策略绑定原则：

1. 只能绑定 `template_schema` 支持的动态槽位。
2. 只能在 `game_rules` 允许范围内调整。
3. 不能改变奖励性质。
4. 不能改变主目标。
5. 每次策略应用必须可记录。
6. 策略失败时必须降级到默认体验。

## 18. 合规提示和规则说明绑定

通过验证的免责声明和规则说明必须进入 H5，而不是只留在后台报告里。

| 内容 | 绑定位置 |
|---|---|
| 活动规则 | 规则弹窗、Footer、结果页 |
| 奖励说明 | 奖励弹窗、结果页、任务页 |
| 非投资建议 | 首屏 Footer、结果页、规则弹窗 |
| 奖励以官方规则为准 | 奖励区、分享卡、规则弹窗 |
| 数据授权说明 | 钱包连接、社媒连接、注册表单 |
| KOL 合作披露 | 首屏、分享卡或规则弹窗 |
| 地区限制 | 规则弹窗、参与前提示 |

合规提示绑定原则：

1. 必须可见，不应只放在极深层页面。
2. 不能被 KOL 自由删除。
3. 不能被视觉遮挡。
4. 和奖励、CTA、数据采集相关的提示要靠近用户动作。
5. 多语言版本要保持含义一致。

## 20. 移动端和 WebView 适配

H5 Playable 主要在移动端消费，因此组装阶段必须考虑设备约束。

| 适配项 | 要求 |
|---|---|
| 首屏加载 | 关键资源尽量轻，避免白屏 |
| 竖屏体验 | 默认优先竖屏 |
| 安全区 | 适配刘海屏、底部手势区 |
| 触控区域 | 按钮、拖拽、射击、画线区域足够大 |
| 文案换行 | 标题、CTA、奖励说明不能溢出 |
| WebView | 适配 Telegram、App 内 WebView、广告 WebView |
| 低端机 | 动画和资源可降级 |
| 网络慢 | 加载状态、重试和降级资源 |
| 音频策略 | 避免自动播放受限 |
| 横竖屏 | 复杂玩法可提示旋转，但 MVP 优先竖屏 |

H5 不是桌面网页的缩小版，组装时要默认以手机屏幕、单手操作和短会话为核心。

## 21. 预览版本与发布版本

预览版本和发布版本应该分开。

| 对比项 | 预览版本 | 发布版本 |
|---|---|---|
| 目标 | 给 KOL、运营、项目方确认体验 | 面向真实用户 |
| URL | `preview_url` | `publish_url` |
| 数据 | 可打测试标记 | 进入正式数据看板 |
| 调试信息 | 可显示 Debug 信息 | 不显示 |
| 分享 | 可禁用或标记测试 | 正式分享 |
| CTA | 可走测试链接 | 正式链接 |
| 版本状态 | preview | published |
| 缓存 | 可频繁刷新 | 稳定缓存 |

预览模式必须避免污染正式数据。

## 22. 构建状态管理

| 状态 | 含义 |
|---|---|
| `queued` | 等待构建 |
| `building` | 正在组装 |
| `build_failed` | 构建失败 |
| `preview_ready` | 预览版本可访问 |
| `simulation_running` | 模拟测试中 |
| `simulation_failed` | 模拟测试失败 |
| `ready_to_publish` | 可发布 |
| `published` | 已发布 |
| `archived` | 已归档 |
| `rolled_back` | 已回滚 |

状态变化需要记录：

1. 谁触发。
2. 使用了哪些对象版本。
3. 发生了哪些警告。
4. 是否进入模拟测试。
5. 是否允许发布。

## 23. 错误与降级机制

H5 组装阶段必须能清楚区分错误类型。

| 错误类型 | 示例 | 处理 |
|---|---|---|
| Schema 错误 | 模板缺少必填槽位 | 阻止构建 |
| 内容错误 | 必需文案缺失 | 返回内容缺失报告 |
| 资产错误 | 背景图无法加载 | 使用默认图或阻止 |
| 规则错误 | 状态机死循环 | 阻止构建 |
| 策略错误 | Agent 策略引用不存在槽位 | 降级到默认策略 |
| 埋点错误 | CTA 没有点击事件 | 阻止发布版构建 |
| 合规错误 | 必需免责声明未绑定 | 阻止构建 |
| 渠道错误 | 发布渠道缺少参数 | 预览可继续，发布阻止 |
| 性能错误 | 包体过大、首屏太慢 | 警告或要求优化 |

降级优先级：

1. 不影响规则和合规的视觉资源可以降级。
2. Agent 动态策略可以降级为默认策略。
3. 分享能力可以降级为复制链接。
4. 埋点、奖励、CTA、规则和合规提示不能静默降级。

## 24. 性能与加载要求

Playable 的体验通常很短，加载慢会直接影响开始率。

| 指标 | MVP 建议 |
|---|---|
| 首屏可见 | 尽量控制在 2 秒内 |
| 首次可交互 | 尽量控制在 3 秒内 |
| 包体大小 | 控制核心包体，非关键资源懒加载 |
| 图片体积 | 使用压缩和合适格式 |
| 动画复杂度 | 移动端优先流畅 |
| 失败重试 | 资源和配置加载失败可重试 |
| Loading | 清晰展示加载状态 |
| 错误页 | 有友好降级和回退路径 |

性能数据也应该被记录到 `tracking_map` 或运行日志中，方便判断开始率下降是内容问题还是加载问题。

## 25. 安全与防篡改

H5 发布后会被外部访问，因此需要基础安全设计。

| 安全项 | 说明 |
|---|---|
| 配置签名 | 防止关键运行时配置被篡改 |
| 版本校验 | 页面加载时确认配置版本和资源版本 |
| CTA 链接白名单 | 防止跳转到未授权链接 |
| 资源域名白名单 | 防止加载未知资源 |
| 埋点参数校验 | 防止伪造 campaign、KOL、版本 |
| 奖励触发校验 | 奖励最终以服务端或验证服务为准 |
| 反作弊参数 | 关键行为需要服务端校验 |
| 敏感配置隔离 | 不把风控规则细节暴露给前端 |

MVP 阶段至少要保证：奖励不能只靠前端判断，CTA 链接不能任意注入，版本和事件参数不能完全信任客户端。

## 26. 与模拟测试的关系

H5 组装完成后，应该交给模拟测试，而不是直接发布。

| 模拟测试项 | 说明 |
|---|---|
| 可打开 | `preview_url` 能正常访问 |
| 可开始 | 用户能点击开始 |
| 可完成 | 用户能完成核心路径 |
| 可失败 | 失败状态能正确出现 |
| 可重试 | 重试或返回路径可用 |
| 可领奖励 | 奖励展示和触发符合规则 |
| 可分享 | 分享按钮和分享卡可用 |
| 可 CTA | CTA 可见、可点击、可追踪 |
| 可埋点 | 关键事件都能上报 |
| 可 Agent | 动态策略能按边界运行或降级 |
| 可降级 | 资源或策略失败时体验不崩 |

模拟测试输出 `simulation_result`，如果失败，可能回到 H5 组装、规则生成、内容生成或约束验证。

## 27. 与发布服务的关系

发布服务负责把通过测试的版本变成正式可传播链接。

| H5 组装输出 | 发布服务使用方式 |
|---|---|
| `playable_version` | 确认发布版本 |
| `build_manifest` | 确认产物和版本快照 |
| `runtime_config` | 发布运行时配置 |
| `tracking_map` | 接入正式数据上报 |
| `asset_manifest` | 上传或绑定 CDN 资源 |
| `preview_url` | 项目方确认 |
| `simulation_result` | 发布前质量门槛 |
| `channel_config` | 生成渠道链接 |

发布后输出：

| 输出 | 含义 |
|---|---|
| `publish_url` | 正式传播链接 |
| `share_url` | 分享链接 |
| `channel_links` | 不同渠道的归因链接 |
| `qr_code` | 社群或线下传播二维码 |
| `published_version` | 已发布版本记录 |
| `rollback_version` | 可回滚版本 |

## 28. 与 KOL 二次编辑的关系

KOL 在预览页修改内容后，Builder 应该根据补丁做局部重组装。

| KOL 修改 | 影响范围 | 处理 |
|---|---|---|
| 改标题 | 内容绑定 | 生成 `content_patch`，重绑首屏 |
| 改按钮文案 | CTA 组件 | 校验 CTA 后重绑 |
| 改分享文案 | 分享卡 | 重生成或重绑分享卡 |
| 改奖励文案 | 奖励和合规 | 重新合规验证后重绑 |
| 改任务数量 | 规则和页面 | 重新生成 `game_rules` 后构建 |
| 改视觉风格 | 视觉资产 | 重新生成或选择资产后重绑 |
| 改 CTA 链接 | 渠道和埋点 | 重新验证链接和 tracking |
| 改 Agent 策略 | 运行时配置 | 重新校验 `agent_policy` 后构建 |

版本策略：

1. 每次预览修改生成新 `playable_version`。
2. 小改动可以复用模板和规则，只更新对应 manifest。
3. 影响规则、奖励、CTA、合规的改动必须重新验证。
4. 已发布版本不能被原地覆盖，应生成新版本。
5. KOL 可以回到历史预览版本。

## 30. Builder API 边界建议

| `handoffToSimulation` | 交给模拟测试 |
| `handoffToPublish` | 交给发布服务 |

API 设计原则：

1. 构建任务异步执行。
2. 每次构建都绑定输入版本。
3. 构建失败返回结构化错误。
4. 预览和发布使用不同状态。
5. 发布前必须读取模拟测试结果。

## 31. 前台 KOL 看到什么

KOL 不需要看到 Builder 的技术细节，只需要看到可理解的预览和问题。

| 前台模块 | KOL 看到的内容 |
|---|---|
| 构建中 | 正在生成你的互动页面 |
| 预览链接 | 可打开体验的版本 |
| 手机预览 | 竖屏真实比例预览 |
| 可编辑项 | 标题、任务、奖励文案、分享卡、CTA 文案等 |
| 锁定项 | 项目方、合规、奖励性质、主 CTA 目标 |
| 问题提示 | 哪些内容缺失、哪些规则不支持 |
| 重新生成 | 修改后重新生成预览 |
| 发布准备 | 当前版本是否可发布 |

KOL 的核心体验应该是：

1. 点生成。
2. 等待可运行预览。
3. 在预览里改少量关键字段。
4. 系统重新组装版本。
5. 通过后进入发布。

## 32. 后台系统真正发生什么

| KOL 前台动作 | 后台系统动作 |
|---|---|
| 点击生成 | 创建 build job |
| 等待预览 | Builder 锁定对象快照并构建 H5 |
| 打开预览 | 访问 `preview_url`，加载 `runtime_config` |
| 点击开始 | 触发 `playable_start` |
| 完成游戏 | 触发规则状态和奖励逻辑 |
| 点击分享 | 触发分享组件和 `share_click` |
| 点击 CTA | 触发 `cta_click` 和渠道归因 |
| 修改标题 | 生成 `content_patch` 并重新构建 |
| 修改任务 | 可能重新生成规则并重新验证 |
| 点击发布 | 交给模拟测试和发布服务 |

## 33. 与数据反馈的关系

H5 组装决定数据能不能被正确采集。

| 数据问题 | 组装阶段原因 |
|---|---|
| 无法计算开始率 | 没有注入 `playable_impression` 或 `playable_start` |
| 无法找流失点 | 页面和规则状态没有 `scene_view`、`drop_off` |
| 无法评估题目 | 题目 ID 没有进入事件参数 |
| 无法评估奖励 | 奖励曝光和触发没有区分 |
| 无法评估 CTA | `cta_view` 和 `cta_click` 缺失 |
| 无法评估 Agent | 没有记录 `agent_decision_applied` |
| 无法归因 KOL | 事件缺少 `kol_id` 或 `kol_ref` |
| 无法归因版本 | 事件缺少 `playable_version_id` |

所以 Builder 不是只影响页面体验，也直接影响后续数据复盘和 Agentic 优化。

## 34. MVP 实施建议

### 34.1 P0 先做

| 模块 | 原因 |
|---|---|
| 单模板 Builder | 先跑通一个高价值模板 |
| `playable_version` 数据结构 | 建立版本概念 |
| `build_manifest` | 保证可追溯 |
| `runtime_config` | 前端可按配置运行 |
| `tracking_map` | 保证数据闭环 |

| 内容绑定 | 首屏、任务、结果、CTA、分享 |

## 35. 不建议的做法

| 不建议做法 | 问题 |
|---|---|
| Builder 直接读自然语言 Brief | 不稳定，无法追踪 |
| Builder 静默忽略缺失字段 | 容易生成半成品 |
| 前端硬编码业务规则 | KOL 修改和数据复盘会失控 |
| 每次小改都全量重生成 | 成本高，速度慢 |
| 已发布版本原地覆盖 | 无法回滚和归因 |
| 预览数据混入正式数据 | 看板污染 |
| 不记录构建清单 | 后续无法审计 |
| Agent 策略不降级 | 策略失败会破坏体验 |
| 埋点发布后再补 | 数据断层无法修复 |
| 只关注视觉，不关注规则和事件 | 不能形成 Agentic 闭环 |

## 36. 结论

H5 Playable 组装是 Airvana 从“AI 生成配置”走向“真实可投放产品”的工程转换层。

它要回答五个问题：

| 问题 | 对应机制 |
|---|---|
| 这些内容放到哪里？ | `template_schema` 和 `component_map` |
| 用户怎么玩？ | `game_rules` 和 `rule_config` |
| Agent 怎么动态调整？ | `agent_policy` 和 `agent_config` |
| 数据怎么回收？ | `tracking_map` 和事件注入 |
| 版本怎么追溯？ | `playable_version` 和 `build_manifest` |

MVP 阶段最重要的是：

1. 先让一个模板可以从配置稳定组装成可运行 H5。
2. `content_assets`、`game_rules`、`agent_policy` 必须结构化，Builder 不读散文。
3. 每次构建都要生成 `playable_version`、`runtime_config`、`tracking_map` 和 `build_manifest`。
4. 预览、模拟测试、发布要分层，不要生成后直接投放。
5. Builder 要能返回结构化错误，避免生成不可解释、不可追踪、不可运营的半成品。

这样，Agentic Playable 才能从“好看的 demo”变成一个可以被 KOL 预览、编辑、发布、投放、追踪和持续优化的营销产品。
