# Airvana Agent OS 关键业务链路结构化文档目录

## 1. 文档目标

这份文档用于把 Airvana Agent OS 的关键业务链路拆成一组可独立展开的结构化文档。

它解决的问题不是单点技术选型，而是：

Airvana 要如何通过 RAG、多模型路由、多 Agent、约束系统、Builder、Runtime、数据反馈和 Memory，完成 Agentic Playable 从生成到运营的完整业务闭环。

推荐把后续文档拆成 13 份。

每一份文档都围绕一个关键业务环节，明确：

| 结构项 | 说明 |
|---|---|
| 核心定义 | 这个环节到底是什么 |
| 业务目标 | 它解决什么业务问题 |
| 输入 | 上游传入什么数据 |
| 输出 | 下游需要什么产物 |
| 关键 Agent | 哪些 Agent 参与 |
| 关键系统 | 哪些平台模块支撑 |
| 关键数据对象 | 需要沉淀哪些结构化对象 |
| 决策逻辑 | 系统如何判断和选择 |
| 约束边界 | 哪些事情不能做 |
| MVP 范围 | 第一阶段先做什么 |
| P1 / P2 扩展 | 后续如何增强 |
| 验收标准 | 怎么判断这个环节成立 |

## 2. 总体业务链路

Airvana Agent OS 的核心链路建议定义为：

| 顺序 | 业务环节 | 关键产物 |
|---|---|---|
| 1 | KOL / 项目方输入与身份上下文 | `kol_context`、`project_context` |
| 2 | 目标识别与生成模式选择 | `campaign_goal`、`generation_mode` |
| 3 | RAG 上下文检索与知识注入 | `retrieval_context` |
| 4 | 多模型路由与 AI Gateway | `model_route_plan`、`llm_call_log` |
| 5 | 多 Agent 任务编排 | `agent_task_plan`、`workflow_state` |
| 6 | 模板 / AI 生成规划 | `template_schema`、`playable_blueprint` |
| 7 | 内容、玩法、规则与策略生成 | `content_assets`、`game_rules`、`agent_policy` |
| 8 | 约束、合规与质量验证 | `validation_report` |
| 9 | H5 Builder 构建与版本管理 | `playable_version` |
| 10 | 模拟测试、预览与 KOL 二次编辑 | `simulation_result`、`config_patch` |
| 11 | 发布投放与媒体连接器 | `publish_url`、`channel_links` |
| 12 | Runtime Agent 动态运营 | `runtime_decision`、`agent_decision_applied` |
| 13 | 数据反馈、Memory 与模板更新 | `diagnosis_result`、`kol_memory`、`template_memory` |

## 3. 建议生成的 13 份结构化文档

### 3.1 文档 1：KOL / 项目方输入与身份上下文机制

建议文件名：

`17. KOL_项目方输入与身份上下文机制结构化梳理.md`

核心问题：

Airvana 如何把 KOL 登录、社媒连接、项目方输入、历史行为、粉丝画像和风险信息，转成可被 Agent OS 使用的上下文。

文档结构建议：

| 模块 | 内容 |
|---|---|
| 核心定义 | 什么是 `kol_context` 和 `project_context` |
| 业务目标 | 识别谁在创作、给谁传播、为哪个项目服务 |
| 数据来源 | 注册信息、社媒连接器、历史 campaign、项目资料、上传资产 |
| 输入对象 | KOL 基础信息、项目基础信息、资产、社群链接 |
| 输出对象 | `kol_context`、`project_context`、`audience_profile`、`risk_profile` |
| Agent | Identity Agent、Project Context Agent |
| RAG | KOL Knowledge、Project Knowledge |
| 约束 | 不采集未授权敏感数据，不做未经确认的身份推断 |
| MVP | KOL 信息、项目名、头像、社媒链接、粉丝标签、项目卖点 |
| 验收 | 能稳定生成后续目标选择和模板推荐所需上下文 |

关键产物：

| 产物 | 作用 |
|---|---|
| `kol_context` | 后续生成 KOL 专属语气、分享卡、房间名 |
| `project_context` | 后续生成项目表达、题目、奖励说明 |
| `audience_profile` | 判断粉丝适合什么玩法和渠道 |
| `risk_profile` | 判断是否需要加强合规和风控 |

### 3.2 文档 2：目标识别与生成模式选择机制

建议文件名：

`18. 目标识别与生成模式选择机制结构化梳理.md`

核心问题：

用户要做 Agentic Playable 时，平台如何判断营销目标，以及走模板生成、AI 辅助模板、AI 生成玩法草案还是混合生成。

文档结构建议：

| 模块 | 内容 |
|---|---|
| 核心定义 | `campaign_goal` 和 `generation_mode` 的关系 |
| 业务目标 | 先确定为什么做，再决定怎么生成 |
| 输入 | `kol_context`、`project_context`、用户自然语言意图 |
| 输出 | `campaign_goal`、`generation_mode`、`goal_constraints` |
| Agent | Goal Agent、Generation Mode Agent |
| 决策逻辑 | 根据目标、资产、风险、KOL 熟练度选择生成模式 |
| 生成模式 | `template_based`、`ai_assisted_template`、`ai_generated_playable`、`hybrid` |
| 约束 | MVP 不做完全自由生成，必须落到结构化模板或 schema |
| MVP | 默认使用 `ai_assisted_template` 和 `hybrid` |
| 验收 | 每次生成都有明确目标、模式和成功指标 |

关键判断：

| 情况 | 推荐模式 |
|---|---|
| 用户知道要用哪个模板 | `template_based` |
| 用户只知道营销目标 | `ai_assisted_template` |
| 用户有创新玩法想法 | `ai_generated_playable` 后结构化 |
| MVP 默认 | `hybrid` |

### 3.3 文档 3：RAG 上下文检索与知识注入机制

建议文件名：

`19. RAG_上下文检索与知识注入机制结构化梳理.md`

核心问题：

Agent 在生成前应该检索哪些知识，如何避免只靠模型自由发挥。

文档结构建议：

| 模块 | 内容 |
|---|---|
| 核心定义 | RAG 在 Airvana Agent OS 中的作用 |
| 业务目标 | 给 Agent 提供 KOL、模板、项目、合规、案例和历史效果上下文 |
| 输入 | `kol_context`、`campaign_goal`、`generation_mode` |
| 输出 | `retrieval_context`、`source_trace` |
| RAG 库 | KOL、Template、Project、Compliance、Case、Performance |
| Agent | Retrieval Agent、Context Composer |
| 检索策略 | 精确检索、语义检索、规则检索、负样本检索 |
| 约束 | 检索结果必须可追溯，不能把未审核内容注入生成 |
| MVP | KOL RAG、Template RAG、Compliance RAG、Negative Examples |
| 验收 | 每次生成能说明使用了哪些上下文 |

RAG 库拆分：

| RAG 库 | 用途 |
|---|---|
| KOL Knowledge | KOL 语气、粉丝、历史活动 |
| Template Knowledge | 模板 schema、玩法、可编辑字段 |
| Project Knowledge | 项目信息、品牌、卖点、活动规则 |
| Compliance Knowledge | 禁止表达、免责声明、平台规则 |
| Case Knowledge | 成功案例和失败案例 |
| Performance Knowledge | 历史数据、渠道效果、策略效果 |

### 3.4 文档 4：多模型路由与 AI Gateway 机制

建议文件名：

`20. 多模型路由与_AI_Gateway_机制结构化梳理.md`

核心问题：

不同 AI 任务应该调用什么模型，如何控制成本、质量、速度、失败重试和审计。

文档结构建议：

| 模块 | 内容 |
|---|---|
| 核心定义 | 什么是 Airvana AI Gateway 和 Model Router |
| 业务目标 | 统一模型调用，避免 Agent 直接散乱调用模型 |
| 输入 | `agent_task`、任务类型、上下文长度、风险等级 |
| 输出 | `model_route_plan`、`llm_response`、`llm_call_log` |
| 路由维度 | 任务类型、质量等级、成本、延迟、合规风险 |
| Agent | Model Router、Cost Controller、Fallback Handler |
| 关键能力 | 模型选择、Prompt 管理、重试、降级、日志、评估 |
| 约束 | 高风险内容必须走强校验，不能只用低成本模型 |
| MVP | 3 类模型路由：抽取、小创作、强推理 |
| 验收 | 所有模型调用都可追踪、可降级、可评估 |

任务路由建议：

| 任务 | 模型策略 |
|---|---|
| 字段抽取 | 小模型 |
| 目标识别 | 小模型 + 规则 |
| 策略生成 | 强推理模型 |
| 文案生成 | 创意模型 |
| 规则校验 | 规则引擎 + 模型辅助 |
| 复盘诊断 | 强推理模型 |
| Embedding | 专用向量模型 |

### 3.5 文档 5：多 Agent 任务编排机制

建议文件名：

`21. 多Agent任务编排机制结构化梳理.md`

核心问题：

Airvana 如何把一个“生成 Agentic Playable”的大任务拆给多个 Agent，并保证顺序、状态、失败回退和产物一致。

文档结构建议：

| 模块 | 内容 |
|---|---|
| 核心定义 | 什么是 Workflow Orchestrator |
| 业务目标 | 管理多 Agent 协作，保证从输入到发布闭环可控 |
| 输入 | `campaign_goal`、`generation_mode`、`retrieval_context` |
| 输出 | `agent_task_plan`、`workflow_state`、`artifact_manifest` |
| Agent | Brief、Strategy、Generation、Rule、Policy、Constraint、Builder、Runtime、Diagnosis |
| 编排方式 | 顺序编排、并行生成、校验回退、人工确认 |
| 状态管理 | Draft、Generated、Validated、Built、Published、Running、Reviewed |
| 约束 | Agent 不能跨越权限直接修改线上版本 |
| MVP | 先做线性编排，不做复杂自治协作 |
| 验收 | 每一步有输入、输出、状态和错误处理 |

关键对象：

| 对象 | 作用 |
|---|---|
| `workflow_state` | 记录当前生成进度 |
| `artifact_manifest` | 记录每个环节产物 |
| `agent_task_plan` | 记录任务分配 |
| `approval_checkpoint` | 记录需要人工确认的节点 |

### 3.8 文档 8：约束、合规与质量验证机制

建议文件名：

`24. 约束合规与质量验证机制结构化梳理.md`

核心问题：

AI 生成结果如何被验证，如何防止不可发布、不可追踪、不可合规的内容进入构建和发布。

文档结构建议：

| 模块 | 内容 |
|---|---|
| 核心定义 | Constraint Service 在 Agent OS 中的角色 |
| 业务目标 | 保证生成结果可发布、可玩、可追踪、可审计 |
| 输入 | `content_assets`、`game_rules`、`agent_policy` |
| 输出 | `validation_report`、`repair_suggestion` |
| Agent | Constraint Agent、Critic Agent、Repair Agent |
| 校验类型 | Schema、规则、合规、品牌、安全、风控、埋点 |
| 约束库 | Constraint Registry、Negative Examples、Audit Log |
| 回退机制 | 校验失败回到对应生成环节 |
| MVP | Schema Validator + Rule Validator + Compliance Checklist |
| 验收 | 不通过验证不能进入 Builder |

核心原则：

| 原则 | 说明 |
|---|---|
| 约束优先 | 模型输出必须服从产品规则 |
| 可解释 | 每个失败原因要能定位 |
| 可修复 | 能生成结构化修复建议 |
| 可审计 | 所有校验有日志 |

| 约束 | 不能用单次低样本结果污染全局模板 |
| MVP | 基础漏斗 + Agent 决策复盘 + KOL / Template Memory |
| 验收 | 下一次生成能读取历史经验并改进默认值 |

## 6. MVP 最先应该展开的文档

如果资源有限，不建议 13 份同时深写。

建议先写 6 份 P0 文档：

| 优先级 | 文档 | 原因 |
|---|---|---|
| P0 | 目标识别与生成模式选择机制 | 决定模板生成和 AI 生成如何进入同一流程 |
| P0 | RAG 上下文检索与知识注入机制 | 决定 Agent 是否有业务上下文 |
| P0 | 多 Agent 任务编排机制 | 决定整个链路能否跑通 |
| P0 | 约束、合规与质量验证机制 | 决定是否能安全发布 |
| P0 | H5 Builder 构建与版本管理机制 | 决定是否能生成真实可玩的 H5 |
| P0 | 数据反馈、Memory 与模板更新机制 | 决定是否形成业务闭环 |

P1 再展开：

| 优先级 | 文档 | 原因 |
|---|---|---|
| P1 | 多模型路由与 AI Gateway | 降低成本和提升稳定性 |
| P1 | Runtime Agent 动态运营机制 | 让 Agentic 真正发生在线上 |
| P1 | 发布投放与媒体连接器机制 | 支持规模化分发 |

P2 再展开：

| 优先级 | 文档 | 原因 |
|---|---|---|
| P2 | KOL / 项目方输入与身份上下文机制 | 更细的画像和长期资产 |
| P2 | 模板 / AI 生成规划机制 | 支持更多生成模式 |
| P2 | 内容、玩法、规则与策略生成机制 | 支持更多玩法和内容形态 |
| P2 | 模拟测试、预览与 KOL 二次编辑机制 | 提升质量和 KOL 使用体验 |

## 7. 最终结论

Airvana Agent OS 的结构化文档不应该按“技术组件”单独拆，例如只写 RAG、只写模型路由、只写多 Agent。

更合理的拆法是按业务链路拆：

1. 输入是谁。
2. 目标是什么。
3. 用什么生成方式。
4. 检索什么知识。
5. 调用什么模型。
6. 哪些 Agent 执行。
7. 生成什么结构化产物。
8. 如何校验。
9. 如何构建。
10. 如何发布。
11. 如何运行时运营。
12. 如何诊断。
13. 如何回写 Memory 和模板。

这样文档体系才能支撑完整闭环，而不是停留在“RAG + 多模型 + 多 Agent”的技术堆叠。
