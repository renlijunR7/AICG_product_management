# Agent OS 架构总体方案

> 本文档为 2026-08 重建稿（原稿遗失），内容依据工作台内既有结构与数据整理，待相关负责人审校。

## 1. 定位与核心定义

Agent OS 是 Airvana 平台的智能中枢，是支撑 Agentic Playable 从生成到运营全生命周期的操作系统层。

它不是单个 AI 功能，而是把 RAG、多模型路由、多 Agent 编排、约束系统、Builder、Runtime、数据反馈和 Memory 组织成一个可控、可审计、可持续学习的整体。

核心命题：

Airvana 要如何让 KOL 和项目方用自然语言输入，稳定产出可发布、可合规、可追踪、可运营的 Playable 营销游戏，并让每次投放的数据变成下一次生成的经验。

| 角色 | Agent OS 提供什么 |
|---|---|
| KOL | 低门槛生成专属 Playable，二次编辑，分成可追溯 |
| 品牌方 / Web3 项目方 | 品牌安全可控的营销活动，结算口径可信 |
| 平台运营 | 全链路状态可见、可干预、可复盘 |
| 合规与风控 | 生成前有约束、发布前有卡点、运行中有边界 |

## 2. 总体分层架构

Agent OS 自上而下分为七层：

```
┌─────────────────────────────────────────────┐
│ L1 接入层        KOL 工作台 / 项目方入口 / API │
├─────────────────────────────────────────────┤
│ L2 编排层        Workflow Orchestrator        │
│                  状态机 · 任务队列 · 审核卡点   │
├─────────────────────────────────────────────┤
│ L3 Agent 运行时  Goal / Strategy / Generation │
│                  Rule / Policy / Constraint   │
│                  Builder / Runtime / Diagnosis│
├─────────────────────────────────────────────┤
│ L4 模型路由层    AI Gateway · Model Router    │
│                  Prompt Registry · Cost 控制  │
├─────────────────────────────────────────────┤
│ L5 记忆与知识层  RAG 六库 · KOL Memory        │
│                  Template Memory · 负样本库   │
├─────────────────────────────────────────────┤
│ L6 工具与连接器  H5 Builder · 媒体连接器      │
│                  归因服务 · 结算 · 钱包/KYC    │
├─────────────────────────────────────────────┤
│ L7 观测与治理    审计日志 · 评测 · 权限        │
│                  成本看板 · 合规约束库         │
└─────────────────────────────────────────────┘
```

各层职责与关键对象：

| 层 | 职责 | 关键对象 |
|---|---|---|
| 接入层 | 身份识别、意图输入、资产上传 | `kol_context`、`project_context` |
| 编排层 | 任务拆分、状态管理、回退、人工卡点 | `workflow_state`、`agent_task_plan`、`approval_checkpoints` |
| Agent 运行时 | 各环节 Agent 的执行容器与权限边界 | `artifact_manifest` |
| 模型路由层 | 统一模型调用、成本、降级、日志 | `model_route_plan`、`llm_call_log`、`prompt_version` |
| 记忆与知识层 | RAG 检索、经验沉淀、模板更新 | `retrieval_context`、`kol_memory`、`template_memory` |
| 工具与连接器 | 构建、发布、归因、结算等确定性能力 | `playable_version`、`publish_url`、`channel_links` |
| 观测与治理 | 审计、评测、权限、合规约束 | `audit_log`、`validation_trace`、`eval_report` |

分层原则：

- 上层只能通过定义好的接口调用下层，Agent 不能绕过 Gateway 直接调模型。
- 确定性能力（构建、结算、归因）放工具层，不交给模型自由发挥。
- 观测与治理横切所有层，任何 Agent 行为都有日志。

## 3. 关键业务链路串联

Agent OS 的一次完整运行（`agent_os_run_id`）串联 13 个业务环节，对应结构化文档 17-29：

| 顺序 | 环节 | 所属层 | 关键产物 | 对应文档 |
|---|---|---|---|---|
| 1 | KOL / 项目方输入与身份上下文 | 接入层 | `kol_context`、`project_context`、`risk_profile` | 文档 17 |
| 2 | 目标识别与生成模式选择 | Agent 运行时 | `campaign_goal`、`generation_mode` | 文档 18 |
| 3 | RAG 上下文检索与知识注入 | 记忆与知识层 | `retrieval_context`、`source_trace` | 文档 19 |
| 4 | 多模型路由与 AI Gateway | 模型路由层 | `model_route_plan`、`llm_call_log` | 文档 20 |
| 5 | 多 Agent 任务编排 | 编排层 | `agent_task_plan`、`workflow_state` | 文档 21 |
| 6 | 模板 / AI 生成规划 | Agent 运行时 | `template_schema`、`playable_blueprint` | 文档 22 |
| 7 | 内容、玩法、规则与策略生成 | Agent 运行时 | `content_assets`、`game_rules`、`agent_policy` | 文档 23 |
| 8 | 约束、合规与质量验证 | 观测与治理 | `validation_report`、`repair_suggestion` | 文档 24 |
| 9 | H5 Builder 构建与版本管理 | 工具与连接器 | `playable_version`、`tracking_map` | 文档 25 |
| 10 | 模拟测试、预览与 KOL 二次编辑 | Agent 运行时 | `simulation_result`、`config_patch` | 文档 26 |
| 11 | 发布投放与媒体连接器 | 工具与连接器 | `publish_url`、`channel_links` | 文档 27 |
| 12 | Runtime Agent 动态运营 | Agent 运行时 | `runtime_decision`、`agent_decision_applied` | 文档 28 |
| 13 | 数据反馈、Memory 与模板更新 | 记忆与知识层 | `diagnosis_result`、`kol_memory`、`template_memory` | 文档 29 |

链路的三个闭环：

| 闭环 | 路径 | 价值 |
|---|---|---|
| 生成闭环 | 输入 → 目标 → 检索 → 生成 → 校验 → 构建 → 发布 | 保证每个 Playable 可发布、可合规 |
| 运营闭环 | 发布 → Runtime 决策 → 事件回收 → 归因 | 保证线上体验可动态优化且不越界 |
| 学习闭环 | 复盘诊断 → Memory 回写 → 模板更新 → 下一轮生成 | 保证平台随投放次数变强 |

## 4. 关键横切机制

### 4.1 约束优先

模型输出必须服从产品规则。所有生成结果落到结构化 schema，经 Constraint Service 校验后才能进入 Builder；校验失败回到对应生成 Agent 修复，而不是直接放行。

### 4.2 统一产物与追踪

每次运行维护统一总控对象：

| 对象 | 说明 |
|---|---|
| `agent_os_run_id` | 一次完整运行 ID |
| `workflow_state` | 当前工作流状态（created 到 memory_updated 共 14 态） |
| `artifact_manifest` | 全链路产物清单 |
| `model_call_logs` | 模型调用记录 |
| `retrieval_trace` | RAG 检索来源 |
| `validation_trace` | 校验记录 |
| `runtime_trace` | 运行时决策记录 |
| `feedback_trace` | 复盘与更新记录 |

### 4.3 人机协同卡点

| 卡点 | 触发条件 | 确认人 |
|---|---|---|
| 奖励与激励设置 | 涉及代币 / 积分 / 提现 | 运营 + 合规 |
| 品牌内容预审 | 品牌方合作活动 | 品牌方 |
| 发布前确认 | 所有活动 | KOL 或运营 |
| 高风险模板 | 抽奖 / 概率类玩法 | 合规 Agent 预审 + 法务复核 |
| 全局模板更新 | Diagnosis 建议改模板默认值 | 模板中心审核 |

## 5. 设计原则

| 原则 | 含义 | 落地机制 |
|---|---|---|
| 人机协同卡点 | AI 提效，人负责高风险决策 | `approval_checkpoints`，高风险节点强制人工确认 |
| 可回滚 | 任何变更可撤销 | 版本化发布，已发布版本不可原地覆盖，托管操作全留痕可回滚 |
| 租户隔离 | KOL 语料、品牌资产互不可见 | KOL 私有子库隔离，RAG 检索带租户边界 |
| 成本可控 | 模型开销与业务价值匹配 | Gateway 按任务分级路由，Cost Controller 熔断，成本可按活动 / KOL / Agent 统计 |
| 约束优先 | 生成服从规则而非相反 | Constraint Registry + 负样本库，不通过验证不进 Builder |
| 可审计 | 全链路行为可追溯 | 统一日志：模型调用、检索来源、校验、Runtime 决策 |
| 确定性优先 | 能用规则解决的不用模型 | 合规校验规则引擎优先，结算与归因走系统对账 |

## 6. 约束边界

| 约束 | 说明 |
|---|---|
| Agent 不能跳过校验 | 生成后必须进入 Constraint Service |
| Agent 不能直接发布 | 发布需要审核状态 |
| Agent 不能修改已发布版本 | 必须生成新版本 |
| Runtime Agent 不能改核心规则 | 只能在 `game_rules` 边界内动态运营 |
| 模型输出不能当最终事实 | 关键事实必须有 RAG 来源可追溯 |
| 不采集未授权敏感数据 | 身份上下文构建有数据边界 |

## 7. 演进路线

### 7.1 MVP（P0）

| 能力 | 说明 |
|---|---|
| 线性编排 | 顺序流程跑通生成到发布闭环 |
| 3 类模型路由 | 抽取、小创作、强推理 |
| 4 个核心 RAG 库 | KOL、Template、Compliance、Negative Examples |
| Schema + 规则 + 合规校验 | 不通过不进 Builder |
| 固定模板配置驱动构建 | 竞猜 / 空投模板先行 |
| 基础反馈 | 漏斗 + Agent 决策复盘 + KOL / Template Memory |
| 人工卡点 | 发布前、奖励、CTA 高风险点 |

### 7.2 P1

| 能力 | 说明 |
|---|---|
| 并行生成与自动修复 | 文案、视觉、题目并行，校验失败自动修 |
| 多供应商模型路由与自动降级 | 稳定性与成本优化 |
| Runtime 动态运营增强 | 动态难度、奖励节奏、分群策略 |
| 媒体连接器规模化 | X、Telegram、Discord 渠道打通与归因 |

### 7.3 P2

| 能力 | 说明 |
|---|---|
| 自适应编排 | 按活动特征动态选择编排路径 |
| 策略性模型选择 | 基于评测排行榜自动选模型 |
| 跨活动策略复用 | Memory 驱动的策略迁移 |
| 更多生成模式与玩法形态 | `ai_generated_playable` 全面开放 |

## 8. 最终结论

Agent OS 的架构价值不在于堆叠 RAG、多模型、多 Agent 等技术组件，而在于用分层架构和三个闭环把它们组织成业务系统：

1. 编排层保证链路可控。
2. Gateway 保证模型调用可控。
3. 约束系统保证输出可控。
4. Memory 保证平台可学习。
5. 观测治理保证一切可审计。

后续 13 份链路文档（17-29）均是本总纲在各环节的展开，新增机制文档应先在本文档的分层与链路中找到位置，再单独深写。
