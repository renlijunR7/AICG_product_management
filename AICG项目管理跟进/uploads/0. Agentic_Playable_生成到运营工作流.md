# Agentic Playable 从生成到运营工作流

## 1. 核心定义

Agentic Playable 不是“带 AI 聊天的小游戏”，而是一个由 AI 参与生成、验证、发布、运行时调优和复盘优化的营销增长系统。

传统 Playable 的核心是“用户可以互动的广告素材”；Agentic Playable 的核心是“在业务约束内，自动生成内容、调整玩法、选择运营策略、记录数据反馈，并把结果沉淀回模板和 KOL 资产”。

一条完整链路应该覆盖：

| 阶段 | 核心问题 | 产出 |
|---|---|---|
| 模板准备 | 这个 Playable 可以被谁复用、哪些地方能改、哪些地方不能改 | `template_schema`、素材包、规则边界 |
| 创作生成 | KOL 想做什么营销活动，系统如何生成一个可上线版本 | `generation_brief`、`game_rules`、`agent_policy`、H5 版本 |
| 约束验证 | 是否合规、可玩、可追踪、可投放 | `validation_report`、预览链接、埋点清单 |
| 发布投放 | 链接、分享卡、渠道、KOL 房间和归因如何打通 | `publish_url`、`share_card`、渠道参数 |
| 运行运营 | 用户来了以后，系统如何动态调难度、奖励、CTA 和推荐 | `runtime_decision`、分群策略、运营策略 |
| 数据复盘 | 哪些用户在哪一步流失，哪个 Agent 决策有效 | 数据看板、诊断报告 |
| 模板迭代 | 什么经验要沉淀到 KOL 记忆、模板库和下一次生成 | `kol_memory`、模板版本、优化建议 |

## 2. 总体闭环

推荐把工作流理解成 15 个连续步骤：

1. KOL 身份识别
2. 营销目标选择
3. 模板选择
4. 关键变量填写
5. 创作 Brief 生成
6. 文案、视觉、任务内容生成
7. 游戏规则生成
8. Agent 运营策略生成
9. 约束与合规验证
10. H5 Playable 组装
11. 模拟测试
12. KOL 二次编辑
13. 发布投放
14. 运行时动态运营
15. 数据反馈与模板更新

关键原则：KOL 不应该改代码，KOL 应该改结构化字段、创作意图和局部补丁；系统再把这些输入转换成可验证、可发布、可追踪的 Playable 版本。

## 3. 前台工作流：KOL 和运营看到什么

| 步骤 | KOL / 运营操作 | 页面或功能 | 成功标准 |
|---|---|---|---|
| 1. 选择身份与目标 | 选择 KOL 类型、粉丝画像、活动目标 | 创作入口 / Campaign Setup | 系统知道“为谁做、给谁玩、要什么结果” |
| 2. 选择模板 | 从竞猜、盲盒、抽奖、答题、任务闯关等模板中选择 | 模板市场 | 模板适配营销目标，不只是视觉好看 |
| 3. 填写关键变量 | 填币种、主题、奖励、CTA、活动周期、渠道 | 结构化表单 | 所有 P0 字段完整，避免自由文本失控 |
| 4. 生成首版 | 点击生成，得到 Playable 预览 | Preview / Builder | 首屏、玩法、奖励、分享、CTA 都可体验 |
| 5. 二次编辑 | 修改标题、任务、奖励节奏、分享文案、CTA | 可视化编辑器 | 只影响对应模块，不重跑全链路 |
| 6. 发布 | 生成链接、分享卡、KOL 专属房间、渠道参数 | 发布台 | 可传播、可归因、可回收数据 |
| 7. 观察数据 | 看点击、开始、完成、分享、CTA、转化、流失点 | 数据看板 | 不只看总量，也看哪一步为什么掉 |
| 8. 运营优化 | 接受系统建议或手动调整策略 | 运营建议 / Agentic Rules | 能改变难度、奖励、CTA、分群和复投策略 |
| 9. 复盘沉淀 | 保存优秀配置，生成复盘报告 | Campaign Review | 经验进入 KOL 记忆和模板库 |

## 4. 后台系统流：每一步真正发生什么

| 阶段 | 后台动作 | 关键对象 |
|---|---|---|
| 身份识别 | 读取 KOL 历史活动、粉丝画像、行业偏好、风险等级 | `kol_context` |
| 目标解析 | 把“拉新、转化、教育、社群裂变、空投预热”等目标转成系统约束 | `campaign_goal` |
| 模板解析 | 读取模板结构、可编辑字段、锁定字段、Agentic 字段、埋点要求 | `template_schema` |
| Brief 生成 | 将 KOL 输入转成可执行创作任务 | `generation_brief` |
| 策略规划 | 决定玩法结构、任务链、奖励节奏、CTA 位置、分群策略 | `strategy_plan` |
| 内容生成 | 生成首屏文案、题目、剧情、任务、分享卡、反馈文案 | `content_assets` |
| 规则生成 | 生成游戏规则、胜负条件、奖励规则、反作弊边界 | `game_rules` |
| Agent 策略 | 生成运行时可调整的难度、奖励、提示、CTA、推荐策略 | `agent_policy` |
| 约束验证 | 检查合规、品牌、安全、奖励表述、数据埋点和可玩性 | `validation_report` |
| H5 构建 | 把模板、配置、素材、规则和埋点组装成可访问版本 | `playable_version` |
| 模拟测试 | 用模拟用户跑关键路径，检查流失、异常、事件缺失 | `simulation_result` |
| 局部修改 | 将 KOL 编辑转换为补丁，只重建受影响模块 | `config_patch` |
| 发布 | 生成链接、渠道参数、版本号、分享资产 | `publish_url` |
| 运行决策 | 根据用户行为、来源、进度和风险，选择运营动作 | `runtime_decision` |
| 数据回流 | 把事件、结果和 Agent 决策回写到报表和记忆 | `kol_memory`、`template_memory` |

## 5. 哪些部分是 Agentic，哪些不是

| 模块 | 是否 Agentic | 判断标准 |
|---|---:|---|
| 登录、积分、排行榜、基础奖励展示 | 否 | 这是基础游戏系统，不负责自动决策 |
| 模板选择推荐 | 是 | 根据 KOL、目标、粉丝画像自动推荐模板 |
| 首屏标题和利益点生成 | 是 | 根据目标用户与活动目标生成并可测试 |
| 游戏难度动态调整 | 是 | 根据用户表现调整题目、提示、回合长度 |
| 奖励节奏调整 | 是 | 根据完成率、风险和转化目标调整奖励触发 |
| CTA 时机选择 | 是 | 根据用户状态决定何时引导注册、分享、入群或购买 |
| 用户分群与推荐 | 是 | 根据来源、行为、完成度、风险自动分群 |
| 反作弊与异常识别 | 是 | 根据行为特征动态限制刷量、羊毛党和异常流量 |
| 数据看板 | 部分是 | 只展示数据不是 Agentic，自动诊断和给策略建议才是 Agentic |
| 模板版本更新 | 是 | 把复盘结论沉淀到下一次生成策略里 |

一句话判断：只要系统在约束内“自动做运营决策并影响用户体验”，就是 Agentic；只是承载玩法或展示数据，不算 Agentic 核心。

## 6. MVP 最小可落地版本

MVP 不需要一开始支持所有游戏类型。建议先跑通一个高价值模板，例如“数字货币竞猜 / 空投任务 / KOL 专属互动房间”。

### 6.1 MVP 必需输入

| 字段 | 说明 | 为什么重要 |
|---|---|---|
| KOL 身份 | 名称、头像、社媒链接、语气、粉丝标签 | 决定信任感和传播素材 |
| 营销目标 | 拉新、教育、转化、社群增长、空投预热 | 决定玩法和 CTA |
| 目标用户 | 新手、交易用户、社区用户、项目方粉丝 | 决定难度和文案 |
| 模板类型 | 竞猜、答题、抽奖、盲盒、任务链 | 决定核心互动结构 |
| 首屏利益点 | 用户为什么要开始玩 | 直接影响开始率 |
| 玩法变量 | 币种、题目、任务、回合数、难度 | 直接影响完成率 |
| 奖励设置 | 虚拟积分、徽章、排行榜、抽奖资格 | 影响留存和分享 |
| CTA 目标 | 注册、入群、关注、领取、跳转、分享 | 影响最终转化 |
| 分享文案 | KOL 语气、结果反馈、社交炫耀点 | 影响裂变 |
| 合规边界 | 不承诺收益、不误导奖励、不违规收集数据 | 决定能否上线 |

### 6.2 MVP 必需 Agent

| Agent | 职责 | MVP 边界 |
|---|---|---|
| Brief Agent | 解析 KOL 输入和营销目标 | 只支持结构化目标，不依赖长文本自由发挥 |
| Strategy Agent | 生成玩法结构、任务链、奖励节奏、CTA 策略 | 先用规则 + LLM，不做复杂强化学习 |
| Generation Agent | 生成文案、题目、反馈语、分享卡内容 | 输出必须符合模板字段 |
| Constraint Agent | 检查合规、品牌、玩法、奖励、数据埋点 | 对上线有一票否决权 |
| Runtime Agent | 根据用户状态调整难度、提示、奖励、CTA | 先限定在几个可控策略 |
| Diagnosis Agent | 复盘流失、转化和 Agent 决策效果 | 输出运营建议和模板更新建议 |

### 6.3 MVP 必需产出

| 产出 | 作用 |
|---|---|
| H5 Playable 预览链接 | 给 KOL 和运营确认体验 |
| 发布链接 | 用于社媒、广告、社群传播 |
| KOL 专属分享卡 | 让 KOL 更愿意传播 |
| 基础数据看板 | 看到开始率、完成率、分享率、CTA、转化 |
| Agent 决策日志 | 解释系统为什么调整难度、奖励或 CTA |
| 复盘报告 | 指出下一轮该改什么 |
| 模板版本记录 | 保证下一次不是从零开始 |

## 7. 数据闭环：最小颗粒度

Agentic Playable 的数据最小单位不是“今天多少点击”，而是：

一个用户在一个会话里，看到了某个组件或 Agent 决策，采取了某个动作，并产生了某个结果。

可以简化为：

| 维度 | 问题 |
|---|---|
| who | 谁来了：用户、来源、KOL、渠道 |
| where | 在哪一步：页面、场景、组件、任务 |
| what agent changed | Agent 做了什么：调难度、改奖励、换 CTA、给提示 |
| what user did | 用户做了什么：点击、开始、答题、分享、跳转、退出 |
| what happened next | 结果是什么：完成、转化、流失、复玩、异常 |

P0 事件建议：

| 事件 | 用途 |
|---|---|
| `playable_impression` | 看到 Playable |
| `playable_start` | 开始互动 |
| `scene_view` | 进入某个场景 |
| `agent_decision_applied` | Agent 策略生效 |
| `user_action` | 用户关键操作 |
| `step_complete` | 完成关键步骤 |
| `reward_granted` | 发放奖励或资格 |
| `share_click` | 点击分享 |
| `cta_click` | 点击转化按钮 |
| `conversion` | 完成目标转化 |
| `drop_off` | 流失 |

数据看板必须能回答三类问题：

1. 用户在哪一步掉了？
2. 哪个 Agent 决策改善或伤害了结果？
3. 下一轮应该改模板、改内容、改奖励，还是改投放人群？

## 8. 运营阶段拆解

### 8.1 冷启动阶段

冷启动阶段不要追求复杂自动化，目标是验证四件事：

| 目标 | 关键问题 | 指标 |
|---|---|---|
| KOL 愿不愿意发 | KOL 是否认为这个内容符合自己人设 | KOL 发布率、二次编辑次数 |
| 粉丝愿不愿意点 | 首屏和分享卡是否有吸引力 | CTR、开始率 |
| 用户能不能玩完 | 难度、奖励、路径是否合理 | 完成率、流失点 |
| 数据能不能解释 | 是否能定位问题和给出下一步建议 | 事件完整率、诊断可用性 |

冷启动 P0 优化字段：

| 优先级 | 字段 |
|---|---|
| P0 | KOL 房间名、头像露出、首屏标题、首屏按钮、核心利益点 |
| P0 | 模板类型、回合长度、首个奖励、初始任务链 |
| P0 | 结果反馈文案、分享卡、CTA 目标和 CTA 时机 |
| P1 | 用户分群规则、动态难度、提示策略 |
| P1 | 排行榜、粉丝身份、社群裂变机制 |
| P2 | 视觉风格、背景、角色、装饰动效 |

冷启动运营动作：

1. 选 1 个模板、3 到 5 个 KOL、少量用户先测。
2. 每个 KOL 生成专属版本，不要投一个通用链接。
3. 首日重点看开始率、完成率、分享率、CTA 和流失点。
4. 只允许少数运行时策略自动调整，避免不可解释。
5. 复盘后沉淀模板字段和 KOL 偏好。

### 8.2 稳定运营阶段

稳定阶段的目标从“能不能跑通”变成“能不能规模化复用和持续提升”。

| 运营方向 | 动作 |
|---|---|
| 模板运营 | 按行业、目标、玩法、Agentic 等级维护模板库 |
| KOL 运营 | 为 KOL 建立长期素材资产、粉丝画像和活动记忆 |
| 策略运营 | 按不同人群自动选择难度、奖励、CTA、分享话术 |
| 数据运营 | 建立横向对比：不同 KOL、模板、渠道、版本的效果 |
| 复投运营 | 把高转化组合复制到相似 KOL 和相似用户群 |
| 风险运营 | 监控异常流量、奖励滥用、合规风险和品牌风险 |

稳定阶段的核心看板：

| 看板 | 作用 |
|---|---|
| KOL 效果看板 | 比较不同 KOL 的流量质量和转化路径 |
| 模板效果看板 | 比较不同模板在不同目标下的表现 |
| Agent 决策看板 | 比较不同运行时策略的效果 |
| 漏斗诊断看板 | 找到从曝光到转化每一步的问题 |
| 复盘沉淀看板 | 把有效策略变成模板升级和运营建议 |

## 9. 上线前检查清单

| 检查项 | 是否必须 | 说明 |
|---|---:|---|
| 模板字段完整 | 必须 | 没有 schema 就无法稳定生成 |
| KOL 专属信息正确 | 必须 | 名称、头像、链接、语气不能错 |
| 核心路径可玩 | 必须 | 用户能从开始走到结果页 |
| CTA 可点击可追踪 | 必须 | 转化目标必须可归因 |
| 埋点完整 | 必须 | 没有数据就无法 Agentic 复盘 |
| 奖励表述合规 | 必须 | 不能承诺收益或误导用户 |
| 分享卡正常 | 必须 | KOL 传播依赖分享资产 |
| Agent 策略有边界 | 必须 | 运行时调整不能越过业务和合规限制 |
| 异常流量处理 | 建议 | 防刷、防重复领取、防异常转化 |
| 版本回滚 | 建议 | 运行中出现问题可以快速回退 |

## 10. 推荐系统架构模块

| 层级 | 模块 | 作用 |
|---|---|---|
| 业务应用层 | KOL 创作台、运营台、数据看板 | 给业务用户使用 |
| 模板层 | 模板库、模板 schema、字段权限 | 决定可复用结构 |
| 编排层 | Brief Agent、Strategy Agent、Generation Agent | 把输入变成生成计划 |
| 约束层 | 合规规则、品牌规则、玩法规则、数据规则 | 控制生成边界 |
| 资产层 | 文案、图片、视频、题库、分享卡 | 支撑内容生成 |
| 构建层 | H5 Builder、版本管理、预览服务 | 生成可发布版本 |
| 运行层 | Runtime Agent、分群、策略选择、风控 | 在线调整体验 |
| 数据层 | 埋点、归因、事件流、实验、报表 | 形成反馈 |
| 记忆层 | KOL Memory、Template Memory、Campaign Memory | 支撑下一次更好生成 |
| 平台层 | 权限、成本、监控、日志、审计 | 保证可运营可治理 |

## 11. 从 MVP 到平台化的建设顺序

| 阶段 | 建设重点 | 不建议过早做 |
|---|---|---|
| 第 1 阶段 | 模板 schema、P0 字段、H5 Builder、基础埋点 | 多模板泛化、复杂智能体协作 |
| 第 2 阶段 | Brief Agent、Generation Agent、Constraint Agent | 完全自由生成 |
| 第 3 阶段 | 发布链路、KOL 专属链接、分享卡、基础看板 | 复杂投放自动化 |
| 第 4 阶段 | Runtime Agent、动态难度、奖励节奏、CTA 策略 | 不可解释的黑盒优化 |
| 第 5 阶段 | Diagnosis Agent、复盘报告、模板记忆、KOL 记忆 | 大规模自动复投 |
| 第 6 阶段 | 模板运营体系、跨 KOL 复用、行业模板库 | 全行业通用平台 |

最务实的 MVP 顺序：

1. 先定义模板 schema 和可编辑字段。
2. 再做一个可稳定生成的模板。
3. 接入基础埋点和数据看板。
4. 加约束验证，保证生成结果能上线。
5. 加少量运行时策略，让 Agentic 先发生在可控范围内。
6. 用复盘报告驱动下一轮模板更新。

## 12. 关键风险

| 风险 | 表现 | 处理方式 |
|---|---|---|
| 把 Agentic 做成聊天框 | 用户只是和 AI 对话，不能影响运营结果 | 把 Agentic 聚焦到策略、生成、运行和复盘 |
| 模板没有 schema | 每次生成都不稳定，无法复用 | 先结构化模板和字段权限 |
| 埋点只看 KPI | 看得到结果，看不到原因 | 记录 Agent 决策和用户后续行为 |
| KOL 改动太自由 | 改坏规则、合规或追踪 | 用结构化字段和补丁机制 |
| 运行时策略无边界 | Agent 自动调整造成合规或品牌风险 | Constraint Service 必须拦截 |
| 数据无法回流模板 | 每次活动都从零开始 | 建立 KOL Memory 和 Template Memory |

## 13. 一句话总结

Agentic Playable 的完整工作流是：

KOL 输入营销意图 -> 系统按模板生成可玩版本 -> 约束服务验证 -> Builder 发布 H5 -> Runtime Agent 在运行中调整体验 -> 数据记录每个 Agent 决策和用户结果 -> Diagnosis Agent 复盘 -> 经验沉淀回 KOL 记忆和模板库。

对于 MVP，最重要的不是一次性做很多游戏，而是先把“一个模板、一个生成链路、一个发布链路、一个数据闭环、一个可控 Agentic 策略”跑通。
