# KOL / 项目方输入与身份上下文机制结构化梳理

## 1. 核心定义

KOL / 项目方输入与身份上下文机制，是 Airvana Agent OS 的业务起点。

它负责把“谁在创建活动、代表哪个项目、面向什么用户、具备什么资产、存在什么风险”转成结构化上下文。

核心产物：

| 产物 | 说明 |
|---|---|
| `kol_context` | KOL 身份、语气、粉丝、社媒、历史活动 |
| `project_context` | 项目信息、品牌、产品、Token、活动资源 |
| `audience_profile` | 目标受众画像 |
| `asset_inventory` | 可用图片、Logo、头像、链接、社群、奖励 |
| `risk_profile` | 身份风险、项目风险、奖励风险、渠道风险 |

## 2. 所处位置

| 上游 | 当前环节 | 下游 |
|---|---|---|
| KOL 登录、项目方提交资料、社媒连接器 | 身份与项目上下文生成 | 目标识别与生成模式选择 |

这是后续所有 Agent 的基础上下文。

如果这个环节不准，后面模板推荐、文案生成、分享卡、CTA、风控都会偏。

## 3. 业务目标

| 目标 | 说明 |
|---|---|
| 识别创作者 | 知道是 KOL、自运营账号、项目方、代理运营还是平台运营 |
| 识别项目 | 知道活动服务哪个品牌、产品、Token 或社区 |
| 识别受众 | 判断粉丝更适合教育、挑战、空投、社群还是转化 |
| 识别资产 | 判断能生成什么样的 Playable |
| 识别风险 | 判断是否需要加强合规、风控、审核 |
| 支撑个性化 | 让生成内容有 KOL 专属语气和项目可信度 |

## 4. 输入数据

| 输入 | 来源 | 用途 |
|---|---|---|
| KOL 基础资料 | 注册、登录、平台资料 | 名称、头像、简介 |
| 社媒账号 | 连接器 | 粉丝数、内容风格、互动表现 |
| 历史活动 | Airvana 内部数据 | 判断偏好和效果 |
| 项目资料 | 项目方提交、官网、白皮书摘要 | 生成项目表达和题目 |
| 社群链接 | Telegram、Discord、官网 | CTA 和发布投放 |
| 品牌资产 | Logo、视觉、角色、Token 图标 | 视觉和分享卡 |
| 奖励信息 | 活动配置 | 奖励表达、风控边界 |
| 合规资料 | 平台规则、项目条款 | 限制禁止表达 |

## 5. 关键 Agent

| Agent | 职责 |
|---|---|
| Identity Agent | 识别 KOL 类型、账号可信度、粉丝特征 |
| Project Context Agent | 解析项目资料、卖点、限制和资产 |
| Audience Agent | 根据 KOL 和项目推断目标受众 |
| Risk Profiling Agent | 识别身份、奖励、内容和渠道风险 |
| Context Normalizer | 把非结构化资料转成统一 schema |

## 6. 支撑系统

| 系统 | 作用 |
|---|---|
| Account Service | 管理 KOL 和项目方账号 |
| Connector Service | 连接 X、Telegram、Discord 等社媒 |
| Asset Service | 管理上传素材和授权资产 |
| RAG Service | 检索 KOL、项目和历史活动知识 |
| Memory Service | 读取历史偏好和表现 |
| Risk Service | 输出初始风险等级 |
| Permission Service | 控制谁能修改项目和活动信息 |

## 7. 数据对象建议

| 对象 | 核心字段 |
|---|---|
| `kol_context` | `kol_id`、`display_name`、`avatar`、`tone_profile`、`social_accounts`、`fan_tags`、`historical_performance` |
| `project_context` | `project_id`、`project_name`、`category`、`brand_assets`、`core_claims`、`official_links`、`restricted_claims` |
| `audience_profile` | `audience_tags`、`knowledge_level`、`motivation`、`preferred_channel` |
| `asset_inventory` | `asset_id`、`asset_type`、`usage_scope`、`license_status` |
| `risk_profile` | `identity_risk`、`reward_risk`、`compliance_risk`、`channel_risk` |

## 8. 决策逻辑

| 判断项 | 决策结果 |
|---|---|
| KOL 粉丝偏教育 | 后续优先推荐竞猜、答题、画线、模拟经营 |
| KOL 粉丝偏娱乐 | 后续优先推荐跑酷、射击、塔防 |
| 项目资产不足 | 降低重视觉模板优先级 |
| 奖励强刺激 | 后续提高风控和合规校验 |
| 项目资料不完整 | 进入资料补全或低置信生成 |
| KOL 历史 CTA 低 | 下游策略需要重点优化 CTA |

## 9. 约束边界

| 约束 | 说明 |
|---|---|
| 不采集未授权敏感数据 | 社媒连接必须授权 |
| 不伪造身份 | KOL 头像、昵称、认证状态不能虚构 |
| 不擅自扩大奖励 | 项目方未确认的奖励不能生成 |
| 不把推断当事实 | 粉丝画像和风险判断要标注置信度 |
| 不绕过合规 | 高风险项目必须进入审核 |

## 10. MVP 范围

MVP 阶段只需要跑通必要上下文：

| P0 能力 | 说明 |
|---|---|
| KOL 基础资料 | 名称、头像、社媒链接 |
| 项目基础资料 | 名称、Logo、官网、核心卖点 |
| 粉丝标签 | 通过 KOL 选择或平台轻量推断 |
| 资产清单 | 上传素材和可用链接 |
| 风险初筛 | 奖励、投资表达、未授权链接 |
| 上下文输出 | 生成 `kol_context` 和 `project_context` |

## 11. P1 / P2 扩展

| 阶段 | 能力 |
|---|---|
| P1 | 社媒连接器自动读取表现、历史活动 Memory、KOL 语气学习 |
| P2 | 跨活动受众画像、渠道质量评分、项目知识图谱、长期风险画像 |

## 12. 验收标准

| 验收项 | 标准 |
|---|---|
| 上下文完整 | 后续目标识别和模板推荐能正常运行 |
| 来源可追踪 | 每个字段知道来自用户填写、连接器、RAG 还是推断 |
| 风险可标记 | 高风险奖励、项目表达、社媒链接能被标记 |
| 可复用 | 下次同一 KOL 创建活动能预填上下文 |
| 可修正 | KOL 或运营能修正错误身份和项目信息 |

## 13. 最终结论

这个环节是 Agent OS 的身份层和业务上下文层。

它不是简单注册资料，而是把 KOL、项目、受众、资产和风险变成后续所有 Agent 可消费的结构化输入。
