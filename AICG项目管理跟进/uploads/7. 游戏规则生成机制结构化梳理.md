# 游戏规则生成机制结构化梳理

## 1. 核心定义

游戏规则生成，是指系统根据 `generation_brief`、`template_schema`、`template_config`、`content_assets`、营销目标和合规边界，生成一套可被 Builder 执行、可被 Constraint Service 校验、可被 Analytics 追踪、可被 Runtime Agent 在边界内调用的玩法规则。

它不是文案生成，不是视觉生成，也不是最终代码，而是 Playable 运行前必须明确的“规则层”。

| 不是 | 是 |
|---|---|
| 不是用户看到的文案 | 是决定用户如何操作、如何完成、如何获得反馈的规则 |
| 不是完整代码实现 | 是 Builder 可以转换成代码配置的规则对象 |
| 不是 Agentic 动态策略 | 是运行时策略必须遵守的边界 |
| 不是单纯玩法说明 | 同时包含胜负、计分、奖励、进度、CTA、反作弊和埋点 |

一句话：

**游戏规则生成 = 把内容和模板变成可执行、可验证、可追踪的玩法规则对象 `game_rules`。**

## 2. 在完整工作流中的位置

| 阶段 | 输入 | 输出 |
|---|---|---|
| 创作 Brief 生成 | `kol_context`、`campaign_goal`、`template_config` | `generation_brief` |
| 文案、视觉、任务内容生成 | `generation_brief`、`template_schema`、资产 | `content_assets` |
| 游戏规则生成 | `generation_brief`、`template_schema`、`template_config`、`content_assets` | `game_rules` |
| Agent 策略生成 | `campaign_goal`、`game_rules`、风险边界 | `agent_policy` |
| 约束验证 | `content_assets`、`game_rules`、`agent_policy` | `validation_report` |
| H5 组装 | 模板代码、`content_assets`、`game_rules`、`agent_policy` | `playable_version` |
| 运行时运营 | `game_rules`、`agent_policy`、用户行为 | `runtime_decision` |
| 数据复盘 | 事件日志、规则版本、Agent 决策 | 诊断报告、模板记忆 |

游戏规则生成处在内容层和运行层之间。它把“用户看到的任务”变成“系统可以执行的规则”。

## 3. 和相邻阶段的区别

| 环节 | 负责什么 | 不负责什么 |
|---|---|---|
| 内容生成 | 用户看到的题目、任务、反馈、分享文案和视觉 | 不决定规则执行 |
| 游戏规则生成 | 用户如何完成、如何计分、如何获奖、如何流转 | 不生成文案风格 |
| Agent 策略生成 | 上线后怎么动态调难度、奖励、提示和 CTA | 不突破规则边界 |
| Constraint Service | 校验规则是否合法、可玩、可追踪 | 不负责创作玩法 |
| Builder | 把规则对象转换成可运行 H5 | 不决定业务规则 |

简单区分：

| 问题 | 属于哪个阶段 |
|---|---|
| 按钮上写什么 | 文案生成 |
| 用户答对一题得几分 | 游戏规则生成 |
| 用户连续失败是否降难度 | Agent 策略生成 |
| 奖励文案是否误导 | 约束验证 |
| 页面如何渲染 | Builder |

## 4. 游戏规则生成的主要输入

| 输入对象 | 关键内容 | 作用 |
|---|---|---|
| `generation_brief` | 创作目标、玩法任务、奖励任务、合规边界 | 决定规则方向 |
| `template_schema` | 模板支持的规则槽位、状态、事件、字段范围 | 决定规则能否被 Builder 执行 |
| `template_config` | 题目数量、任务数量、难度、奖励、CTA、时长 | 决定本次活动参数 |
| `content_assets` | 题目、任务、视觉、反馈、CTA 文案 | 决定规则绑定的具体内容 |
| `campaign_goal` | 主目标、次目标、核心指标 | 决定规则服务哪个转化目标 |
| `compliance_constraints` | 禁止表达、奖励边界、风控要求 | 决定规则是否可上线 |
| `risk_profile` | KOL 风险、活动风险、奖励风险 | 决定反作弊强度 |
| `tracking_requirements` | 必需事件、漏斗、归因字段 | 决定规则如何埋点 |

## 5. 核心输出

游戏规则生成的统一输出对象是 `game_rules`。

| 输出模块 | 说明 |
|---|---|
| `start_rules` | 用户如何开始，开始前需要什么条件 |
| `progression_rules` | 任务、关卡、题目、波次如何推进 |
| `interaction_rules` | 用户可做哪些操作，每个操作如何响应 |
| `win_conditions` | 什么情况下算完成、胜利或达成目标 |
| `fail_conditions` | 什么情况下算失败、中断、超时或退出 |
| `scoring_rules` | 如何计分、评级、分层 |
| `reward_rules` | 奖励何时触发、发什么、如何限制 |
| `cta_rules` | CTA 何时出现、出现给谁、点击后到哪里 |
| `anti_abuse_rules` | 防刷、防重复、异常行为限制 |
| `state_machine` | 游戏状态如何流转 |
| `tracking_rules` | 每一步触发哪些事件 |
| `runtime_boundaries` | Runtime Agent 允许调整什么、不允许调整什么 |
| `fallback_rules` | 缺资产、失败、网络异常、用户退出时怎么处理 |

## 6. 规则生成的核心任务

| 任务 | 说明 |
|---|---|
| 定义开始规则 | 用户如何进入 Playable，是否需要授权、登录、钱包或社群链接 |
| 定义推进规则 | 题目、任务、关卡、波次、路径如何从一步进入下一步 |
| 定义完成条件 | 用户完成什么动作后进入结果页 |
| 定义失败条件 | 超时、答错、失败、退出、异常时如何处理 |
| 定义计分/评级 | 如何从用户行为得到分数、等级、身份或结果 |
| 定义奖励触发 | 什么条件触发积分、徽章、资格、抽奖机会 |
| 定义 CTA 触发 | 在什么状态下出现入群、注册、关注、领取或分享 |
| 定义反作弊 | 如何限制重复参与、刷量、异常设备、异常钱包 |
| 定义埋点 | 每个关键状态和行为要记录什么事件 |
| 定义运行边界 | Agent 后续动态调整时不能越过哪些规则 |

| `fail_conditions` | 失败 / 中断条件 |

## 8. 规则类型拆解

### 8.1 开始规则 `start_rules`

开始规则决定用户进入活动前需要满足什么。

| 字段 | 示例 |
|---|---|
| 开始方式 | 点击开始按钮、扫码进入、KOL 链接进入 |
| 前置条件 | 无需登录、需要授权、需要连接钱包、需要邀请码 |
| 入口参数 | KOL ID、渠道、campaign ID、分享来源 |
| 初始状态 | 新用户、回访用户、已完成用户、异常用户 |
| 初始事件 | `playable_start` |

MVP 建议：默认不强制登录，先保证开始率；只有空投、奖励、钱包任务才增加前置验证。

### 8.2 推进规则 `progression_rules`

推进规则决定用户从一个步骤进入下一个步骤。

| 类型 | 示例 |
|---|---|
| 顺序推进 | 第 1 题 -> 第 2 题 -> 第 3 题 -> 结果页 |
| 条件推进 | 完成入群任务后解锁问答 |
| 分支推进 | 答错进入解释页，答对进入下一题 |
| 波次推进 | 塔防第 1 波结束后进入第 2 波 |
| 关卡推进 | 跑酷完成当前赛道后进入结果页 |
| 路径推进 | 画线成功后进入反馈页 |

推进规则必须能被状态机表示，不能靠自然语言描述。

### 8.3 交互规则 `interaction_rules`

交互规则定义用户能做哪些操作。

| 操作 | 规则示例 |
|---|---|
| 点击开始 | 初始化会话，进入第一步 |
| 选择答案 | 每题只能选一个，提交后不可修改 |
| 完成任务 | 验证任务状态，解锁下一步 |
| 分享 | 生成带归因参数的分享卡 |
| 点击 CTA | 记录来源并跳转目标 |
| 重试 | 是否允许重试，重试是否影响计分 |
| 跳过 | 是否允许跳过，跳过后是否失去奖励 |

### 8.4 完成/胜利条件 `win_conditions`

胜利条件不一定是“赢游戏”，在营销 Playable 中更常见的是“完成目标路径”。

| 模板 | 完成条件示例 |
|---|---|
| 竞猜 | 完成全部题目并进入结果页 |
| 空投任务 | 完成指定任务并满足奖励条件 |
| 跑酷 | 到达终点或达到最低分数 |
| 塔防 | 防守到最后一波或保护核心资产 |
| 射击 | 达到分数、命中数或通关条件 |
| 画线 | 成功连接起点终点并避开障碍 |
| 模拟经营 | 达到资源、等级、用户数或任务目标 |

### 8.5 失败/中断条件 `fail_conditions`

失败规则决定用户没有完成时怎么处理。

| 失败类型 | 处理方式 |
|---|---|
| 答错 | 给解释，允许继续或重试 |
| 超时 | 进入失败反馈或降低难度 |
| 死亡 / 撞障碍 | 给重试机会，记录失败点 |
| 任务未完成 | 保留进度或提示下一步 |
| 用户退出 | 记录 `drop_off` |
| 异常行为 | 进入风控路径或限制奖励 |

营销 Playable 不建议过早让用户彻底失败。MVP 更适合“失败可继续，奖励分层”。

### 8.6 计分规则 `scoring_rules`

计分规则决定用户的结果分型、排行榜和奖励。

| 计分方式 | 示例 |
|---|---|
| 答题计分 | 每题 1 分 |
| 完成计分 | 完成任务 +10 分 |
| 收集计分 | 每收集 1 个 Token +1 分 |
| 连击计分 | 连续命中加成 |
| 时间计分 | 越快完成分数越高 |
| 防守计分 | 剩余生命、击败敌人、升级选择 |
| 路径计分 | 路径长度、收集量、是否避障 |

计分要服务营销目标，不要为了复杂而复杂。

### 8.7 奖励规则 `reward_rules`

奖励规则决定什么条件触发什么奖励。

| 字段 | 示例 |
|---|---|
| 奖励类型 | 积分、徽章、抽奖资格、白名单资格、排行榜排名 |
| 触发条件 | 完成全部任务、达到 80 分、分享一次 |
| 发放方式 | 页面展示、后台记录、跳转领取、Webhook 通知 |
| 限制条件 | 每用户一次、每钱包一次、每设备一次 |
| 失效条件 | 活动结束、作弊、重复领取 |
| 合规文案 | 奖励以官方规则为准 |

Web3 / 金融相关 MVP 建议优先使用虚拟积分、徽章、资格和抽奖机会，不要直接承诺真实 Token 或收益。

### 8.8 CTA 规则 `cta_rules`

CTA 规则决定用户在什么状态下看到转化入口。

| 场景 | CTA 触发建议 |
|---|---|
| 项目教育 | 完成题目后展示“了解更多” |
| 社群增长 | 完成核心任务或得到结果后展示“加入社群” |
| 转化领取 | 达到奖励条件后展示“领取资格” |
| 裂变传播 | 结果页展示“分享给朋友” |
| 留存复活 | 完成后展示“明天继续挑战” |

CTA 不能和主目标冲突。例如主目标是社群增长，就不应该把购买 CTA 作为唯一主要动作。

### 8.9 反作弊规则 `anti_abuse_rules`

反作弊规则保护奖励、数据和项目方信任。

| 风险 | 规则示例 |
|---|---|
| 重复参与 | 同一设备、浏览器、账号、钱包只计一次 |
| 刷点击 | 极短时间大量点击进入异常路径 |
| 刷分享 | 重复分享但无人点击不计有效邀请 |
| 刷奖励 | 同一钱包或账号重复领取被限制 |
| 羊毛党 | 高速完成、相同路径、异常来源进入人工审核 |
| 虚假转化 | CTA 点击后无有效完成不计转化 |

反作弊强度要和奖励强度匹配。奖励越强，规则越严格。

### 8.10 埋点规则 `tracking_rules`

规则生成必须同时生成埋点规则，否则无法复盘。

| 规则事件 | 触发时机 |
|---|---|
| `playable_impression` | Playable 被展示 |
| `playable_start` | 用户点击开始 |
| `scene_view` | 用户进入场景 / 步骤 |
| `user_action` | 用户执行关键操作 |
| `answer_submit` | 用户提交答案 |
| `step_complete` | 用户完成任务或关卡 |
| `reward_granted` | 奖励触发 |
| `share_click` | 用户点击分享 |
| `cta_click` | 用户点击 CTA |
| `conversion` | 用户完成目标转化 |
| `drop_off` | 用户中断或流失 |
| `anti_abuse_triggered` | 触发异常规则 |

每个事件至少应该带：

| 维度 | 示例 |
|---|---|
| 用户和会话 | `user_id`、`session_id` |
| 活动归因 | `campaign_id`、`kol_id`、`channel` |
| 版本 | `playable_version_id`、`rule_version` |
| 位置 | `scene_id`、`step_id`、`component_id` |
| 行为结果 | `action_type`、`result` |
| Agent 决策 | `agent_decision_id`，如果有 |

## 9. 状态机 `state_machine`

复杂规则必须落成状态机，否则 Builder 和 Runtime Agent 难以稳定执行。

| 状态 | 说明 |
|---|---|
| `not_started` | 用户未开始 |
| `started` | 已进入活动 |
| `in_step` | 正在完成题目、任务、关卡 |
| `step_completed` | 当前步骤完成 |
| `reward_pending` | 奖励待触发 |
| `reward_granted` | 奖励已触发 |
| `cta_shown` | CTA 已展示 |
| `completed` | 活动完成 |
| `dropped` | 用户流失 |
| `blocked` | 风控阻断 |

状态机要求：

1. 必须有开始状态和结束状态。
2. 每个状态必须有可达路径。
3. 不允许无出口循环。
4. 失败和退出必须有记录路径。
5. Runtime Agent 只能在允许状态内调整体验。

## 10. 不同模板的规则生成重点

### 10.1 竞猜 / 预测模板

| 规则模块 | 重点 |
|---|---|
| 开始规则 | 点击开始进入第 1 题 |
| 推进规则 | 按题目顺序推进，提交后进入下一题 |
| 交互规则 | 每题单选或多选，提交后不可修改 |
| 计分规则 | 答对得分，答错给解释 |
| 结果规则 | 按分数生成用户分型 |
| 奖励规则 | 完成全部题目或达到分数触发 |
| CTA 规则 | 结果页展示入群、查看项目或领取资格 |
| 反作弊 | 限制重复提交和异常高速完成 |
| 埋点 | 每题展示、提交、正确率、流失点 |

### 10.2 空投任务模板

| 规则模块 | 重点 |
|---|---|
| 开始规则 | 从 KOL 专属链接进入任务链 |
| 推进规则 | 按任务顺序或核心任务解锁推进 |
| 交互规则 | 入群、关注、答题、分享、钱包验证 |
| 完成规则 | 完成指定任务组合后进入结果页 |
| 奖励规则 | 触发积分、抽奖资格或白名单资格 |
| CTA 规则 | 核心任务完成后展示领取或入群 CTA |
| 反作弊 | 设备、账号、钱包、来源、速度校验 |
| 埋点 | 任务完成、入群点击、分享、异常行为 |

### 10.3 跑酷模板

| 规则模块 | 重点 |
|---|---|
| 开始规则 | 点击开始进入赛道 |
| 推进规则 | 按距离、时间或终点推进 |
| 交互规则 | 移动、跳跃、躲避、收集 |
| 失败规则 | 撞障碍、掉落、超时 |
| 计分规则 | 收集物、距离、时间、连击加分 |
| 奖励规则 | 到达终点或达到分数触发 |
| CTA 规则 | 完赛或高分后展示 |
| 反作弊 | 异常分数、异常速度、重复刷分限制 |
| 埋点 | 开始、失败点、收集、完赛、分享 |

### 10.4 塔防模板

| 规则模块 | 重点 |
|---|---|
| 开始规则 | 进入地图并获得初始资源 |
| 推进规则 | 波次推进、敌人生成、塔升级 |
| 交互规则 | 建塔、升级、释放技能、选择策略 |
| 胜利规则 | 防守到最后一波或保护核心资产 |
| 失败规则 | 核心资产生命值归零 |
| 计分规则 | 击败敌人、剩余生命、资源使用效率 |
| 奖励规则 | 通关、击败 Boss 或高分触发 |
| CTA 规则 | 胜利、升级完成或 Boss 后展示 |
| 埋点 | 波次流失、塔选择、升级、胜利率 |

### 10.5 射击模板

| 规则模块 | 重点 |
|---|---|
| 开始规则 | 进入射击场景 |
| 推进规则 | 固定时间、目标数量或关卡推进 |
| 交互规则 | 瞄准、射击、命中、连击 |
| 失败规则 | 时间结束、生命耗尽、命中不足 |
| 计分规则 | 命中、连击、目标类型、时间奖励 |
| 奖励规则 | 达到分数或通关触发 |
| CTA 规则 | 高分、连击或结果页展示 |
| 反作弊 | 异常命中率、异常点击频率 |
| 埋点 | 命中率、连击、目标类型、完赛 |

### 10.6 画线 / 路径规划模板

| 规则模块 | 重点 |

| 开始规则 | 展示起点、终点和障碍 |
| 推进规则 | 画线完成后执行路径校验 |
| 交互规则 | 画线、重画、连接、避障 |
| 胜利规则 | 成功连接目标并满足路径条件 |
| 失败规则 | 碰撞障碍、路径断裂、超时 |
| 计分规则 | 路径长度、收集物、避障成功、时间 |
| 奖励规则 | 完成路径或高分触发 |
| CTA 规则 | 完成路径后展示 |
| 埋点 | 失败点、路径长度、提示使用、完成率 |

### 10.7 模拟经营模板

| 规则模块 | 重点 |
|---|---|
| 开始规则 | 初始化资源、建筑和任务 |
| 推进规则 | 资源生产、升级、事件、目标达成 |
| 交互规则 | 建造、升级、分配资源、处理事件 |

## 11. 和 Agent 策略的关系

`game_rules` 是边界，`agent_policy` 是在边界内动态调整的策略。

| 规则层 | Agent 策略层 |
|---|---|
| 规定题目最多 5 题 | Agent 可在 3-5 题范围内选择 |
| 规定奖励只能是积分或资格 | Agent 不能改成真实 Token 奖励 |
| 规定 CTA 只能在结果页出现 | Agent 不能在首屏强插 CTA |
| 规定难度范围是 1-3 | Agent 可根据表现调到 1、2、3 |
| 规定反作弊触发条件 | Agent 可根据风险提高验证强度 |

重要原则：

1. Agent 不能改主目标。
2. Agent 不能突破合规边界。
3. Agent 不能改变奖励性质。
4. Agent 的调整必须被记录。
5. Agent 修改体验后，仍要符合 `game_rules`。

## 12. 规则生成后的校验

规则生成后必须先校验，再进入 Builder。

| 校验项 | 说明 |
|---|---|
| 规则完整性 | 是否包含开始、推进、完成、失败、奖励、CTA、埋点 |
| 状态可达性 | 每个状态是否可进入、可退出 |
| 无死循环 | 是否存在无法结束的规则循环 |
| 目标一致性 | 规则是否服务 `campaign_goal` |
| 模板一致性 | 规则是否在 `template_schema` 支持范围内 |
| 内容一致性 | 规则是否能绑定 `content_assets` |
| 奖励合规 | 奖励是否违反边界 |
| CTA 合法 | CTA 是否和目标匹配 |
| 反作弊充分 | 奖励强度是否匹配风控强度 |
| 数据可追踪 | 每个关键行为是否有事件 |
| Builder 可执行 | 规则是否能被前端模板实现 |

校验失败时，不能直接发布，必须返回修改：

| 失败原因 | 返回哪里 |
|---|---|
| CTA 和目标冲突 | 营销目标 / 关键变量 |
| 模板不支持规则 | 模板推荐 / 关键变量 |
| 奖励风险过高 | 关键变量 / 合规约束 |
| 状态机不可达 | 规则生成 |
| 内容缺失 | 内容生成 |
| 必需埋点缺失 | 规则生成 / Analytics 配置 |

## 13. 与 Builder 的接口

Builder 应读取结构化 `game_rules`，而不是自然语言玩法说明。

| Builder 需要 | 来自 `game_rules` |
|---|---|
| 初始状态 | `start_rules`、`state_machine` |
| 页面流转 | `progression_rules` |
| 用户操作 | `interaction_rules` |
| 结果判断 | `win_conditions`、`fail_conditions` |
| 分数计算 | `scoring_rules` |
| 奖励触发 | `reward_rules` |
| CTA 展示 | `cta_rules` |
| 风控拦截 | `anti_abuse_rules` |
| 埋点触发 | `tracking_rules` |

如果 Builder 无法执行某条规则，应返回规则不支持报告，而不是静默忽略。

## 14. KOL 二次编辑与规则 Patch

不是所有 KOL 编辑都会影响规则。

| KOL 修改 | 是否影响 `game_rules` | 处理方式 |
|---|---:|---|
| 改首屏标题 | 否 | 内容 Patch |
| 改分享文案 | 否 | 内容 Patch |
| 改题目文案但不改答案 | 否或轻微 | 内容 Patch + 校验 |
| 改题目数量 | 是 | 规则 Patch |
| 改任务顺序 | 是 | 规则 Patch |
| 改奖励条件 | 是 | 规则 Patch + 合规校验 |
| 改 CTA 目标 | 是 | 回到目标 / 关键变量 |
| 改模板 | 是 | 重新生成规则 |

规则 Patch 流程：

1. 识别修改影响范围。
2. 生成 `game_rule_patch`。
3. 校验状态机、奖励、CTA、埋点和合规。
4. 只重建受影响模块。
5. 生成新的 `rule_version` 和 `playable_version`。

## 18. 不建议的做法

| 不建议事项 | 原因 |
|---|---|
| 用自然语言描述规则但不结构化 | Builder 难以执行，校验困难 |
| 只做内容不做规则 | 用户看到任务但系统无法判断完成 |
| 规则不绑定埋点 | 无法复盘流失和转化 |
| 奖励规则不加限制 | 容易刷奖励和产生合规风险 |
| Agent 可以随意改规则 | 运行时不可控 |
| 规则和模板 schema 脱节 | 前端无法实现 |
| 规则改动后不版本化 | 数据和复盘无法归因 |

## 19. 结论

游戏规则生成是 Agentic Playable 从“内容素材”进入“可运行玩法”的关键阶段。

它要解决四件事：

| 问题 | 解决方式 |
|---|---|
| 用户怎么玩 | 生成开始、推进、交互、胜负和失败规则 |
| 用户怎么得结果 | 生成计分、评级、奖励和 CTA 规则 |
| 系统怎么防风险 | 生成反作弊、合规和奖励限制 |
| 后续怎么复盘 | 生成埋点、状态机和规则版本 |

MVP 阶段最重要的是：

1. `game_rules` 必须结构化，不能只是玩法说明。
2. 每个规则必须能被 Builder 执行。
3. 每个关键状态必须能被埋点追踪。
4. 奖励、CTA 和反作弊必须前置校验。
5. Runtime Agent 只能在规则允许范围内动态调整。

这样，游戏规则生成才不是“写怎么玩”，而是把 Playable 变成可执行、可验证、可运营、可复盘的规则系统。
