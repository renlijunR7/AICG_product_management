# 关键变量填写机制结构化梳理

## 1. 核心定义

关键变量填写，是指在 KOL 选择营销目标和模板之后，平台把“我要做一个 Agentic Playable 营销游戏”拆成一组结构化字段，让系统能够稳定生成、验证、发布和运营。

它不是让用户填写所有细节，也不是让 KOL 写代码，而是把创作意图转换成系统可执行的配置对象。

| 不是 | 是 |
|---|---|
| 让 KOL 写复杂 Prompt | 用结构化字段表达营销意图 |
| 让用户配置所有游戏参数 | 只让用户确认影响结果的关键变量 |
| 一个普通表单 | 连接生成、玩法、奖励、CTA、约束和数据的核心配置 |
| 只影响首版生成 | 会影响发布后的 Agentic 运营和复盘 |

一句话：

**关键变量填写 = Agentic Playable 生成前的核心参数表，决定为谁做、玩什么、怎么奖励、引导用户做什么，以及后续 Agent 如何运营。**

## 2. 在完整工作流中的位置

关键变量填写位于“营销目标选择”和“创作 Brief 生成”之间。

| 步骤 | 输入 | 输出 |
|---|---|---|
| KOL 身份识别 | 注册、社媒、历史 campaign、平台行为 | `kol_context` |
| 营销目标选择 | 用户目标、项目 Brief、平台推荐 | `campaign_goal` |
| 模板推荐 | 目标、KOL、资产、渠道 | `template_schema`、推荐模板 |
| 关键变量填写 | 用户确认、平台默认、Agent 推断、项目方锁定 | `template_config`、`generation_brief_input` |
| Brief 生成 | 关键变量 + 上下文 | `generation_brief` |
| 规则生成 | 模板配置 + 目标 | `game_rules` |
| Agent 策略生成 | 目标 + 用户路径 + 风险边界 | `agent_policy` |
| 约束验证 | 规则、奖励、CTA、合规要求 | `validation_report` |
| H5 构建 | 模板、资产、规则、埋点 | `playable_version` |

关键变量不是孤立存在的，它会被后续多个模块读取。

## 3. 为什么需要关键变量

如果不做关键变量填写，用户的输入通常是模糊的：

| 模糊表达 | 系统无法判断的问题 |
|---|---|
| 帮我做一个空投小游戏 | 是拉群、注册、领取还是教育用户？ |
| 做一个竞猜活动 | 猜什么、几题、难度多高、结果怎么反馈？ |
| 帮我给粉丝做福利 | 福利是什么、发放条件是什么、是否合规？ |
| 做一个好玩的跑酷 | 谁跑、收集什么、终点 CTA 是什么？ |
| 做一个塔防宣传项目 | 防守什么、敌人代表什么风险、胜利后引导什么？ |

关键变量的作用是把模糊表达变成可执行配置：

| 能力 | 说明 |
|---|---|
| 可生成 | 生成 Agent 知道要生成什么 |
| 可验证 | Constraint Service 能检查是否合规、可玩、可追踪 |
| 可发布 | Builder 能组装 H5 Playable |
| 可运营 | Runtime Agent 能根据变量做策略调整 |
| 可复盘 | Diagnosis Agent 能判断变量是否影响结果 |
| 可复用 | Template Memory 能沉淀成功配置 |

## 4. 关键变量的四种来源

关键变量不应该全部让用户手填。合理机制是：用户只填少量关键决策，平台和 Agent 自动补全大部分细节。

| 来源 | 说明 | 示例 |
|---|---|---|
| 用户填写 | KOL 必须确认的核心意图 | 活动主题、CTA、奖励类型 |
| 平台默认 | 根据模板、目标和最佳实践给默认值 | 推荐题目数量、默认难度、默认分享卡结构 |
| Agent 推断 | 根据 `kol_context`、`campaign_goal`、资产和历史数据生成 | 文案语气、任务顺序、奖励节奏 |
| 项目方 / 合规锁定 | 不允许 KOL 修改的边界 | 品牌名、主 CTA、免责声明、奖励规则 |

建议前台交互不要展示“所有变量”，而是按影响程度分层。

## 5. 关键变量分层

### 5.1 P0：必须确认的变量

P0 变量会直接影响生成方向和转化结果，必须在生成前确认。

| 变量 | 说明 | 示例 |
|---|---|---|
| 营销目标 | 活动要达成什么 | 社群增长、项目教育、转化领取 |
| 目标用户 | 主要给谁玩 | 新手、交易用户、项目粉丝、社区用户 |
| 模板类型 | 核心玩法容器 | 竞猜、空投、跑酷、塔防、画线 |
| 活动主题 | 用户看到的主题 | BTC 行情判断、项目空投任务 |
| 核心利益点 | 用户为什么开始玩 | 测测判断力、获得积分、赢取资格 |
| CTA 目标 | 最终引导用户做什么 | 入群、注册、关注、领取、分享 |
| 奖励类型 | 用户完成后得到什么 | 积分、徽章、抽奖资格、白名单资格 |
| 合规边界 | 什么不能说或不能做 | 不承诺收益、不做投资建议 |

### 5.2 P1：建议确认的变量

P1 变量会影响体验质量和运营效果，但可以由平台推荐默认值。

| 变量 | 说明 | 示例 |
|---|---|---|
| 活动时长 | 活动持续多久 | 3 天、7 天、14 天 |
| 单局时长 | 用户一次玩多久 | 30 秒、60 秒、2 分钟 |
| 难度等级 | 初始难度 | 新手友好、中等、挑战型 |
| 任务数量 | 要完成几步 | 3 步任务、5 题竞猜 |
| 分享机制 | 是否鼓励分享 | 分享结果卡、邀请好友、排行榜 |
| 排行榜 | 是否展示排名 | KOL 粉丝榜、项目活动榜 |
| 用户分群 | 是否区分用户 | 新用户、老用户、高意向用户 |
| 首屏风格 | 首屏表达方式 | 专业解释、福利活动、挑战感 |

### 5.3 P2：系统自动推断的变量

P2 变量不建议在 MVP 里让用户手填，否则表单过重。

| 变量 | 推荐处理方式 |
|---|---|
| 题目细节 | Agent 根据项目资料和目标生成 |
| 任务顺序 | Strategy Agent 根据转化路径生成 |
| 提示文案 | Generation Agent 自动生成 |
| 失败反馈 | Generation Agent 自动生成 |
| 奖励触发阈值 | 平台根据模板默认和风控设置 |
| 动态难度规则 | Runtime Agent 根据策略生成 |
| 埋点字段 | 系统根据模板自动配置 |
| A/B 实验参数 | 平台运营或系统后续生成 |

## 6. 通用关键变量字段

所有模板都应该有一组通用关键变量。

| 字段组 | 字段 | 作用 |
|---|---|---|
| 业务目标 | `primary_goal`、`secondary_goal`、`target_action` | 决定生成方向 |
| 用户对象 | `target_audience`、`audience_level`、`audience_interest` | 决定难度和文案 |
| KOL 表达 | `kol_name`、`kol_avatar`、`tone_profile`、`fan_label` | 决定专属感 |
| 项目信息 | `project_name`、`project_category`、`core_message` | 决定内容 |
| 模板选择 | `template_type`、`template_id`、`template_version` | 决定玩法结构 |
| 玩法设置 | `session_length`、`difficulty`、`round_count` | 决定完玩率 |
| 奖励设置 | `reward_type`、`reward_condition`、`reward_message` | 决定激励强度 |
| CTA 设置 | `primary_cta`、`cta_timing`、`cta_url` | 决定转化 |
| 分享设置 | `share_title`、`share_card_style`、`invite_text` | 决定裂变 |
| 风控合规 | `compliance_rules`、`blocked_claims`、`risk_level` | 决定能否上线 |
| 数据追踪 | `target_metrics`、`required_events`、`attribution_params` | 决定复盘 |

## 7. 用户填写、平台默认、Agent 推断、锁定字段分工

| 字段类型 | 由谁决定 | 示例 | 原因 |
|---|---|---|---|
| 用户必须填 | KOL / 运营 | 活动主题、CTA 目标、奖励类型 | 代表真实营销意图 |
| 用户确认即可 | 平台推荐，用户确认 | 营销目标、模板、难度、任务数量 | 降低选择成本 |
| 平台默认 | 平台规则 | 默认单局时长、默认埋点、默认分享结构 | 保证稳定生成 |
| Agent 推断 | Brief / Strategy / Generation Agent | 文案、题目、任务顺序、结果反馈 | 减少用户负担 |
| 项目方锁定 | 项目方 / Campaign Brief | 项目名、品牌信息、主 CTA、活动规则 | 保证 campaign 一致 |
| 合规锁定 | Constraint Service | 免责声明、收益承诺限制、奖励边界 | 控制风险 |

前台设计原则：

1. 不要一开始展示所有字段。
2. 先让用户确认 P0 字段。
3. P1 字段放到“高级设置”或“可调整”里。
4. P2 字段由系统生成后在预览里体现。
5. 锁定字段要显示原因，不能让用户误以为系统坏了。

### 8.1 竞猜 / 预测模板

| 字段 | 示例 | 是否必须 |
|---|---|---:|
| 竞猜对象 | BTC、ETH、项目 Token、项目知识点 | 必须 |

## 10. 前台交互建议

关键变量填写页面不要做成一个很长的表单。推荐分 4 步。

| 步骤 | 页面问题 | 字段 |
|---|---|---|
| 1. 活动意图 | 你希望粉丝完成什么动作？ | 营销目标、CTA、目标用户 |
| 2. 玩法配置 | 这个活动怎么玩？ | 模板类型、难度、时长、任务数量 |
| 3. 激励与分享 | 用户完成后得到什么，愿不愿意分享？ | 奖励、结果反馈、分享卡 |
| 4. 发布约束 | 有哪些规则不能违反？ | 合规边界、活动规则、链接 |

### 10.1 推荐交互形态

| 字段类型 | 交互控件 |
|---|---|
| 目标、模板、CTA | 卡片选择 / 分段选择 |
| 难度、时长、题目数量 | 滑杆 / 步进器 / 下拉 |
| 奖励类型 | 单选卡片 |
| 分享卡文案 | 平台生成后可编辑 |
| 合规规则 | 锁定展示 + 提示原因 |
| 高级参数 | 默认折叠 |

### 10.2 不建议的交互

| 不建议 | 原因 |
|---|---|
| 一次展示几十个字段 | KOL 会被表单劝退 |
| 让用户手写完整 Prompt | 输出不可控，难以验证 |
| 所有字段都可编辑 | 容易破坏模板、合规和埋点 |
| 不解释锁定字段 | 用户会认为平台限制太多 |
| 不展示生成影响 | 用户不知道自己改字段会影响什么 |

## 11. 平台默认值机制

关键变量需要默认值，否则新手用户很难完成创建。

| 默认值来源 | 示例 |
|---|---|
| 模板默认 | 竞猜默认 3 题，跑酷默认 60 秒 |
| 营销目标默认 | 社群增长默认入群 CTA |
| KOL 历史默认 | 该 KOL 常用专业语气和短任务 |
| 行业默认 | Web3 活动默认增加风险提示 |
| 渠道默认 | TikTok 模板默认更短，Telegram 默认任务链 |
| 风控默认 | 高奖励活动默认开启反作弊 |

默认值必须可解释：

| 展示内容 | 示例 |
|---|---|
| 默认字段 | 题目数量：3 |
| 推荐原因 | 3 题通常能平衡完成率和教育效果 |
| 可否修改 | 可修改 |
| 影响说明 | 增加题目会提升教育深度，但可能降低完成率 |

## 12. Agentic 可调变量

有些关键变量不是只在生成前使用，还会影响运行时 Agent 的自动策略。

| 变量 | 运行时怎么用 |
|---|---|
| 用户分群 | 给新手和老用户不同难度 |
| 难度范围 | Runtime Agent 在范围内动态调整 |
| 奖励触发条件 | 根据完成率和风险调整提示 |
| CTA 时机 | 根据用户状态选择提前或延后 |
| 提示策略 | 流失风险高时增加提示 |
| 分享激励 | 高参与用户强化分享任务 |
| 风控等级 | 异常用户进入更严格路径 |

重要原则：

1. Agent 只能在变量允许的范围内调整。
2. Agent 不能改主目标和合规边界。
3. Agent 的每次调整都要记录为 `agent_decision_applied`。
4. 复盘时要能看出哪个变量调整影响了结果。

## 13. 约束和合规变量

Web3 / 金融 / 奖励相关 Playable 必须把约束变量前置，而不是上线前才检查。

| 约束变量 | 示例 |
|---|---|
| 禁止表达 | 不承诺收益、不保证空投、不暗示投资回报 |
| 奖励边界 | 只能是积分、资格、徽章或抽奖机会 |
| CTA 边界 | 不能诱导投资，只能引导了解、加入、注册或领取资格 |
| 风险提示 | 活动规则、非投资建议、奖励以官方规则为准 |
| 数据隐私 | 钱包、社媒、联系方式必须授权 |
| 反作弊 | 重复设备、重复钱包、异常点击限制 |

这些字段通常不应该让 KOL 自由删除。

## 14. 数据追踪变量

关键变量必须和埋点绑定，否则无法复盘。

| 变量 | 对应事件 |
|---|---|
| 模板类型 | `playable_start`、`scene_view` |
| 题目数量 / 任务数量 | `step_complete`、`drop_off` |
| 奖励触发 | `reward_granted` |
| CTA 设置 | `cta_click`、`conversion` |
| 分享设置 | `share_click` |
| Agent 调整 | `agent_decision_applied` |
| 用户分群 | 所有关键事件的维度字段 |
| 版本配置 | `playable_version_id` |

复盘时要能回答：

1. 是目标选错了，还是模板选错了？
2. 是关键变量配置不合理，还是内容生成不够好？
3. 是奖励太弱、CTA 太早，还是难度太高？
4. 是 KOL 受众不匹配，还是渠道不匹配？

## 15. 关键变量校验规则

生成前必须校验关键变量。

| 校验项 | 规则 |
|---|---|
| 主目标 | 必须存在，只能一个 |
| 模板类型 | 必须和目标匹配 |
| CTA | 必须和目标一致 |
| 奖励 | 必须有规则，不能误导 |
| 玩法参数 | 必须在模板允许范围内 |
| 合规字段 | 必须存在且不可被删除 |
| 资产 | 必需资产缺失时要降级或阻止生成 |
| 埋点 | 每个模板必须有基础事件 |
| 风控 | 高奖励或高风险活动必须开启 |

示例冲突：

| 冲突 | 处理 |
|---|---|
| 主目标是社群增长，但 CTA 是购买 | 要求用户修改 CTA 或切换目标 |
| 空投奖励很强，但没有反作弊 | 阻止发布或开启强校验 |
| 竞猜题目涉及收益承诺 | Constraint Service 重写或拦截 |
| 跑酷模板缺少角色和收集物 | 自动生成资产或推荐轻量模板 |

## 19. 结论

关键变量填写不是普通表单，而是 Agentic Playable 生成链路里的核心配置层。

它要解决四件事：

| 问题 | 解决方式 |
|---|---|
| 用户意图太模糊 | 用结构化字段表达目标、用户、玩法、奖励和 CTA |
| 生成结果不稳定 | 用 `template_config` 和默认值约束生成 |
| 上线风险不可控 | 用合规、奖励、风控变量提前校验 |
| 运营复盘说不清 | 把关键变量写入埋点和版本记录 |

MVP 阶段最合理的做法是：

1. 只让 KOL 确认 P0 变量。
2. 平台给 P1 默认值，允许用户调整。
3. Agent 自动生成 P2 细节。
4. 项目方和合规字段可以锁定。
5. 所有关键变量进入 `template_config`、`generation_brief`、`game_rules`、`agent_policy` 和数据追踪。

这样，关键变量填写就能从“用户填表”升级为“把营销意图变成可生成、可验证、可运营 Playable 的中间层”。
