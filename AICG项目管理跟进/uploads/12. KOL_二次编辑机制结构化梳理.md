# KOL 二次编辑机制结构化梳理

## 1. 核心定义

KOL 二次编辑，是指系统已经根据 KOL 身份、营销目标、模板、关键变量、Brief、内容、规则、Agent 策略、约束验证、H5 组装和模拟测试生成出一个可预览的 Playable 版本之后，KOL 在预览页或编辑器中对可控字段进行局部修改，系统再把这些修改转成结构化 `config_patch`，只重新生成、验证、组装和测试受影响模块。

它的核心不是让 KOL 改代码，也不是重新从头生成，而是让 KOL 在安全边界内做创作微调。

| 容易误解 | 正确认知 |
|---|---|
| KOL 二次编辑就是重新生成一次 | 应该生成 Patch，只更新受影响模块 |
| KOL 可以随便改所有内容 | 必须区分可编辑、需校验、需重算、锁定字段 |
| 只改文案不影响系统 | 文案可能影响合规、CTA、分享、奖励和埋点 |
| 二次编辑只是前台体验 | 后台要触发验证、重构建、回归测试和版本管理 |
| KOL 要懂模板和代码 | KOL 只改意图、表达和可控字段，系统处理技术链路 |

一句话：

**KOL 二次编辑 = KOL 在预览版本上做局部修改，系统生成 `config_patch`，再按影响范围局部重生成、重验证、重组装、重测试，形成新的 `playable_version`。**

## 2. 在完整工作流中的位置

KOL 二次编辑通常发生在 H5 组装和模拟测试之后、正式发布之前；发布后也可以用于版本迭代，但不能原地覆盖已发布版本。

| 阶段 | 输入 | 输出 |
|---|---|---|
| KOL 身份识别 | KOL 注册、社媒、历史 campaign、风险信号 | `kol_context` |
| 营销目标选择 | 目标、CTA、指标、渠道 | `campaign_goal` |
| 模板推荐 | 目标、KOL、资产、渠道 | `template_schema` |
| 关键变量填写 | 主题、奖励、任务、CTA、风格 | `template_config` |
| Brief 生成 | 上游意图和约束 | `generation_brief` |
| 内容生成 | Brief、模板、资产库 | `content_assets` |
| 游戏规则生成 | Brief、模板、内容、目标 | `game_rules` |
| Agent 运营策略生成 | 目标、规则、用户路径、风险 | `agent_policy` |
| 约束与合规验证 | 内容、规则、策略、目标、资产 | `validation_report` |
| H5 Playable 组装 | 通过验证的对象、模板代码、资产 | `playable_version` |
| 模拟测试 | 可运行版本、模拟用户、关键路径 | `simulation_result` |
| KOL 二次编辑 | 预览版本、KOL 修改、可编辑字段 | `config_patch` |
| 局部重生成 / 重验证 | Patch、受影响对象 | 新对象版本 |
| 局部重组装 | 新对象版本、模板代码 | 新 `playable_version` |
| 回归测试 | 新版本、受影响路径 | 新 `simulation_result` |
| 发布投放 | 测试通过版本、渠道参数 | `publish_url` |

关键原则：

1. KOL 不改代码，只改结构化字段。
2. 每次修改都形成 Patch，而不是覆盖原始版本。
3. 只重建受影响模块，不重跑整条链路。
4. 涉及规则、奖励、CTA、合规、埋点和 Agent 策略的修改必须重新校验。
5. 已发布版本不能原地覆盖，必须生成新版本。

## 3. KOL 二次编辑解决的问题

| 问题 | 二次编辑的价值 |
|---|---|
| AI 生成内容不够像 KOL | KOL 可以改语气、标题、分享文案 |
| KOL 不愿意发布 | 通过局部调整提升发布意愿 |
| 首版太通用 | 加入 KOL 专属表达、粉丝梗、社群语气 |
| 任务过难或过长 | 调整任务表达、任务数量或提示强度 |
| 分享卡不够传播 | 调整分享文案、结果表达和视觉焦点 |
| CTA 不够自然 | 调整 CTA 文案或展示语气 |
| 奖励表达不清 | 调整奖励说明，但不改变奖励性质 |
| 全量重生成成本高 | Patch 机制降低修改成本和等待时间 |
| 修改容易破坏合规 | 通过锁定字段和校验保护发布链路 |

## 4. 编辑权限分层

KOL 二次编辑必须做权限分层，否则很容易破坏模板、规则、合规和数据。

| 字段类型 | 含义 | 示例 | 处理 |
|---|---|---|---|
| 可自由编辑 | 改了不影响规则和合规核心 | 标题语气、部分描述文案、非关键视觉风格 | 内容 Patch + 轻校验 |
| 可编辑但需校验 | 可能影响转化、合规或数据 | 奖励文案、分享文案、CTA 文案、任务说明 | Patch + Constraint Service |
| 可编辑但需重算 | 影响规则、策略、埋点或版本 | 任务数量、题目数量、奖励条件、CTA 目标 | 回到对应上游模块 |
| 项目方锁定 | 必须保持 campaign 一致 | 项目名、Logo、官方链接、主 CTA 目标 | 不允许 KOL 修改 |
| 合规锁定 | 风险控制必需 | 免责声明、奖励边界、非投资建议、禁止表达 | 不允许删除或弱化 |
| 系统锁定 | 保障运行和追踪 | 事件名、版本 ID、风控规则、状态机关键字段 | 不允许前台编辑 |
| Agentic 可调 | 可由策略控制，不直接手改 | 难度、提示、CTA 时机、奖励提示强度 | 通过策略 Patch |
| Runtime 字段 | 运行中根据用户行为变化 | 用户分群、风险状态、动态推荐 | 不在 KOL 编辑器开放 |

## 5. KOL 可编辑字段建议

### 5.1 P0 优先开放

| 字段 | 说明 | 风险 |
|---|---|---|
| 首屏标题 | 最影响 KOL 是否愿意发 | 中 |
| 首屏副标题 | 解释活动价值 | 中 |
| 开始按钮文案 | 影响开始率 | 低 |
| 任务说明语气 | 影响完成率 | 中 |
| 结果反馈文案 | 影响分享和满意度 | 中 |
| 分享文案 | 影响传播 | 中 |
| 分享卡标题 | 影响社媒点击 | 中 |
| CTA 文案 | 影响转化 | 中 |
| KOL 专属称呼 | 增强身份感 | 低 |
| 视觉风格选择 | 背景、色调、角色风格 | 低到中 |

### 5.2 P1 再开放

| 字段 | 说明 | 风险 |
|---|---|---|
| 题目内容 | 影响玩法和内容质量 | 中 |
| 任务顺序 | 影响完成路径 | 中 |
| 任务数量 | 影响规则和完成率 | 中到高 |
| 奖励展示强度 | 影响激励和合规 | 中到高 |
| CTA 出现时机 | 影响规则和 Agent 策略 | 中到高 |
| 分享卡视觉 | 影响品牌和合规 | 中 |
| 提示文案 | 影响完成率 | 中 |
| 难度偏好 | 影响规则和 Agent 策略 | 中 |

### 5.3 P2 谨慎开放

| 字段 | 说明 | 风险 |
|---|---|---|
| 奖励条件 | 影响奖励触发、风控和合规 | 高 |
| CTA 目标链接 | 影响转化和安全 | 高 |
| 模板切换 | 影响全链路 | 高 |
| 游戏规则参数 | 影响状态机和可玩性 | 高 |
| Agentic 规则 | 影响运行时用户路径 | 高 |
| 风控强度 | 影响奖励安全 | 高 |
| 数据采集字段 | 影响隐私和合规 | 高 |

P2 字段可以给高级运营或项目方，而不是默认给所有 KOL。

## 6. 不建议 KOL 自由修改的字段

| 字段 | 原因 |
|---|---|
| 项目名 | 防止品牌错误和冒用 |
| 项目 Logo | 防止授权和品牌风险 |
| 主营销目标 | 牵动模板、CTA、指标和策略 |
| 主 CTA 目标 | 牵动转化路径和合规 |
| 奖励性质 | 防止积分被改成真实 Token 或现金 |
| 奖励发放规则 | 涉及风控和用户承诺 |
| 合规免责声明 | 不能被删除或弱化 |
| 非投资建议提示 | Web3 / 金融内容必须保留 |
| 反作弊规则 | 防止 KOL 为提高完成率绕过风控 |
| 关键埋点 | 防止数据断裂 |
| 版本 ID | 防止归因和回滚失效 |
| 状态机核心结构 | 防止游戏无法完成 |
| Runtime 风控逻辑 | 防止被绕过 |

锁定字段要在前台解释原因，否则 KOL 会误以为平台不可控或编辑器坏了。

## 7. 主要输入

| 输入 | 来源 | 作用 |
|---|---|---|
| `playable_version` | H5 Builder | 被编辑的当前预览版本 |
| `preview_url` | H5 Builder | KOL 体验和编辑入口 |
| `editable_field_schema` | 模板库 / 权限系统 | 定义哪些字段可改、怎么改 |
| `locked_field_schema` | 项目方 / 合规 / 系统 | 定义哪些字段不能改 |
| `kol_context` | KOL 身份识别 | 决定 KOL 语气、权限和风险 |
| `campaign_goal` | 营销目标选择 | 判断修改是否偏离目标 |
| `template_config` | 关键变量 | 判断修改是否影响本次活动配置 |
| `content_assets` | 内容生成 | 承接文案、视觉、任务类修改 |
| `game_rules` | 规则生成 | 判断修改是否影响状态机、奖励和 CTA |
| `agent_policy` | Agent 策略 | 判断修改是否影响动态难度、提示和 CTA |
| `validation_report` | 约束服务 | 判断修改是否触发重新验证 |
| `simulation_result` | 模拟测试 | 判断修改是否需要回归测试 |

## 8. 核心输出

统一输出对象是 `config_patch`。

| 输出字段 | 含义 |
|---|---|
| `config_patch_id` | Patch ID |
| `source_playable_version_id` | 修改基于哪个版本 |
| `target_playable_version_id` | 修改后生成的新版本，可为空 |
| `kol_id` | 修改人 |
| `campaign_id` | 所属 campaign |
| `patch_scope` | 内容、规则、策略、合规、埋点、视觉、渠道等 |
| `changed_fields` | 修改字段列表 |
| `before_values` | 修改前值 |
| `after_values` | 修改后值 |
| `impact_analysis` | 影响范围分析 |
| `requires_validation` | 是否需要重新约束验证 |
| `requires_rebuild` | 是否需要重新组装 H5 |
| `requires_simulation` | 是否需要回归测试 |
| `approval_status` | 自动通过、需运营确认、需项目方确认、被拒绝 |
| `created_at` | 创建时间 |
| `created_from` | 预览页、编辑器、运营后台或 API |

## 9. Patch 类型

| Patch 类型 | 影响对象 | 示例 |
|---|---|---|
| `brief_patch` | `generation_brief` | 改活动表达方向、目标用户、KOL 语气 |
| `content_patch` | `content_assets` | 改标题、任务文案、分享文案、结果反馈 |
| `visual_patch` | `visual_assets` | 改背景、角色、色调、图标 |
| `rule_patch` | `game_rules` | 改题目数量、任务顺序、奖励触发条件 |
| `agent_policy_patch` | `agent_policy` | 改提示策略、CTA 时机、难度偏好 |
| `cta_patch` | `campaign_goal` / `template_config` / `content_assets` | 改 CTA 文案或链接 |
| `reward_patch` | `game_rules` / `content_assets` / 合规 | 改奖励表达或条件 |
| `share_patch` | `share_assets` | 改分享卡文案、结果表达、邀请语 |
| `tracking_patch` | `tracking_map` | 补事件参数、修正归因 |
| `compliance_patch` | `validation_report` / 约束配置 | 补免责声明、替换风险表达 |

## 10. 标准二次编辑流程

| 步骤 | 动作 | 输出 |
|---|---|---|
| 1. KOL 打开预览 | 访问 `preview_url`，体验当前版本 | 预览行为 |
| 2. KOL 选择编辑字段 | 在可编辑字段中修改 | 编辑草稿 |
| 3. 前台即时校验 | 检查长度、格式、必填、锁定字段 | 表单校验结果 |
| 4. 生成 Patch | 把修改转为结构化 `config_patch` | Patch |
| 5. 影响范围分析 | 判断影响内容、规则、策略、合规、埋点还是渠道 | `impact_analysis` |
| 6. 约束验证 | 高风险字段进入 Constraint Service | Patch 验证结果 |
| 7. 局部重生成 | 只重生成受影响对象 | 新对象版本 |
| 8. H5 重组装 | Builder 根据 Patch 生成新预览版本 | 新 `playable_version` |
| 9. 回归测试 | 跑受影响路径 | 新 `simulation_result` |
| 10. KOL 再预览 | KOL 确认新版本 | 确认状态 |
| 11. 发布准备 | 通过后进入发布链路 | `publish_ready` |

## 11. 影响范围判断

KOL 修改后，系统首先要判断影响范围。

| KOL 修改 | 影响模块 | 处理 |
|---|---|---|
| 改首屏标题 | 内容、合规、视觉溢出 | `content_patch` + 轻校验 |
| 改副标题 | 内容、合规 | `content_patch` |
| 改开始按钮 | 内容、埋点触发位置 | `content_patch` + 开始事件回归 |
| 改任务说明 | 内容、规则理解、合规 | `content_patch` + 可能规则校验 |
| 改题目文案 | 内容、答案解释 | `content_patch` + 题目回归 |
| 改题目答案 | 规则、得分、结果 | `rule_patch` |
| 改题目数量 | 规则、页面、埋点、Agent 难度 | `rule_patch` + `agent_policy_patch` |
| 改任务顺序 | 规则、完成路径、埋点 | `rule_patch` |
| 改奖励文案 | 内容、合规、奖励理解 | `reward_patch` + 约束验证 |
| 改奖励条件 | 规则、风控、合规 | `rule_patch` + 人工或强校验 |
| 改分享文案 | 分享资产、合规、传播 | `share_patch` |
| 改分享图 | 视觉、品牌、分享合规 | `visual_patch` + 分享回归 |
| 改 CTA 文案 | 内容、CTA 事件 | `cta_patch` + CTA 回归 |
| 改 CTA 链接 | 渠道、授权、安全、归因 | `cta_patch` + 链接验证 |
| 改 CTA 目标 | 营销目标、规则、策略 | 回到 `campaign_goal` |
| 改视觉风格 | 视觉资产、页面布局 | `visual_patch` + 视觉回归 |
| 改难度偏好 | `agent_policy`、`game_rules` | 策略 Patch + 规则边界校验 |
| 改模板 | 全链路 | 重新推荐模板并生成 |

## 12. 前台编辑器设计

KOL 二次编辑应该在预览上下文里完成，而不是让 KOL 面对复杂后台配置。

| 编辑器模块 | 作用 |
|---|---|
| 手机预览 | 以真实移动端比例展示当前 Playable |
| 可编辑字段高亮 | 标记 KOL 可以改的位置 |
| 锁定字段提示 | 告诉 KOL 为什么不能改 |
| 字段侧边栏 | 展示标题、任务、奖励、CTA、分享等字段 |
| 版本历史 | 可回到上一个预览版本 |
| 即时风险提示 | 当文案涉及收益、空投、投资表达时提醒 |
| 字数和布局提示 | 避免标题、按钮、奖励文案溢出 |
| 重新生成预览 | 提交 Patch 后生成新版本 |
| 发布状态 | 告知是否通过验证和测试 |
| 问题列表 | 展示需要修改的问题 |

前台应避免：

1. 让 KOL 直接改 JSON。
2. 让 KOL 看复杂规则对象。
3. 把所有字段平铺给 KOL。
4. 只提示“失败”，不解释原因。
5. 允许 KOL 删除合规提示。

## 13. 编辑字段的优先级

二次编辑不应该让 KOL 被大量字段淹没。推荐按营销影响排序。

| 优先级 | 字段 | 为什么重要 |
|---|---|---|
| P0 | 首屏标题 / 利益点 | 决定点击后是否继续 |
| P0 | KOL 头像 / 名称 / 房间名 | 决定身份可信度 |
| P0 | 开始按钮 | 决定开始率 |
| P0 | 首个奖励表达 | 决定参与动机 |
| P0 | 初始任务链 | 决定完成率 |
| P0 | 结果反馈 | 决定满意度和分享意愿 |
| P0 | 分享卡 | 决定传播 |
| P0 | CTA 文案和时机 | 决定转化 |
| P1 | 题目内容 / 任务内容 | 决定体验质量 |
| P1 | 难度 / 时长 | 决定完成率 |
| P1 | 视觉风格 | 决定品牌和吸引力 |
| P1 | 提示文案 | 决定低意向用户是否完成 |
| P2 | Agentic 规则 | 决定动态运营能力 |
| P2 | 风控强度 | 决定奖励安全 |
| P2 | 数据看板维度 | 决定复盘深度 |

## 14. 约束与合规验证

KOL 二次编辑后，不是所有修改都能直接进入新版本。

| 修改类型 | 验证要求 |
|---|---|
| 普通标题 | 敏感词、长度、品牌一致性 |
| 奖励表达 | 是否承诺收益、是否误导、是否需要免责声明 |
| 空投表达 | 是否暗示必中、是否夸大价值 |
| CTA 文案 | 是否诱导投资、是否与目标一致 |
| CTA 链接 | 是否授权、安全、可追踪 |
| 分享文案 | 是否夸大奖励、是否误导传播 |
| 任务内容 | 是否强制刷量、骚扰或违规操作 |
| 视觉资产 | 是否使用未授权品牌、名人、交易所 Logo |
| Agent 策略 | 是否越过 `game_rules` 和 `runtime_boundaries` |
| 数据字段 | 是否采集未授权信息 |

处理方式：

| 验证结果 | 处理 |
|---|---|
| 通过 | 进入重组装 |
| 警告 | 可继续，但提示 KOL 或运营 |
| 自动修复 | 替换为安全表达后再确认 |
| 需修改 | 返回编辑器，让 KOL 修改 |
| 需人工审核 | 进入运营或项目方审核 |
| 阻止 | 不允许生成新版本 |

## 15. 与 H5 组装的关系

二次编辑最终要重新生成可运行版本。

| Patch 类型 | Builder 处理 |
|---|---|
| `content_patch` | 重新绑定文案、任务、结果、CTA |
| `visual_patch` | 重新处理资产和布局 |
| `share_patch` | 重新生成或绑定分享卡 |
| `cta_patch` | 重新绑定 CTA 文案、链接、事件参数 |
| `rule_patch` | 重新生成 `rule_config` 和状态机 |
| `agent_policy_patch` | 更新 `runtime_config` 中的策略配置 |
| `tracking_patch` | 更新 `tracking_map` |
| `compliance_patch` | 更新免责声明和风险提示 |

版本策略：

1. 二次编辑后生成新的 `playable_version_id`。
2. 新版本记录来源 Patch。
3. 原版本保留，可回滚。
4. 预览版本和发布版本分开。
5. 已发布版本不允许原地覆盖。

## 16. 与模拟测试的关系

二次编辑后必须做回归测试，但不一定全量测试。

| KOL 修改 | 回归测试范围 |
|---|---|
| 改标题 | 首屏可见、文案溢出、合规提示 |
| 改开始按钮 | 开始点击、`playable_start` |
| 改任务说明 | 任务页展示、任务完成事件 |
| 改题目 | 对应题目展示、选择、答案、事件 |
| 改奖励文案 | 奖励展示、免责声明、`reward_view` |
| 改奖励条件 | 规则测试、奖励测试、风控测试 |
| 改 CTA 文案 | CTA 展示、点击、`cta_view`、`cta_click` |
| 改 CTA 链接 | 链接、跳转、参数、授权 |
| 改分享卡 | 分享展示、`share_click`、合规提示 |
| 改 Agent 策略 | Agent 决策事件、策略边界、降级 |
| 改模板 | 全量模拟测试 |

阻断规则：

1. 改动后核心路径断裂，不能发布。
2. 改动后关键事件缺失，不能发布。
3. 改动后奖励触发错误，不能发布。
4. 改动后 CTA 不可点击或不可追踪，不能发布。
5. 改动后 Agent 越界，不能发布。

## 17. 与版本管理的关系

KOL 二次编辑必须和版本系统绑定。

| 对象 | 说明 |
|---|---|
| `source_playable_version_id` | 修改基于哪个版本 |
| `config_patch_id` | 本次修改记录 |
| `target_playable_version_id` | 修改后新版本 |
| `patch_version` | Patch 自身版本 |
| `validation_report_id` | Patch 验证报告 |
| `simulation_result_id` | 回归测试报告 |
| `publish_status` | 是否可发布 |
| `rollback_target` | 可回滚版本 |

版本管理原则：

1. 每个 Patch 都要可追溯。
2. 每个新版本都要能解释差异。
3. 已发布版本不能被直接覆盖。
4. KOL 可以比较两个预览版本。
5. 数据看板必须按版本归因。

## 18. 与数据反馈的关系

二次编辑本身也要被记录，因为它能反映 KOL 偏好和模板问题。

| 记录项 | 价值 |
|---|---|
| KOL 改了哪些字段 | 判断 KOL 最在意什么 |
| 哪些字段被反复修改 | 判断模板默认值是否不好 |
| 哪些 Patch 被拒绝 | 沉淀合规和风险案例 |
| 哪些修改提升发布率 | 优化生成默认值 |
| 哪些修改提升开始率 | 优化首屏和按钮 |
| 哪些修改提升完成率 | 优化任务和难度 |
| 哪些修改提升分享率 | 优化分享卡 |
| 哪些修改提升 CTA | 优化转化路径 |
| 哪些修改导致测试失败 | 优化可编辑边界 |

这些数据应回写：

| 回写对象 | 用途 |
|---|---|
| `kol_memory` | 记住 KOL 偏好和常用表达 |
| `template_memory` | 优化模板默认字段 |
| `negative_examples` | 沉淀违规和失败案例 |
| `generation_defaults` | 改善下一次首版生成 |
| `editable_field_schema` | 调整哪些字段开放 |

## 19. 前台 KOL 体验

KOL 的理想体验应该是轻量、明确、有控制感。

| 步骤 | KOL 看到什么 |
|---|---|
| 1. 打开预览 | 一个可玩的手机预览 |
| 2. 看到可编辑标记 | 标题、按钮、分享、奖励等位置可点 |
| 3. 修改字段 | 用自然语言或表单改内容 |
| 4. 看到风险提示 | 如果表达有风险，系统解释原因 |
| 5. 点击重新生成 | 生成新预览版本 |
| 6. 查看修改差异 | 看到改动前后对比 |
| 7. 通过测试 | 看到“可发布”状态 |
| 8. 提交发布 | 进入发布台 |

前台提示应该具体：

| 场景 | 推荐提示 |
|---|---|
| 字段锁定 | 该字段由项目方锁定，用于保持活动目标一致 |
| 奖励表达风险 | “必中空投”属于确定性奖励承诺，请改为“获得活动资格” |
| CTA 链接风险 | 当前链接未授权或缺少追踪参数，请使用项目方确认链接 |
| 文案过长 | 当前标题在手机首屏会换行遮挡按钮，请缩短 |
| 修改影响规则 | 修改任务数量会重新生成规则并重新测试 |
| 修改已通过 | 新版本已通过验证和回归测试，可以进入发布 |

## 20. 后台系统动作

| 前台动作 | 后台动作 |
|---|---|
| KOL 打开预览 | 读取 `playable_version` 和可编辑 schema |
| KOL 点击标题 | 加载标题字段和限制 |
| KOL 修改标题 | 生成 `content_patch` 草稿 |
| KOL 修改奖励文案 | 生成 `reward_patch` 并触发约束校验 |
| KOL 修改任务数量 | 生成 `rule_patch` 并触发规则重算 |
| KOL 修改 CTA 链接 | 触发链接授权、渠道参数和埋点校验 |
| KOL 提交修改 | 生成正式 `config_patch` |
| Patch 通过校验 | Builder 局部重组装 |
| 新版本生成 | 生成新 `playable_version` 和预览链接 |
| 回归测试通过 | 标记可发布 |
| 回归测试失败 | 返回问题和修复建议 |

## 24. 示例：空投任务二次编辑

| KOL 修改 | 原始内容 | 修改后 | 系统处理 |
|---|---|---|---|
| 首屏标题 | 完成任务领取空投资格 | 和我一起解锁社区任务徽章 | `content_patch` |
| 奖励文案 | 必中空投 | 获得活动积分和抽选资格 | `reward_patch` + 合规校验 |
| 任务说明 | 邀请好友 | 邀请好友加入社区挑战 | `content_patch` + 分享校验 |
| CTA 文案 | 加入 Telegram | 进群查看任务进度 | `cta_patch` |
| CTA 链接 | KOL 自填链接 | 未授权链接 | 阻止，要求项目方链接 |
| 钱包提示 | 删除用途说明 | 删除 | 阻止，合规锁定 |
| 任务数量 | 5 个改 3 个 | 3 个任务 | `rule_patch` + 回归测试 |

生成链路：

1. 生成 `config_patch`。
2. 判断包含 `content_patch`、`reward_patch`、`cta_patch`、`rule_patch`。
3. 奖励和 CTA 进入约束验证。
4. 任务数量触发 `game_rules` 更新。
5. Builder 生成新 `playable_version`。
6. 模拟测试跑任务、奖励、CTA、分享和风控路径。
7. 通过后进入发布。

## 28. 不建议的做法

| 不建议做法 | 问题 |
|---|---|
| KOL 每次修改都全量重生成 | 成本高、慢、不可控 |
| 所有字段都开放 | 容易破坏规则、合规、埋点和品牌 |
| 只保存最终结果，不保存 Patch | 无法追溯和复盘 |
| 已发布版本原地覆盖 | 数据归因和回滚失效 |
| 修改后不做回归测试 | 容易发布坏版本 |
| 修改 CTA 链接不校验 | 安全和归因风险 |
| 奖励文案不重新验证 | 容易出现收益承诺 |
| 允许删除免责声明 | 合规风险高 |
| 让 KOL 改 JSON 或代码 | 体验差且风险高 |
| 不解释锁定字段 | KOL 会认为平台限制不透明 |

## 29. 结论

KOL 二次编辑是 Agentic Playable 从“系统生成”走向“KOL 愿意发布”的关键协作环节。

它要回答五个问题：

| 问题 | 对应机制 |
|---|---|
| KOL 能改什么？ | `editable_field_schema` |
| 哪些不能改？ | 锁定字段和权限分层 |
| 修改影响哪里？ | `impact_analysis` |
| 如何不重跑全链路？ | `config_patch` 和局部重生成 |
| 修改后能不能发布？ | 约束验证、H5 重组装、回归测试 |

MVP 阶段最重要的是：

1. 先开放高价值、低风险字段：标题、按钮、任务说明、分享文案、CTA 文案、视觉风格。
2. 奖励、CTA、合规、规则和 Agent 策略相关修改必须重新校验。
3. 每次修改都形成 `config_patch`，并生成新的 `playable_version`。
4. 不允许 KOL 删除合规提示、改变奖励性质、绕过风控或修改关键埋点。
5. 二次编辑后的版本必须做受影响路径回归测试，再进入发布。
