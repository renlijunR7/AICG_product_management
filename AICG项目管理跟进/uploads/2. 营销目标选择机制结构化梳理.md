# 营销目标选择机制结构化梳理

## 1. 核心结论

Airvana 的营销目标选择不应该做成单纯的“平台默认”或“用户自己选择”，而应该采用：

**平台推荐默认目标 + 用户确认/调整 + 特定场景目标锁定**

原因是营销目标会直接影响后续生成链路：

| 影响对象 | 营销目标会决定什么 |
|---|---|
| 模板推荐 | 推荐竞猜、答题、盲盒、抽奖、任务链、排行榜还是分享裂变 |
| 首屏文案 | 是强调项目认知、奖励、社群身份、挑战感还是立即转化 |
| 玩法结构 | 是短路径转化、教育型答题、连续任务还是社交裂变 |
| 奖励节奏 | 是首局奖励、完赛奖励、分享奖励、社群任务奖励还是转化奖励 |
| CTA 策略 | 是关注、入群、注册、领取、分享、购买还是预约 |
| Agentic 策略 | 动态调整难度、提示、奖励、CTA 时机和分群推荐 |
| 埋点指标 | 看曝光、开始、完成、分享、入群、注册、领取还是复玩 |
| 数据看板 | 按不同目标展示不同核心指标和诊断结论 |

所以，营销目标必须是一个结构化对象 `campaign_goal`，而不是普通下拉框。

## 2. 产品判断

| 方案 | 优点 | 问题 | 是否推荐 |
|---|---|---|---|
| 平台完全默认 | 使用简单，新手不需要理解营销术语 | 容易生成不符合 KOL 意图的活动，用户控制感弱 | 不推荐单独使用 |
| 用户完全选择 | 用户自主性强 | 新手容易选错，营销目标和模板/CTA 不匹配 | 不推荐单独使用 |
| 平台推荐 + 用户确认 | 降低选择成本，同时保留控制权 | 需要解释推荐理由 | 推荐 |
| 项目方发起时锁定主目标 | 保证项目 campaign 一致性 | KOL 创作自由度降低 | 特定场景推荐 |

推荐原则：

1. **主目标只能有一个**，否则生成逻辑会分裂。
2. **次目标最多一个**，用于辅助优化，不参与核心生成冲突。
3. **平台必须给推荐理由**，让 KOL 知道为什么推荐这个目标。
4. **KOL 自主活动允许修改目标**，否则会削弱创作感。
5. **项目方发起活动可以锁定主目标**，KOL 只改表达角度和内容包装。

## 3. 三种目标选择模式

### 3.1 模式一：平台推荐，KOL 确认

这是 Airvana MVP 最推荐的默认模式。

| 适用场景 | 说明 |
|---|---|
| KOL 第一次使用平台 | KOL 不熟悉目标体系，平台降低理解成本 |
| KOL 自主创建活动 | 平台根据身份、模板、历史数据推荐目标 |
| 平台已有 KOL 数据 | 根据过往表现推荐更适合的目标 |
| 模板目标比较明确 | 例如空投任务模板天然偏社群增长和参与转化 |

前台体验：

| 页面动作 | 用户看到什么 |
|---|---|
| 选择模板后 | 平台自动显示“推荐营销目标” |
| 推荐卡片 | 展示主目标、推荐原因、核心指标 |
| 用户确认 | 可以直接使用推荐目标 |
| 用户调整 | 可以更换目标或添加一个次目标 |

推荐文案示例：

| 展示项 | 示例 |
|---|---|
| 推荐目标 | 社群增长 |
| 推荐原因 | 你选择的是 Web3 空投任务模板，该模板更适合引导用户加入 Telegram / Discord 并完成任务 |
| 核心指标 | 入群点击率、任务完成率、分享率 |
| 生成影响 | 系统会强化社群任务、排行榜、分享卡和入群 CTA |

### 3.2 模式二：项目方/平台预设主目标，KOL 选择表达方式

当活动由项目方发起，主目标应该由项目方或平台运营预设，不能让每个 KOL 自由改变。

| 适用场景 | 说明 |
|---|---|
| 项目方邀请 KOL 参与统一 campaign | 保证所有 KOL 服务同一个项目目标 |
| 空投预热活动 | 主目标可能是白名单报名、社群增长或任务完成 |
| 新品发布活动 | 主目标可能是项目教育或预约注册 |
| 交易所 / 钱包 / GameFi 联合活动 | 主目标可能是注册、领取或参与任务 |

前台体验：

| 元素 | 规则 |
|---|---|
| 主目标 | 已由项目方设定，KOL 不可修改 |
| 次目标 | 可选，必须不冲突 |
| 表达角度 | KOL 可选择专业解释、娱乐挑战、粉丝福利、排行榜竞争等 |
| 模板范围 | 只展示符合项目目标的模板 |
| CTA | 由项目方设定，KOL 只能改文案语气，不能改目标动作 |

这种模式下，KOL 的创作空间应该放在：

1. 首屏表达方式。
2. 题目和任务包装。
3. 分享卡语气。
4. 粉丝身份设计。
5. KOL 专属房间名称。
6. 结果反馈文案。

而不是放在主目标和转化路径上。

### 3.3 模式三：高级用户手动选择

对于专业运营、机构 KOL、项目方运营人员，可以开放更强控制权。

| 适用用户 | 可开放能力 |
|---|---|
| 项目方运营 | 选择主目标、次目标、CTA、渠道和核心指标 |
| 机构 KOL / MCN | 给不同 KOL 批量分配不同目标 |
| 高频 KOL | 保存自己的目标偏好和模板组合 |
| 平台运营 | 手动覆盖系统推荐并记录原因 |

但高级模式也要有边界：

| 边界 | 说明 |
|---|---|
| 主目标仍然只能一个 | 避免生成冲突 |
| 目标和 CTA 必须匹配 | 不能选择社群增长却设置购买 CTA 为唯一转化 |
| 高风险目标需要审核 | 涉及奖励、收益、金融、投资表达时要进入约束校验 |
| 手动覆盖必须记录原因 | 便于后续复盘和责任追踪 |

## 4. 营销目标分类

Airvana MVP 可以先支持 7 类标准目标。

| 目标 | 用户语言 | 系统目标 | 适合模板 | 核心指标 |
|---|---|---|---|---|
| 项目认知 | 让更多人了解这个项目 | `awareness` | 答题、知识闯关、剧情介绍 | 曝光、开始率、完赛率 |
| 用户教育 | 让用户理解产品或玩法 | `education` | 问答、测验、教程型任务 | 完赛率、正确率、停留时长 |
| 拉新激活 | 让新用户开始参与 | `activation` | 新手任务、短挑战、盲盒 | 开始率、首个任务完成率 |
| 社群增长 | 让用户加入 Telegram / Discord / 社群 | `community_growth` | 任务链、排行榜、邀请挑战 | 入群点击率、任务完成率 |
| 转化领取 | 让用户注册、领取、预约、购买 | `conversion` | 奖励任务、结果页 CTA、抽奖 | CTA 点击率、最终转化 |
| 裂变传播 | 让用户分享给朋友 | `referral` | 分享卡、排行榜、组队任务 | 分享率、邀请点击、二跳用户 |
| 留存复活 | 让老用户回来继续参与 | `retention` | 连续任务、签到、进阶挑战 | 复玩率、复访率、连续参与 |

建议前台不要直接展示英文系统目标，而是用用户能理解的问题引导。

## 5. 前台交互设计

### 5.1 不建议直接问“请选择营销目标”

很多 KOL 不一定理解“拉新、转化、留存、裂变”这些运营术语。更好的方式是问：

**你希望粉丝完成什么动作？**

| 用户选择 | 映射目标 |
|---|---|
| 了解项目是做什么的 | 项目认知 / 用户教育 |
| 开始参与一个活动 | 拉新激活 |
| 加入我的社群 | 社群增长 |
| 完成注册或领取资格 | 转化领取 |
| 分享给朋友一起玩 | 裂变传播 |
| 老用户回来继续参与 | 留存复活 |

### 5.2 推荐目标卡片

平台给出推荐目标时，必须同时展示 4 个信息：

| 信息 | 作用 |
|---|---|
| 推荐目标 | 告诉用户系统建议做什么 |
| 推荐理由 | 建立信任，避免黑盒推荐 |
| 核心指标 | 告诉用户后续看什么数据 |
| 生成影响 | 告诉用户这个选择会改变哪些内容 |

推荐卡片可以这样组织：

| 字段 | 内容 |
|---|---|
| 推荐目标 | 社群增长 |
| 推荐理由 | 你选择了空投任务模板，且连接的 X 账号以 Web3 社群用户为主 |
| 核心指标 | 入群点击率、任务完成率、分享率 |
| 生成影响 | 系统会强化社群任务、邀请机制、排行榜和入群 CTA |
| 可选操作 | 使用推荐 / 更换目标 / 添加次目标 |

### 5.3 目标选择后的二次确认

用户确认目标后，平台应该把“目标影响”展示清楚。

| 确认项 | 示例 |
|---|---|
| 主目标 | 社群增长 |
| 次目标 | 项目教育 |
| CTA | 加入 Telegram |
| 推荐模板 | 空投任务链、知识答题、排行榜挑战 |
| 核心看板 | 入群点击率、任务完成率、分享率 |
| Agentic 策略 | 动态任务提示、分享奖励、入群 CTA 时机 |

这个确认页的作用是防止用户选错目标后，后面才发现生成结果不符合预期。

## 6. 后台决策逻辑

平台推荐营销目标时，可以从 8 类信号中判断。

| 信号 | 示例 | 影响 |
|---|---|---|
| 项目方 Campaign Brief | 项目方要求增长社群或推广新品 | 最高优先级 |
| 模板默认目标 | 空投任务偏社群增长，答题偏教育 | 强推荐信号 |
| KOL 身份画像 | Web3 教育型 KOL、交易型 KOL、娱乐型 KOL | 影响目标和表达方式 |
| KOL 历史效果 | 分享率高、转化高、完成率低等 | 推荐最可能有效的目标 |
| 社媒受众画像 | 粉丝是新手、交易用户、社区用户 | 影响教育/转化/社群目标 |
| 用户入口来源 | 项目邀请、自主创建、模板市场、复盘建议 | 决定是否锁定 |
| 风险与合规信号 | 金融、收益、奖励、空投相关风险 | 限制目标和 CTA |
| 平台运营策略 | 当前阶段需要冷启动、验证模板或复投 | 调整推荐优先级 |

### 6.1 推荐优先级

| 优先级 | 规则 |
|---|---|
| P0 | 项目方明确设定目标时，主目标锁定 |
| P0 | 合规规则禁止某类目标时，不允许选择 |
| P1 | 模板只有单一强目标时，平台默认推荐 |
| P1 | KOL 历史数据明确指向某目标时，优先推荐 |
| P2 | 没有历史数据时，根据 KOL 身份和模板推断 |
| P2 | 信息不足时，使用新手默认目标并要求用户确认 |

### 6.2 推荐结果必须带置信度

| 置信度 | 场景 | 产品表现 |
|---|---|---|
| 高 | 项目方锁定、模板目标明确、历史数据充分 | 默认选中，推荐直接使用 |
| 中 | 模板和 KOL 画像一致，但历史数据不足 | 默认推荐，但提示可调整 |
| 低 | 新用户、数据少、输入模糊 | 让用户主动选择，不强推荐 |

## 7. `campaign_goal` 数据结构

`campaign_goal` 建议包含以下字段。

| 字段 | 说明 |
|---|---|
| `primary_goal` | 主目标，只能一个 |
| `secondary_goal` | 次目标，最多一个，可为空 |
| `goal_source` | 目标来源：项目方预设、平台推荐、用户选择、运营覆盖 |
| `goal_lock_status` | 是否锁定：可修改、部分锁定、完全锁定 |
| `recommendation_confidence` | 推荐置信度 |
| `recommendation_reason` | 推荐原因 |
| `user_confirmed` | 用户是否确认 |
| `override_reason` | 用户或运营覆盖系统推荐的原因 |
| `target_action` | 用户最终要完成的动作 |
| `primary_cta` | 主 CTA |
| `secondary_cta` | 次 CTA，可为空 |
| `target_metrics` | 该目标对应的核心指标 |
| `template_constraints` | 对模板选择的约束 |
| `agent_policy_constraints` | 对运行时 Agent 策略的约束 |
| `compliance_constraints` | 合规约束 |
| `created_from_context` | 使用了哪些上下文生成推荐 |

## 8. 目标到生成链路的映射

| 主目标 | 模板推荐 | 文案方向 | 奖励策略 | CTA 策略 | 看板指标 |
|---|---|---|---|---|---|
| 项目认知 | 知识答题、剧情介绍 | 解释项目价值和使用场景 | 完赛反馈、知识徽章 | 了解更多、关注项目 | 开始率、完赛率、停留 |
| 用户教育 | 问答、教程任务 | 降低理解成本，强调学习 | 正确率反馈、进阶提示 | 查看教程、进入文档 | 完赛率、正确率 |
| 拉新激活 | 新手挑战、盲盒 | 强化低门槛和即时反馈 | 首次参与奖励 | 开始参与、领取资格 | 开始率、首任务完成 |
| 社群增长 | 任务链、排行榜 | 强调一起参与和社群身份 | 入群任务、邀请奖励 | 加入 Telegram / Discord | 入群点击、任务完成 |
| 转化领取 | 奖励任务、结果页 CTA | 强调明确利益和下一步动作 | 完成后触发资格 | 注册、领取、预约、购买 | CTA 点击、最终转化 |
| 裂变传播 | 分享卡、组队挑战 | 强调结果炫耀和邀请朋友 | 分享奖励、组队奖励 | 分享给朋友 | 分享率、邀请点击 |
| 留存复活 | 连续任务、签到挑战 | 强调进度、等级、连续权益 | 连续奖励、复玩奖励 | 继续挑战、回到活动 | 复玩率、复访率 |

## 9. 目标冲突处理

营销目标之间会有冲突，系统必须拦截。

| 冲突 | 表现 | 处理方式 |
|---|---|---|
| 社群增长 vs 直接购买 | 用户还未建立信任，却要求直接购买 | 主目标二选一，另一个作为次目标或后置 CTA |
| 用户教育 vs 短路径转化 | 教育内容需要时间，转化要求路径短 | 用教育作为主目标，转化放在结果页 |
| 裂变传播 vs 高合规风险 | 用户分享可能扩大违规表达 | 强化审核，限制分享文案自由编辑 |
| 空投参与 vs 反作弊 | 奖励越强，刷量越多 | 加钱包、设备、行为和任务校验 |
| KOL 自主目标 vs 项目方目标 | KOL 想做粉丝福利，项目方要注册转化 | 项目方活动锁主目标，KOL 改表达方式 |

## 10. MVP 实施建议

### 10.1 P0 必须做

| 模块 | 要求 |
|---|---|
| 标准目标枚举 | 先支持 7 类目标 |
| 用户自然语言选择 | 用“你希望粉丝完成什么动作”替代专业术语 |
| 平台推荐目标 | 至少根据模板类型和入口来源推荐 |
| 用户确认机制 | 推荐后必须确认 |
| 主目标唯一 | 不允许多个主目标 |
| CTA 匹配校验 | 目标和 CTA 必须一致 |
| 目标写入 `campaign_goal` | 后续生成链路统一读取 |
| 目标影响展示 | 告诉用户会影响模板、奖励、CTA、看板 |

### 10.2 P1 再做

| 模块 | 要求 |
|---|---|
| KOL 历史表现推荐 | 根据开始率、完成率、分享率、CTA 推荐目标 |
| 项目方锁定主目标 | 项目邀请活动不让 KOL 改主目标 |
| 次目标机制 | 允许一个不冲突的次目标 |
| 推荐置信度 | 高/中/低置信度展示不同交互 |
| 运营覆盖记录 | 运营手动修改要记录原因 |

### 10.3 P2 平台化后做

| 模块 | 要求 |
|---|---|
| 多 KOL 批量目标分配 | 项目方给不同 KOL 分配不同子目标 |
| 自动实验 | 不同目标/CTA 做 A/B 测试 |
| 复盘反推目标 | Diagnosis Agent 判断下一次该换目标还是换模板 |
| 目标策略库 | 沉淀行业、模板、KOL 类型对应的最佳目标 |

## 11. 推荐流程

完整流程建议如下：

1. 用户进入创建活动。
2. 系统判断入口来源：项目邀请、自主创建、模板市场、复盘建议。
3. 如果是项目邀请，读取项目方预设目标。
4. 如果不是项目邀请，读取 KOL 身份、模板、历史表现和受众数据。
5. 平台生成推荐主目标和推荐理由。
6. 用户确认、修改或添加次目标。
7. 系统校验主目标、次目标、CTA 和模板是否冲突。
8. 生成 `campaign_goal`。
9. Brief Agent 根据 `campaign_goal` 生成创作 Brief。
10. Strategy Agent 根据 `campaign_goal` 生成玩法、奖励和 CTA 策略。
11. Runtime Agent 根据 `campaign_goal` 决定运行时优化方向。
12. 数据看板根据 `campaign_goal` 展示对应指标。
13. Diagnosis Agent 根据目标完成情况输出复盘。

## 12. 不同场景下的选择规则

| 场景 | 推荐规则 |
|---|---|
| KOL 第一次使用 | 平台推荐一个新手默认目标，用户确认 |
| KOL 选择空投模板 | 默认推荐社群增长或转化领取 |
| KOL 选择答题模板 | 默认推荐项目认知或用户教育 |
| KOL 选择排行榜模板 | 默认推荐裂变传播或留存复活 |
| KOL 历史分享率高 | 优先推荐裂变传播 |
| KOL 历史转化率高 | 优先推荐转化领取 |
| KOL 历史完成率低 | 不建议直接转化，先推荐拉新激活或用户教育 |
| 项目方邀请活动 | 主目标由项目方锁定 |
| 高风险奖励活动 | 限制转化和奖励表达，进入合规校验 |

## 13. 对前后台的分工

| 角色 | 职责 |
|---|---|
| KOL | 确认目标、选择表达方式、决定是否接受推荐 |
| 项目方 | 在项目 campaign 中设定主目标、CTA 和核心指标 |
| 平台运营 | 配置目标体系、审核高风险目标、手动覆盖特殊活动 |
| Brief Agent | 把目标转换成创作 Brief |
| Strategy Agent | 把目标转换成玩法、奖励、CTA 和分群策略 |
| Constraint Service | 校验目标、CTA、奖励和合规边界 |
| Runtime Agent | 根据目标优化用户路径 |
| Diagnosis Agent | 判断目标是否达成，并给下一轮建议 |

## 14. 结论

Airvana 的营销目标选择应该是一个“推荐-确认-约束-复盘”的机制：

| 阶段 | 机制 |
|---|---|
| 推荐 | 平台根据入口、模板、KOL 画像、历史表现和项目 Brief 给默认目标 |
| 确认 | KOL 确认或调整，避免黑盒生成 |
| 约束 | 项目方活动、合规风险、CTA 匹配关系可以限制可选范围 |
| 生成 | `campaign_goal` 驱动 Brief、玩法、奖励、CTA、Agentic 策略 |
| 复盘 | 数据看板和 Diagnosis Agent 判断目标是否选对 |

MVP 阶段最推荐的产品方案是：

**平台默认推荐一个主目标，用户必须确认；项目方发起的活动可以锁定主目标；高级用户和运营可以手动覆盖，但必须记录原因。**
