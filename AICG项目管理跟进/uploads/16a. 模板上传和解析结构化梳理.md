# 模板上传和解析机制结构化梳理

## 1. 核心定义

模板上传和解析机制，是 Airvana Agent OS 模板供给侧的入口，位于所有业务链路之前。

它负责回答两个问题：

| 环节 | 回答的问题 | 一句话 |
|---|---|---|
| 模板上传 | 模板从哪来、归谁管 | 让模板**进得来、管得住** |
| 模板解析 | 模板能被系统怎么用 | 把静态工程变成**可推荐、可生成、可验证、可运营**的结构化玩法容器 |

核心产物：

| 产物 | 说明 |
|---|---|
| `template_package` | 上传的原始工程 / 素材包 + 最小元数据 |
| `template_schema` | 可编辑字段、锁定字段、Agentic 可调字段 |
| `asset_manifest` | 必需 / 可选资产清单与缺口 |
| `instrument_report` | 埋点能力检查结果 |
| `intake_report` | 合规与质量预检结论（通过 / 整改 / 拒绝） |

## 2. 所处位置

| 上游 | 当前环节 | 下游 |
|---|---|---|
| codex + godot 模板生成、开发者 / KOL 自制模板、SEELE AI 等外部工具产出 | 模板入库与 schema 生成 | KOL / 项目方输入与身份上下文、模板推荐、模板与 AI 生成规划 |

如果这个环节缺失，模板库只能靠官方自建，推荐系统没有结构化输入，后面所有"按字段生成、按字段编辑、按字段验证"的机制都无从谈起。

## 3. 业务目标

### 3.1 模板上传的目的

| 目标 | 说明 |
|---|---|
| 供给侧扩容 | 模板库不再只靠官方自建：KOL、开发者、AI 产出都能进库 |
| 资产入库与版本管理 | 一个 H5 工程 / 素材包变成平台资产：有版本号、归属人、审核状态 |
| 确权与复用边界 | 上传时确定谁可用、哪些可改、是否参与分成 / 核销 |
| 标准化入口 | 强制附带最小元数据（玩法类型、适用渠道、资产清单、时长），为推荐系统供料 |

### 3.2 模板解析的目的

| 目标 | 说明 |
|---|---|
| 生成 template_schema（最核心） | 拆出可编辑字段 / 锁定字段 / Agentic 可调字段，是推荐、Brief、生成、验证、二次编辑的共同地基 |
| 资产清单提取 | 识别必需 / 可选资产及缺口，支撑资产准备度判断和缺失提示 |
| 玩法结构识别 | 核心操作、关卡 / 难度 / 奖励 / CTA 挂点，决定 Agentic 可调项和延展能力 |
| 埋点能力检查 | 检查开始 / 完成 / 分享 / CTA / 流失事件，缺失则注入 |
| 合规与质量预检 | 收益承诺、奖励误导、性能问题在入库时拦截 |
| 落成推荐维度 | 解析结果打分成推荐系统维度：目标适配、资产要求、分享潜力、Agentic 潜力 |

## 4. 上传的输入

| 输入 | 是否必需 | 说明 |
|---|---:|---|
| 模板工程包 | 必需 | H5 工程 / Godot 导出 / 引擎产物 |
| 玩法类型声明 | 必需 | 竞猜、跑酷、塔防、空投任务等 |
| 适用目标与渠道 | 必需 | 拉新 / 教育 / 裂变；X / TG / TikTok |
| 资产清单 | 必需 | 哪些素材可替换、尺寸规格 |
| 可编辑字段声明 | 建议 | 上传者标注哪些字段开放给 KOL |
| 归属与授权 | 必需 | 作者、可用范围、分成规则 |
| 演示链接 / 录屏 | 建议 | 加速人工审核 |

## 5. 解析流水线

1. **结构扫描** — 校验工程完整性、入口文件、依赖和体积。
2. **字段抽取** — 结合上传者声明与代码分析，抽出可配置字段。
3. **字段分层** — 标记为可编辑 / 锁定 / Agentic 可调三类。
4. **资产清单生成** — 识别素材引用点，产出必需 / 可选资产与规格。
5. **玩法结构识别** — 识别关卡、难度、奖励、CTA 挂点和失败 / 胜利机制。
6. **埋点检查与注入** — 核对五类核心事件，缺失自动注入 SDK 埋点。
7. **合规与质量预检** — 收益承诺、奖励表述、加载性能、移动端适配。
8. **schema 落库** — 生成 `template_schema` + `asset_manifest`，进入模板库。
9. **推荐维度打分** — 按目标适配、资产准备、分享潜力、Agentic 潜力打初始分。

## 6. 解析结论与处理

| 结论 | 条件 | 处理 |
|---|---|---|
| 通过 | schema 完整、埋点齐、无合规问题 | 进入模板库，参与推荐 |
| 整改 | 字段声明不全、埋点缺失可注入、资产规格不符 | 返回整改清单，上传者补充后重新解析 |
| 拒绝 | 收益承诺、违规内容、无法运行 | 拒绝入库，记录原因 |

## 7. MVP 实施建议

### 7.1 P0 先做

| 模块 | 要求 |
|---|---|
| 上传入口 + 最小元数据表单 | 玩法类型、目标、渠道、资产清单必填 |
| 声明式解析 | 先靠上传者声明 + 人工校验生成 schema，不追求全自动 |
| 埋点检查清单 | 五类核心事件人工核对 + SDK 注入 |
| 版本与归属记录 | 每次上传生成版本号，记录作者与授权 |

### 7.2 P1 再做

| 模块 | 要求 |
|---|---|
| 自动字段抽取 | 代码分析辅助生成可编辑字段 |
| 资产缺口自动识别 | 与资产准备度判断打通 |
| 合规预检自动化 | 文案扫描 + 规则库 |

### 7.3 P2 平台化后做

| 模块 | 要求 |
|---|---|
| codex + godot 产物直连 | AI 生成模板自动走解析流水线入库 |
| 解析结果反哺推荐权重 | 与模板表现数据联动 |
| 第三方开发者生态 | 开放上传规范与分成体系 |

## 8. 不建议的做法

| 不建议事项 | 原因 |
|---|---|
| 上传只收 zip 不收元数据 | 解析无从下手，推荐系统无米下锅 |
| 解析只做格式校验 | 没有 schema，后面全部环节退化成人工改代码 |
| 埋点留到发布前才检查 | 返工成本高，且容易带病上线 |
| 一开始追求全自动解析 | MVP 阶段声明式 + 人工校验更可控 |
| 不记录归属与授权 | 分成、核销和品牌合作无法落地 |

## 9. 结论

模板上传解决供给和治理：让模板进得来、有版本、有归属、有边界。

模板解析解决可用性：把一个静态工程变成带 `template_schema`、资产清单、埋点能力和合规结论的结构化玩法容器。

MVP 阶段建议：上传入口 + 声明式解析 + 埋点清单先跑通，自动化解析和 AI 产物直连放到 P1 / P2。
